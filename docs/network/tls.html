TLS 握手：加密的连接是怎么建起来的

总览里说，TCP 连上之后还要再握一次手，花了 15 毫秒，之后的内容路上就没人看得懂了。这份笔记把这 15 毫秒拆开：两边各发了哪几条消息、每条多大、证书凭什么可信、密钥是怎么当着所有人的面商量出来的。

客户端收尾64 字节

一个来回约 15 ms

数据是 2026-11-20 用 OpenSSL 3.6.1 的 s_client 连 mythlin19920302.github.io:443 实测的，密钥交换限定用 X25519（原因见第 06 节）。耗时用 curl 测了 20 次，取中位数。证书会定期更换，文中的日期和大小以这一天为准。握手在整个请求里的位置见 一个请求是怎么送到的。

01TLS 管的三件事

HTTP 的请求和响应本来是明文。从手机到服务器，中间隔着家里的路由器、运营商和机房的设备（总览里数过，六台路由器），每一台都能看到内容，也能改内容。TLS（Transport Layer Security，传输层安全）夹在 TCP 和 HTTP 之间，替上面的协议做三件事：

保证意思没有它会怎样靠什么做到
保密路上的人看不懂内容沿途任何一台设备都能读到你的请求和页面对称加密
完整内容被改过能发现页面里被插进广告，下载的文件被换掉每条记录带 16 字节的校验标签
身份对面确实是这个域名的主人连上的是冒充的服务器，加密得再好也是白搭证书和签名
 
HTTP/2     应用层   GET /Media/
TLS 1.3    本文　   先握手，再把上面交下来的字节加密
TCP        传输层   端口 443，保证不丢、不乱

https:// 就是 HTTP 跑在 TLS 上，默认端口从 80 换成 443。SSL 是它的旧名字，现在说的"SSL 证书""SSL 握手"指的都是 TLS。

这三件事都要在发出第一个字节的 HTTP 之前准备好，这个准备过程就是握手。总览里 41 毫秒的页面加载，TLS 握手占 15 毫秒；这次重测 20 遍，中位数是 15.2 毫秒。

TLS 不管的事也要清楚：它不隐藏你在和谁通信（第 09 节），不保证服务器本身可靠，也不管数据到了对方之后怎么存。

02两种加密：快的和慢的

加密算法分两类，TLS 两类都用：

对称加密非对称加密
密钥加密和解密用同一把一对：公钥可以公开，私钥自己留着
速度快慢
难处两边怎么先拿到同一把密钥？直接发过去，路上的人就看到了太慢，不能用来处理大量数据
这次握手里的AES-128-GCMX25519（商量密钥）、RSA（签名）

非对称算法在 TLS 1.3 里只做两种事：

  • 密钥交换。两边各拿自己的私钥和对方的公钥算一次，得到同一个数。路上的人只看到两个公钥，算不出这个数。见第 06 节。
  • 签名。用私钥对一段数据算出一个签名，任何人拿公钥都能验证它是真的，但没有私钥就造不出来。证书和握手里的身份证明都靠它。

还有一样工具是哈希：把任意长的数据算成固定长度的指纹，SHA-256 的指纹是 32 字节。数据改一个比特，指纹就完全不同。签名签的其实是数据的哈希，握手里派生密钥、核对消息也用它。

运算类别实测速度
AES-128-GCM 加密对称约 10.4 GB/s
ChaCha20-Poly1305 加密对称约 2.2 GB/s
X25519 算一次共享的数非对称每次 0.033 ms
RSA 2048 位，签名一次非对称每次 0.34 ms
RSA 2048 位，验证一次签名非对称每次 0.01 ms

在写这篇笔记的电脑上跑 openssl speed 得到的，对称加密取的是 16 KB 一块的成绩。换一台机器绝对值会变。

RSA 签一次名要 0.34 毫秒，同样的时间 AES 能加密 3.5 MB。一次握手里这类慢运算只做几次，可以接受；要是每一段数据都这么算，就什么都传不动了。

所以握手的分工是：用慢的那一类商量出一把对称密钥、证明服务器的身份，之后所有数据都交给快的那一类。握手结束，非对称算法就不再出场。

03证书和信任链

密钥交换有一个漏洞：它保证除了和你商量的那一方，没有别人知道密钥，但不保证那一方是谁。路上的人可以冒充服务器和你商量一把，再冒充你和真服务器商量一把，两头的内容他都看得到。这叫中间人。证书解决的就是"对面是谁"。

证书是一份文件，写着"这把公钥属于这些域名"，再由一家证书颁发机构（CA）用自己的私钥签名担保。握手时服务器发来的那一张是这样的：

可用域名（SAN）*.github.io、github.io、*.github.com、github.com、*.githubusercontent.com、githubusercontent.com真正用来比对域名的字段
签发者（Issuer）Let's Encrypt 的 YR1谁签的名
有效期2026-09-30 23:44:46 到 2026-12-29 23:44:45（UTC）90 天。查看这天还剩 39 天
公钥RSA，2048 位握手时服务器要用配套的私钥当场签名
签名算法sha256WithRSAEncryption签发者先算 SHA-256，再用自己的 RSA 私钥签
用途数字签名、密钥加密；只能当 TLS 服务器的身份不能拿去签别的证书（CA:FALSE）

curl 核对域名时打印的是这一行：

subjectAltName: host "mythlin19920302.github.io" matched cert's "*.github.io"
  • 通配符 * 只顶一级。拿 a.b.github.io 去比这张证书，实测报 hostname mismatch。
  • 这张证书不是这个知识库专有的。所有 用户名.github.io 的站点共用它，私钥在 GitHub 的服务器上。
  • 有效期只有 90 天，靠程序自动续。期限短，私钥万一泄露，能被冒用的时间也短。

信任链：一张担保一张

客户端不认识 YR1，凭什么信它签的东西？因为 YR1 自己也有一张证书，是上一级签的。这样一级一级往上，直到一张客户端本来就存着的证书为止。服务器这次一共发来三张：

  • 表里最后一行是根证书，自己给自己签名，可信不可信全看它在不在本机的信任列表里。这个列表随系统或浏览器装进来，有一百多张（这次用的 OpenSSL 根证书包里是 187 张）。
  • 中间那两张叫中间证书。根证书的私钥平时离线锁着，日常签发交给中间证书。中间证书出了事可以单独作废，不用去换每台设备里的根。
  • Root YR 名字里有 Root，这里却是被别人签的。在这台电脑的系统根证书和 OpenSSL 的根证书包里都找不到它，说明它还没有普及到各个系统里。所以由已经普及的老根 ISRG Root X1 给它签了一张，借老根的信任。这叫交叉签名。

报错是把这三张证书存下来，用 openssl verify 分别换一个域名、把时间拨到 2027-01-01 和 2026-01-01、去掉中间证书得到的。时间拨到 2026-01-01 时，先出问题的是 Root YR 那张：它 5 月 13 日才生效。

证书是公开的，谁都能抄一份发出去。光出示证书不算数，服务器还要当场用配套的私钥签一次名，这一步是握手里的 CertificateVerify，见第 05 节。

吊销和透明日志

证书没到期但私钥泄露了，CA 要能提前作废它：定期公布一份作废名单（CRL），或者让客户端拿着证书来问（OCSP）。这张证书里只写了 CRL 的地址，握手时服务器也没有附带 OCSP 的答复（-status 实测）。实际中很多客户端不在握手时联网去查，因为要多一次请求，查不到时又不敢直接拒绝。有效期缩到 90 天、到期自动作废，是更实在的兜底。

证书里还嵌着 2 条 SCT，是公开的证书透明日志开的收据：这张证书登记在案。域名的主人可以在日志里发现有没有人冒领了自己域名的证书。

04握手：一个来回

TCP 的三次握手做完，连接通了，TLS 的握手就在这条连接上开始。这次一共 7 条消息，客户端发 2 条，服务器发 5 条：

服务器   127 + 6 + 41 + 4,175 + 286 + 58 = 4,693
客户端   340 + 6 + 58                    =   404

两个 6 是那两条兼容记录（ChangeCipherSpec），明文，没有内容。合计和 s_client 最后报的 SSL handshake has read 4693 bytes and written 404 bytes 一致。

服务器那一批里，Certificate 一条就占 4,175 字节，是全部的 89%，里面是三张证书合计 4,130 字节。握手有多大，基本就看证书链有多大。

4,693 字节按每段 1,448 字节算是 4 段。总览里说过，发送方起步可以一口气发 10 段，约 14 KB，所以这一批不用等确认，一轮发完。证书链要是配得太长，超过这个数，握手就要多等一个来回。起步窗口的来历见 拥塞控制。

为什么一个来回就够

老版本的做法是先问再答：客户端先报自己会哪些算法，等服务器挑好了，再发密钥交换用的数据，所以要两个来回。TLS 1.3 改成先猜：客户端在第一条消息里就附上自己那一半密钥，赌服务器支持这种算法。服务器回话时带上另一半，从这一刻起两边都能算出密钥，所以同一批里 ServerHello 后面的消息已经是加密的。

客户端收到服务器的 Finished，验证通过后发出自己的 Finished，HTTP 请求紧跟在后面一起发，不用再等服务器回话。从发出 ClientHello 到发出 HTTP 请求，中间只等了一次。

对上耗时：TCP 握手实测 10 毫秒左右，正好是到服务器的一个来回。TLS 握手 15 毫秒，是一个来回，加上两边算密钥、签名、验证证书链的时间。

猜错了多一个来回

把客户端设成优先用 P-521、其次 X25519（-groups P-521:X25519），它在第一条消息里附的就是 P-521 的那一半。这台服务器不支持 P-521，回了一条 93 字节的 HelloRetryRequest，意思是换 X25519 重来。客户端重发 ClientHello，握手变成两个来回。主流客户端默认附的都是 X25519，平时碰不到这种情况。

ServerHello：127 字节，明文

服务器的回答很短：选定的版本（TLS 1.3）、它的 32 字节随机数、选定的密码套件 TLS_AES_128_GCM_SHA256，以及它那一半密钥，也是 32 字节的 X25519 公钥。两边到这里都能算出同一把密钥，后面的消息全部加密。

加密的那一批

消息消息本身内容作用
EncryptedExtensions19确认收到了 SNI；ALPN 选了 h2和密钥无关的协商结果，放在加密的部分里
Certificate4,153三张证书：1,355 + 1,247 + 1,528出示公钥是谁的

每条消息加密后装进一条记录，多出 22 字节：5 字节记录头、1 字节类型、16 字节标签。所以 36 字节的 Finished 在线上是 58 字节。

  • CertificateVerify 签的是到这一步为止全部握手消息的哈希。里面有两边的随机数和各自那一半密钥，所以这个签名只对这一次握手有效，抄不走。中间人要是把密钥的某一半换成自己的，两边看到的握手消息就不一样，签名验不过。密钥交换和身份就这样绑在了一起。
  • 签名 256 字节，因为证书里的 RSA 公钥是 2048 位。
  • Finished 用握手密钥对全部握手消息算一个校验值。路上有人改过 ClientHello，比如删掉强的密码套件逼两边用弱的，两边算出的值就不同，握手失败。

客户端的 Finished：58 字节

客户端收到这一批后要做三件事：按第 03 节查证书链，用证书里的公钥验 CertificateVerify 的签名，核对服务器的 Finished。都通过了，才发出自己的 Finished，握手完成。

这次握手只有服务器证明了身份，客户端没有出示证书。服务器不知道对面是谁，这件事留给上层去做：登录、Cookie、令牌。

06密钥交换：各出一半

两边要在所有人都看得见的线路上，商量出一个只有自己知道的数。这次用的办法叫 X25519，过程是：

  • 两边各自随机生成一个私钥，32 字节，不发给任何人。
  • 各自从私钥算出一个公钥，也是 32 字节，放在 key_share 里发给对方。
  • 客户端用自己的私钥和服务器的公钥算一次，服务器用自己的私钥和客户端的公钥算一次，结果是同一个 32 字节的数。

用两对临时生成的密钥在本机走一遍：

76b0f846 06350420 … eeb58066    甲的公钥
c0b358f9 fcc7dea4 … 4b801610    乙的公钥

a7612f0e 222d8d6a … 4df87223    甲的私钥和乙的公钥算出来的
a7612f0e 222d8d6a … 4df87223    乙的私钥和甲的公钥算出来的

openssl genpkey -algorithm X25519 生成密钥，openssl pkeyutl -derive 计算，两个结果逐字节相同。

数学上，公钥是"私钥 × 一个公开的起点"，这里的乘法是椭圆曲线上的一种运算。它满足 a ×（b × 起点）= b ×（a × 起点），所以两边算出同一个结果。从私钥算公钥很快，从公钥倒推私钥在计算上做不到，路上的人拿着两个公钥也没有办法。

这类办法统称 (EC)DHE：DH 是两位发明人的姓，EC 表示用椭圆曲线，最后的 E 表示临时（ephemeral），每次握手都新生成一对，用完就扔。

从这个数到密钥

共享的数不直接当密钥用。两边把它和到目前为止全部握手消息的哈希一起送进一个密钥派生函数，先得到一组握手密钥，加密 ServerHello 之后的握手消息；握手完成后再派生一组应用密钥，加密 HTTP。每组里两个方向各一把，这次的套件下每把 16 字节。握手消息被人动过一个字节，两边的哈希就不同，派生出的密钥对不上，握手当场失败。

前向保密

私钥用完就扔，带来一个重要的性质：有人把今天的流量全部录下来，日后又拿到了服务器证书的私钥，也解不开这些录像。证书的私钥只用来签名，没有参与过密钥的计算，而算密钥的那两个私钥早就不存在了。这叫前向保密。老式的 RSA 密钥交换没有这个性质，见第 11 节。

这台服务器接受哪些

让客户端每次只提供一种，挨个试：X25519、P-256、P-384（另外两条椭圆曲线）和 X25519MLKEM768 能握手成功；P-521、X448、ffdhe2048 被服务器用一条警报拒绝。

新的默认：X25519MLKEM768

不加限制时，OpenSSL 3.6.1 和这台服务器协商出的其实是最后那一种。它把两种算法叠在一起用：一半还是 X25519，另一半是 ML-KEM-768，一种设计上能抵抗量子计算机的新算法。两边的结果拼在一起派生密钥，只要其中一种没被攻破就安全。防的是有人现在把流量录下来，等将来有了量子计算机再解。代价是握手变大：

ClientHello 在线上340 字节1,574 字节
服务器那一批4,693 字节5,781 字节

1,574 字节超过了一段能装的 1,448 字节，ClientHello 自己就要分两段发（OpenSSL 还顺带附了一份 32 字节的纯 X25519 备用，也算在里面）。本文其余的数字都取自只用 X25519 的那次握手：它小，好拆，流程完全一样。手机上的 App 用哪一种，取决于系统里 TLS 库的版本。

07密码套件和 ALPN

握手里有两处是同一个模式：客户端报一个清单，服务器从里面挑一个。

读懂密码套件的名字

密码套件说的是握手之后用哪种对称加密。这次选中的是 TLS_AES_128_GCM_SHA256：

TLS协议
AES_128对称加密算法 AES
密钥 128 位
GCM工作方式：加密的同时
算出校验标签
SHA256握手里用的哈希

TLS_CHACHA20_POLY1305_SHA256 同理：ChaCha20 是加密算法，Poly1305 负责算校验标签。ChaCha20 不依赖专门的 CPU 指令，在没有 AES 硬件加速的设备上比 AES 快；有硬件加速时反过来，第 02 节那台电脑上 AES 快了将近 5 倍。

TLS 1.3 的套件名字里没有密钥交换和签名算法，那两样各自单独商量。TLS 1.2 的名字把四样都写上，例如 TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256：密钥交换 ECDHE、签名 RSA、加密 AES-128-GCM、哈希 SHA-256。OpenSSL 把同一个套件写成 ECDHE-RSA-AES128-GCM-SHA256。

选哪个取决于客户端报了什么。同一台服务器，换几种客户端配置：

客户端它报的顺序（TLS 1.3 的部分）服务器选的
OpenSSL 3.6.1，默认AES_256_GCM、CHACHA20、AES_128_GCMTLS_AES_128_GCM_SHA256
OpenSSL，把 CHACHA20 排到最前CHACHA20、AES_256_GCM、AES_128_GCMTLS_CHACHA20_POLY1305_SHA256
OpenSSL，不报 AES_128_GCMAES_256_GCM、CHACHA20TLS_AES_256_GCM_SHA384
系统自带的 curl 8.7.1（LibreSSL 3.3.6）默认TLS_CHACHA20_POLY1305_SHA256

从这几次看，服务器有自己的偏好，不是简单地取客户端的第一个；但客户端把 ChaCha20 排在最前时它会照办。所以用 curl 或 openssl 看到的套件，不等于你的 App 协商出的套件。OkHttp 里可以直接问：response.handshake?.cipherSuite 和 tlsVersion。

ALPN：HTTP/2 是怎么选上的

同一个 443 端口上，握手完既可以说 HTTP/1.1，也可以说 HTTP/2。ALPN（应用层协议协商）让这件事在握手里顺便定下来：客户端在 ClientHello 里列出自己会的，服务器在 EncryptedExtensions 里回一个。握手一结束两边就知道该说哪种，不用再多一个来回。

客户端报服务器的回答
h2、http/1.1h2
只有 http/1.1http/1.1
不带 ALPN不回答，握手照常完成，之后按 HTTP/1.1 应答
只有 h3警报 no_application_protocol，握手失败

h2 就是 HTTP/2。h3 是 HTTP/3，它跑在 UDP 上的 QUIC 里，在一条 TCP 连接上选不了；这个站点的响应里也没有宣告 HTTP/3 的 alt-svc 头。QUIC 把 TLS 1.3 的握手直接嵌进了自己的握手，细节见 HTTP/2 与 HTTP/3。

08握手之后：记录层

握手之后，上层交下来的字节被切成一条条记录（record），每条单独加密。装着证书的那条记录，开头 5 个字节是：

17 03 03 10 4a   …
17类型 23：应用数据。加密的记录外面一律这么写
03 03版本，固定写成 TLS 1.2
10 4a后面还有 4,170 字节
…4,154 字节密文，16 字节标签
  • 头 5 个字节是明文，路上的人看得到每条记录多长。
  • 真正的类型藏在密文里。明文末尾多带 1 个字节，写着这条记录其实是握手消息、应用数据还是警报。所以上面这条明明装的是证书，外面写的却是"应用数据"。
  • 16 字节的标签管完整。它由密钥、记录头和密文一起算出来。路上改了任何一位，接收方验不过，直接断开连接，不会重试。TCP 的校验和只防线路上偶然出错，防不了有人故意改，标签防的是后者。
  • 每条记录有一个不发出来的序号，从 0 开始，两边各自数，参与加密。记录被重放、丢掉一条或者调了顺序，序号对不上，解密失败。
  • 一条记录最多装 16,384 字节（214）明文，再多就切成几条。

HTTP 是怎么装进去的

TLS 不认识 HTTP，它只看到一串字节。用 HTTP/1.1 取一次知识库首页，记录是这样的：

方向内容记录数每条的明文每条在线上
客户端 → 服务器请求17698
服务器 → 客户端响应头1686708
页面151,3781,400
页面的最后一截1495517
关闭通知1224

s_client -trace 实测，单位是字节。这次请求没有要压缩，页面是 21,165 字节原文。

  • 每条记录的开销是 22 字节。响应一共 21,851 字节，装成 17 条记录后是 22,225 字节，多了 1.7%。
  • 服务器没有用满 16 KB，每条只装 1,378 字节，加上开销正好 1,400 字节，放得进一个 TCP 段。好处是客户端每收到一段就能解密一条，不用攒齐一大条才能开始。
  • 记录的边界和 HTTP 的边界无关。响应头恰好单独一条是服务器的写法，协议不保证。用 HTTP/2 时装在里面的是 HTTP/2 的帧，见 总览的请求一步。
  • 关连接之前先发一条关闭通知（close_notify），也是加密的。收到它才算正常结束；没收到连接就断了，可能是有人中途截断了数据。

再往下，这些记录交给 TCP 切成段，就回到了 总览的传输一步。

10会话恢复和 0-RTT

握手完成后，服务器还会发来一条 NewSessionTicket，线上 215 字节，里面是一张 176 字节的票据，有效期 86,400 秒，也就是一天。客户端把票据和这次会话派生出的一个密钥一起存下来。下次连同一台服务器时，把票据放进 ClientHello，服务器认出来，就不用再出示证书：

完整握手用票据恢复
客户端发出404 字节627 字节
服务器发回4,693 字节238 字节
服务器的消息ServerHello、EncryptedExtensions、Certificate、CertificateVerify、FinishedServerHello、EncryptedExtensions、Finished
发请求前等几个来回11

先用 -sess_out 把会话存成文件，再用 -sess_in 带着它重连，s_client 报 Reused, TLSv1.3。

来回数没有变，省的是 4 KB 多的证书，以及服务器的一次签名和客户端验证证书链的计算。恢复时两边仍然各出一半 X25519 密钥重新算了一遍（两条 Hello 里都还带着 key_share），所以前向保密还在。

比恢复更省的是根本不新建连接。同一个站点的后续请求复用已有的连接，一次握手都不用做。App 里全局共用一个 OkHttpClient，它的连接池才起作用。

0-RTT：连一个来回都不等

TLS 1.3 允许带着票据的客户端更进一步：用票据对应的密钥把 HTTP 请求加密，和 ClientHello 一起发出去，一个来回都不等。它有两个代价：

  • 可以被重放。这份数据的加密不依赖服务器这一次给出的任何新东西。路上的人看不懂它，但可以原样录下来再发一遍，服务器单靠密码学分不出这是第二遍。所以它只能用于重复执行也没有后果的请求，比如取一个静态页面，不能用于下单、转账这一类。
  • 这部分数据没有前向保密。它只靠票据对应的密钥保护。
这个站点不收 0-RTT 数据。s_client 显示 Max Early Data: 0：愿意收多少提前数据要由服务器在票据里声明，这里声明的是 0。

RSA 密钥交换为什么被去掉

TLS 1.2 还有一种更老的密钥交换：客户端自己生成一个随机数，用证书里的 RSA 公钥加密后发给服务器，服务器用私钥解开，两边拿这个数派生密钥。它的问题是所有会话的安全都押在证书的那一把私钥上。有人把流量录下来，日后拿到私钥，过去的每一次会话都能解开。TLS 1.3 把它删掉了，只留下每次握手都换新密钥的办法。

协议删了，不等于服务器不再接受。实测这台服务器在 TLS 1.2 下仍然接受 RSA 密钥交换（只报 AES128-GCM-SHA256 这一个套件，握手成功），只是正常的客户端都把 ECDHE 排在前面，轮不到它。更老的版本则确实关了：TLS 1.1 和 1.0 被服务器用 protocol version 警报拒绝。

12抓包和证书锁定

Charles、mitmproxy 这类工具能看到 HTTPS 的明文，靠的就是第 03 节说的中间人，只不过是你自己请来的：

① App 发起握手
  1. 手机的代理设成电脑
  2. ClientHello 到了抓包工具手里
② 工具现做一张证书
  1. 域名照着 SNI 填
  2. 用工具自己的根证书签名
③ App 验证这张证书
  1. 域名对，时间对
  2. 签名链接不接得上，看工具的根在不在信任列表里
④ 工具另连真服务器
  1. 两条 TLS 连接
  2. 中间那一段是明文

所以抓包前要把工具的根证书装进手机。没有装，第 ③ 步过不去，这正是 TLS 该有的表现：不经设备主人同意，谁也当不了中间人。

Android 7 之后多一道门

从 Android 7.0（API 24）起，面向 API 24 及以上的 App 默认只信任系统自带的根证书，用户自己装的不算。在系统设置里装了抓包工具的证书，浏览器可能认，你的 App 不认。自己的 App 要抓包，用网络安全配置在调试包里放开：

<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <debug-overrides>                       <!-- 只在 debuggable 的包里生效 -->
        <trust-anchors>
            <certificates src="user" />     <!-- 信任用户安装的证书 -->
        </trust-anchors>
    </debug-overrides>
</network-security-config>

<!-- AndroidManifest.xml -->
<application android:networkSecurityConfig="@xml/network_security_config" …>

只想看自己 App 的请求，不一定要抓包。OkHttp 的日志拦截器、Android Studio 的 Network Inspector 工作在 App 内部、TLS 的上面，看到的本来就是明文。要量握手花了多久，用 OkHttp 的 EventListener，secureConnectStart 和 secureConnectEnd 之间就是 TLS 握手。

证书锁定

系统信任的根有一百多张，任何一家 CA 出错或被迫签出一张你域名的证书，默认的检查都会放行。证书锁定（pinning）是让 App 自己再加一条：链上必须出现我指定的公钥。OkHttp 的写法：

val client = OkHttpClient.Builder()
    .certificatePinner(
        CertificatePinner.Builder()
            .add("example.com", "sha256/主用公钥的哈希")
            .add("example.com", "sha256/备用公钥的哈希")
            .build()
    ).build()

锁定的值是证书里公钥部分的 SHA-256，再做 Base64。对这个站点的证书链算出来是：

*.github.io    sha256/lNuax9RNol8Xx1GETur9frjXt+himsZHCLKOginvFyw=
YR1            sha256/LoMHBotttiDko50Gi13uXW71eIy7LAttI+rYT8wXF4w=
Root YR        sha256/fk6IOKit1ild5647BH06ujSIq5XbCgqlbYl6ANhhi88=

openssl x509 -pubkey -noout | openssl pkey -pubin -outform DER | openssl dgst -sha256 -binary | base64

  • 锁的是公钥，不是整张证书。证书续期时只要公钥不换，值就不变。
  • 至少锁两个值。只锁一个，对方一换密钥，所有已经装出去的 App 都连不上，只能等用户升级。网络安全配置里的 <pin-set expiration="…"> 可以给锁定设一个过期日，到期自动退回普通检查。
  • 不要锁别人的证书。这个站点的证书归 GitHub 管，什么时候换、换成哪家签的，都不由你定。链上那张 YR1 是 2025 年 9 月才生效的，签发方的层级说换就换。
  • 做了锁定的 App，装了根证书也抓不了包，因为抓包工具现做的证书里不是那把公钥。

联调时写的"信任所有证书"带上了线自定义的 X509TrustManager 什么都不查，等于没有身份这一条，任何中间人都能冒充调试用的放宽只写在 debug-overrides 里，不写进代码
用 IP 直连后报域名不匹配证书里写的是域名；SNI 也没有带对，服务器可能出示别的证书连接用 IP，SNI 和域名校验仍然用原来的域名
每个请求都比预期多几十毫秒每次都新建连接，TCP 和 TLS 各握一次全局共用一个 OkHttpClient，让连接复用

握手的消息、字节数、证书字段和各种协商结果，是 2026-11-20 用 OpenSSL 3.6.1 连 mythlin19920302.github.io:443 得到的：主要是 openssl s_client -connect … -servername … -alpn h2,http/1.1 -groups X25519 -trace，另外换用 -msg、-tls1_2、-ciphersuites、-sess_out 和 -sess_in、-status，以及不加 -groups 的默认配置。证书用 openssl x509 -text 解析，四项检查的报错来自对存下来的证书链跑 openssl verify。耗时是 curl -w 两种版本各 20 次的中位数（curl 8.7.1，TLS 库是 LibreSSL 3.3.6）。加密速度来自 openssl speed。消息的含义、记录层的格式和 0-RTT 的重放问题依据 RFC 8446。Android 一节依据平台文档和 OkHttp 的行为，没有在真机上实测。
