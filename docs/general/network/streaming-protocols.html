流媒体协议：HLS、RTMP、WebRTC 各管什么

点播、直播、视频通话用的不是同一套协议。它们的差别主要在一件事上：数据是切成文件等播放器来取，还是在一条连接上不停地推过去。延迟是几十秒、几秒还是几百毫秒，就是这么分出来的。这份笔记把工程里的示例视频真的切成 HLS，再把 FLV 和 RTP 的包头拆开，看每种协议在线上传的到底是什么。

示例 MP4，8 秒1 个关键帧
→
原样切成 HLS1 个分片
→
改成 2 秒一个关键帧4 个分片
→
4 个 TS 合计223,068 字节

示例是工程里的 landscape_720p.mp4（H.264 1280×720 30 fps + AAC，8 秒，240 帧）。文中的播放列表、分片大小、FLV 标签和 RTP 包头，都是用 ffmpeg 从这个文件实际生成之后读出来的。各协议的延迟范围是公开资料里常见的量级，没有实测，用到的地方会注明。

01三种需求，两种送法

把音视频通过网络送到另一台设备上播，按"能等多久"分成三种需求。这里的延迟，指从摄像头拍到，到对方屏幕上显示出来的时间差。

需求例子能接受的延迟数据丢了常用协议
点播电影、短视频，内容早就存好了谈不上延迟，只看多久能开始播、会不会卡等重发，一个字节都不能少单个 MP4、HLS、DASH
直播赛事、带货、游戏直播几秒到几十秒等重发，宁可晚一点主播到服务器用 RTMP；观众用 HTTP-FLV、HLS、DASH
实时通话视频会议、连麦、云游戏单程 0.4 秒以内，0.15 秒以内最好不等，跳过去WebRTC

通话的两个数出自国际电信联盟的 G.114 建议：单程延迟在 150 毫秒以内，对话基本不受影响；超过 400 毫秒，两个人就会抢话。主播那一端把编码好的数据送上服务器叫推流，观众这一端取数据叫拉流。

下载式和推送式

协议很多，送数据的办法只有两种：

下载式推送式
怎么送服务器上放着一个个文件，播放器用 HTTP 自己去取先建一条连接，数据在这条连接上不停地流过来
服务器普通的 Web 服务器，不知道自己传的是视频专门的流媒体服务器，要一直维持着每个观众的连接
延迟至少一个文件的时长，通常是好几个没有"等文件写完"这一步，可以很低
观众多的时候文件能被缓存，一份数据发给所有人，便宜每个观众占一条长连接，贵
代表单个 MP4、HLS、DASHRTMP、HTTP-FLV、RTSP、SRT、WebRTC

"文件能被缓存"说的是 CDN（内容分发网络）：分布在各地的一批缓存服务器，观众从离自己最近的一台取文件。把观众引到哪一台，通常在域名解析那一步就定了，见 DNS。

跑在 TCP 上的那几种，数据丢了要等重发；WebRTC 不等。这个取舍的来历见 丢包：少了一段怎么办和 TCP、UDP、QUIC 怎么选。下面先讲下载式的 MP4、HLS、DASH，再讲推送式的 FLV、RTMP，最后是 WebRTC。

02起点：MP4 加范围请求

最简单的点播用不着任何流媒体协议：把 MP4 放在 Web 服务器上，播放器用 HTTP 下载，下到哪播到哪。这叫渐进式下载。它有一个前提：索引 moov 要在文件前面，否则得先去文件末尾把它取回来，见 moov 在前还是在后。

拖进度条时，播放器查索引得到目标位置的字节偏移，发一个只要文件其中一段的请求（请求那一步提过）：

GET /landscape_720p.mp4 HTTP/1.1
Range: bytes=10105-

HTTP/1.1 206 Partial Content
Accept-Ranges: bytes
Content-Range: bytes 10105-158660/158661
Content-Length: 148556

按 HTTP 规范写出的一问一答，不是抓包。数字是示例文件的真实布局：前 10,105 字节是 ftyp、moov 和 free，后面 148,556 字节是 mdat。

206 表示"给你的是一部分"，Content-Range 写明是哪一段、文件一共多大。服务器不支持范围请求时会回 200 和整个文件，播放器就没法跳转。

这种做法到今天还在用，短视频尤其多。它有两个做不到的事：

  • 只有一种码率。码率是每秒的数据量。网速比码率低就卡，网速富余也不会变清晰。
  • 做不了直播。索引要等所有帧都写完才有，而直播没有"写完"的那一刻。

HLS 和 DASH 就是冲着这两条来的：把视频切成很多小文件，每个小文件准备几种码率。

03HLS：清单加小文件

HLS（HTTP Live Streaming）是苹果 2009 年推出的，规范是 RFC 8216。它只有两样东西：

  • 分片（media segment）。几秒钟一个的小媒体文件。本文把它叫分片，免得和 TCP 的"段"混在一起。
  • 播放列表（playlist）。扩展名是 .m3u8 的文本文件，一行一条，写着分片的地址和时长。

播放列表分两级。主播放列表列出有哪几个档位，每个档位指向一份媒体播放列表；媒体播放列表列出这一档的全部分片。播放器的工作是一个循环：

① 取主播放列表
  1. GET master.m3u8
  2. 看有哪几档，按屏幕和网速挑一档
② 取这一档的列表
  1. GET 720p/index.m3u8
  2. 得到分片的地址和时长
③ 按顺序下载分片
  1. GET seg0.ts、seg1.ts…
  2. 边下边播，记下每个分片下得多快
④ 回到 ② 或 ③
  1. 直播：过一会儿重取列表，看有没有新分片
  2. 网速变了：换一档

服务器从头到尾只做一件事：按地址给文件。把示例编成 720p 和 360p 两档，ffmpeg 写出的主播放列表是这样的：

#EXTM3U
#EXT-X-VERSION:3
#EXT-X-STREAM-INF:BANDWIDTH=228607,AVERAGE-BANDWIDTH=222967,RESOLUTION=1280x720,CODECS="avc1.64001f,mp4a.40.2"
720p/index.m3u8

#EXT-X-STREAM-INF:BANDWIDTH=169200,AVERAGE-BANDWIDTH=166755,RESOLUTION=640x360,CODECS="avc1.64001e,mp4a.40.2"
360p/index.m3u8

每个 #EXT-X-STREAM-INF 描述下一行那个档位：

属性含义示例里的值怎么来的
BANDWIDTH这一档的峰值码率，单位是比特每秒。必须写约等于最大的分片 57,152 字节 × 8 ÷ 2 秒
AVERAGE-BANDWIDTH平均码率约等于 4 个分片合计 223,068 字节 × 8 ÷ 8 秒
RESOLUTION画面的宽和高1280×720
CODECS用了什么编码。播放器不用下载分片，就知道自己解不解得了avc1.64001f 是 H.264，64 是 High 档次，1f 是级别 3.1，和 SPS 里读到的一样；mp4a.40.2 是 AAC-LC

自适应码率

播放器每下完一个分片，就知道刚才的下载速度：字节数除以用时。速度比当前档位的 BANDWIDTH 高出不少，下一个分片就换高一档；速度不够，或者缓冲的内容快播完了，就换低一档。这叫自适应码率（ABR）。换不换、换到哪，全由播放器决定，服务器不参与。

换档只能发生在分片的边界上，所以有两个要求：每个分片都以关键帧开头，各档的切点对齐。关键帧是不依赖别的帧、能单独解出来的帧。示例是彩条，特别好压，360p 只比 720p 小四分之一；正常的视频相邻两档一般差一倍上下。

04动手切一次

先试最省事的办法：不重新编码，把 MP4 里的包原样装进分片（转封装），要求每 2 秒切一个。

ffmpeg -i landscape_720p.mp4 -c copy -f hls -hls_time 2 \
       -hls_playlist_type vod -hls_segment_filename 'seg%d.ts' index.m3u8

结果只切出了一个分片，194,956 字节，8 秒：

#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:8
#EXT-X-MEDIA-SEQUENCE:0
#EXT-X-PLAYLIST-TYPE:VOD
#EXTINF:8.000000,
seg0.ts
#EXT-X-ENDLIST

分片必须能单独解码，所以只能在关键帧的位置下刀。示例的 240 帧里只有第 1 帧是关键帧（见 I、P、B 和参考关系），ffmpeg 到 2 秒时想切，一直等不到下一个关键帧，等到了文件结束。-hls_time 只是"希望"，关键帧的位置才说了算。

这样的 HLS 等于没切。中途换不了档；如果是直播，第一个分片要 8 秒后才写完，观众在那之前什么都拿不到。

再来一次，这回重新编码视频，让编码器每 2 秒放一个关键帧。音频不动。

ffmpeg -i landscape_720p.mp4 -c:v libx264 -crf 26 \
       -g 60 -keyint_min 60 -sc_threshold 0 -c:a copy \
       -f hls -hls_time 2 -hls_playlist_type vod \
       -hls_segment_filename 'seg%d.ts' index.m3u8

-g 60 是最多隔 60 帧放一个关键帧，30 fps 下正好 2 秒。-sc_threshold 0 关掉"画面突变时自动加一个关键帧"，保证关键帧只落在整 2 秒上。编码器这次产出 4 个 I 帧、60 个 P 帧、176 个 B 帧，切出了 4 个分片：

#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:0
#EXT-X-PLAYLIST-TYPE:VOD
#EXTINF:2.000000,
seg0.ts
#EXTINF:2.000000,
seg1.ts
#EXTINF:2.000000,
seg2.ts
#EXTINF:2.000000,

分片字节视频帧其中关键帧音频包
seg0.ts55,27260185

帧数和包数用 ffprobe 逐个分片数出。每个分片的第一个视频包都是关键帧。

每一行是什么意思

以 #EXT 开头的行是标签，不以 # 开头的行是地址。

这一行含义
#EXTM3U必须是第一行，表明这是一份扩展的 M3U 播放列表
#EXT-X-VERSION:3用到了协议的第几版。时长写成小数，至少要第 3 版
#EXT-X-TARGETDURATION:2分片时长的上限，整数秒。每个分片的时长四舍五入后都不能超过它。播放器按它决定隔多久刷新列表、离直播点多远
#EXT-X-MEDIA-SEQUENCE:0列表里第一个分片的序号。点播一直是 0；直播每移走一个旧分片就加 1，见第 06 节
#EXT-X-PLAYLIST-TYPE:VOD这份列表不会再变。另一个取值 EVENT 表示只会在末尾追加
#EXTINF:2.000000,下一行那个分片的时长，单位是秒。逗号后面可以写标题，一般空着
seg0.ts分片的地址，相对于播放列表自己的地址
#EXT-X-ENDLIST后面不会再有新分片。没有这一行，播放器就当它是直播，会不停地回来刷新

05分片里是 TS 还是 fMP4

HLS 的分片可以用两种容器。

MPEG-TS

最早只有这一种。它来自广播电视，整个文件由 188 字节的小包组成，每个包以 0x47 开头，带 4 字节的头，头里的编号（PID）说明这个包属于哪条流。seg0.ts 是 55,272 ÷ 188 = 294 个包：3 个包是表，说明哪个 PID 是视频、哪个是音频；199 个包是视频；92 个包是音频。

每个分片都以这几张表开头，每个关键帧前面也都带着一份 SPS 和 PPS（这是起始码那种包装的做法），所以任何一个分片单独拿出来都能解。代价是开销大，seg0.ts 的 55,272 字节是这样分的：

部分字节说明
音视频包45,620ffprobe 数出的 60 个视频包和 85 个音频包
包头1,176294 个包，每包 4 字节
填充6,172没装满的包里补的无用字节
其余2,304每帧外面的一层头、时钟、三个表
容器的开销合计9,652后三行相加，占 17.5%

填充是这样来的：每一帧必须从一个新的包开始，上一帧最后那个包没装满的部分只能填上无用的字节。示例的 B 帧平均只有 166 字节，一帧连一个包都装不满，浪费就特别显眼。码率几 Mbps 的视频帧大得多，填充占的比例会小很多，但每包 4 字节的头省不掉，开销的下限是 4 ÷ 188 = 2.1%。

fMP4

2016 年起 HLS 也能用分片 MP4，结构见 fMP4：把索引切碎。编码参数不变，命令里加一个 -hls_segment_type fmp4，播放列表变成：

#EXTM3U
#EXT-X-VERSION:7
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:0
#EXT-X-PLAYLIST-TYPE:VOD
#EXT-X-MAP:URI="init.mp4"
#EXTINF:2.000000,
seg0.m4s
#EXTINF:2.000000,
seg1.m4s
#EXTINF:2.000000,
seg2.m4s
#EXTINF:2.000000,
seg3.m4s
#EXT-X-ENDLIST

多了一行 #EXT-X-MAP，它指向初始化分片 init.mp4：1,355 字节，里面是 ftyp 和一个采样表全空的 moov，装着解码器要的参数。播放器先下载它一次，后面的分片里就不再重复这些参数。规范要求用了这个标签版本号不能低于 6，ffmpeg 写的是 7。

06直播：滑动窗口和延迟

点播的列表一次写完，以 #EXT-X-ENDLIST 结尾。直播的列表没有这一行，而且一直在变：编码器每切好一个分片，就在末尾加一条，同时把最旧的一条移走。列表里始终只有最近的几个分片，这叫滑动窗口。把第 04 节的命令换成只保留 3 条、不写结尾（-hls_list_size 3 -hls_flags omit_endlist），得到的就是直播进行到第 8 秒时的列表：

#EXTM3U
#EXT-X-VERSION:3
#EXT-X-TARGETDURATION:2
#EXT-X-MEDIA-SEQUENCE:1
#EXTINF:2.000000,
seg1.ts
#EXTINF:2.000000,
seg2.ts
#EXTINF:2.000000,
seg3.ts

seg0.ts 被移出去了，#EXT-X-MEDIA-SEQUENCE 从 0 变成 1。播放器靠这个数对账：上次的列表从 0 号开始有 3 条，这次从 1 号开始有 3 条，所以只有 3 号是新的。刷新的节奏规范里也定了：列表有变化，等一个分片的时长再来；没变化，等半个 TARGETDURATION 再试。

为什么延迟是好几个分片

  • 分片要写完才能进列表。正在编码的这几秒，观众拿不到。
  • 播放器不从最新的分片开始播。规范建议起播点离列表末尾至少 3 个 TARGETDURATION，给网络波动留余量。下一个分片下载慢了，手里还有两个可以播。
  • 再加上编码、上传和 CDN 分发的时间。

所以 2 秒的分片，延迟是 6 到 8 秒起步。苹果推荐的分片时长是 6 秒，延迟就到了 20 秒上下。把分片切得很短也有代价：关键帧要跟着变密，码率上升；请求数成倍增加。

低延迟 HLS

苹果 2019 年提出的低延迟 HLS（LL-HLS）不改"取文件"这个模式，只在上面三条里抠时间：

  • 把分片再切成几百毫秒的小块（#EXT-X-PART）。小块一编完就进列表，不用等整个分片。播放器只需要落后 3 个小块。
  • 把刷新请求挂住。播放器请求列表时说明"我要等到第几个分片的第几块"，服务器先不回答，新的小块一出来立刻返回，省掉来回询问的空档。
  • 预告下一块的地址（#EXT-X-PRELOAD-HINT），播放器可以提前把请求发出去等着。

延迟能压到 2 到 5 秒（常见的说法）。代价是请求数多了几倍，苹果要求走 HTTP/2，让这些请求共用一条连接（见 HTTP/2 与 HTTP/3），服务器和 CDN 也都要专门支持。

07DASH 和 CMAF

MPEG-DASH 是 2012 年的国际标准（ISO/IEC 23009-1）。思路和 HLS 完全一样：一份清单加一堆分片，播放器自己挑档位。区别在写法：清单是 XML，叫 MPD。示例用 ffmpeg … -f dash -seg_duration 2 manifest.mpd 切出来的 MPD，删掉命名空间等几处之后是这样：

<MPD type="static" mediaPresentationDuration="PT8.0S"
     maxSegmentDuration="PT2.0S" minBufferTime="PT4.0S">
  <Period id="0" start="PT0.0S">
    <AdaptationSet id="0" contentType="video" segmentAlignment="true" …>
      <Representation id="0" mimeType="video/mp4" codecs="avc1.64001f"
                      bandwidth="119389" width="1280" height="720">
        <SegmentTemplate timescale="1000000" duration="2000000" startNumber="1"
            initialization="init-stream$RepresentationID$.m4s"
            media="chunk-stream$RepresentationID$-$Number%05d$.m4s"/>
      </Representation>
    </AdaptationSet>
    <AdaptationSet id="1" contentType="audio" segmentAlignment="true" …>
      <Representation id="1" mimeType="audio/mp4" codecs="mp4a.40.2"
                      bandwidth="64305" audioSamplingRate="44100">
        <SegmentTemplate …和上面相同… />
      </Representation>
    </AdaptationSet>
  </Period>
</MPD>
  • 四层结构。Period 是一段节目，中间插广告时会有多个；AdaptationSet 是一组可以互相替换的内容，视频一组、音频一组；Representation 是一个档位；最里面说明分片在哪。
  • 分片地址不用一个个列。SegmentTemplate 给的是模板，$Number%05d$ 换成 00001、00002… 就是每个分片的文件名。每个分片 2,000,000 ÷ 1,000,000 = 2 秒。
  • type="static" 是点播。直播是 dynamic，另外写明从哪个时刻开播、隔多久重新取一次 MPD。
  • 音频和视频各切各的。这次视频切出 4 个分片（29,340、29,128、29,882、30,223 字节），音频切出 5 个：前 4 个都在 16,500 字节上下，最后一个只有 376 字节，因为音轨比视频长 23 毫秒。

MSE（Media Source Extensions）是浏览器的一个接口：网页里的脚本可以把媒体数据一段一段喂给 <video>，各家浏览器都收的格式是 fMP4。

两套协议长期各用各的分片，同一个视频要切两遍、存两份。CMAF（2018 年的 ISO 标准）规定了一种两边都认的 fMP4 分片：只切一遍，再写一份 .m3u8 和一份 .mpd 指向同一批文件。上面 DASH 的 chunk-stream0-00001.m4s 和第 05 节 HLS 的 seg0.m4s 就是同一种结构：styp、sidx、moof、mdat。

08FLV 和 HTTP-FLV

FLV 是 Flash 时代留下的容器，结构很简单：9 字节的文件头，后面是一个接一个的标签（tag）。每个标签有 11 字节的头，记着类型、数据长度和毫秒时间戳，接着是数据，最后 4 字节再写一遍这个标签有多长。把示例转封装成 FLV（ffmpeg -i landscape_720p.mp4 -c copy -f flv sample.flv），开头是这样的：

类型数据字节时间戳数据开头内容

标签 2 和 3 叫序列头，装的就是 MP4 里 stsd 那两段初始化数据，字节和 MP4 封装格式 里读到的完全一样。解码器拿到它们才能开工。每个标签自带时间戳，不靠文件末尾的索引，所以 FLV 可以一边生成一边发，也可以从中间接上。

HTTP-FLV：一个不结束的响应

HTTP-FLV 就是把这串标签放进一个 HTTP 响应里，而这个响应不结束：

GET /live/demo.flv HTTP/1.1

HTTP/1.1 200 OK
Content-Type: video/x-flv
Transfer-Encoding: chunked

文件头 → onMetaData → 两个序列头 → 最近的一个关键帧 → 帧 → 帧 → …

示意，不是抓包。响应头里没有 Content-Length，因为服务器也不知道主播什么时候下播。

观众不管什么时候进来，服务器都先补发文件头和两个序列头，再从缓存的最近一个关键帧发起，之后主播那边来一帧就转一帧。没有分片要等，延迟通常是 2 到 3 秒（常见的说法），主要花在服务器缓存的那一小段和播放器自己的缓冲上。

它在国内的直播里特别常见，原因有四个：

  • 走的是 HTTP。用 80 或 443 端口，防火墙不拦，可以直接套 HTTPS，国内的 CDN 普遍支持。
  • 延迟比 HLS 低一个量级。
  • 服务器省事。主播用 RTMP 推上来的数据和 FLV 标签是同一种格式（见下一节），转发时不用转码，也不用切片。
  • 网页也能播。2016 年开源的 flv.js 用脚本把 FLV 转成 fMP4 交给 MSE，不再需要 Flash 插件。

它也有短处：不是正式标准，苹果的系统播放器和 Safari 不认；一条连接只有一种码率，换档要断开重连。

09RTMP，以及 RTSP 和 SRT

RTMP（Real-Time Messaging Protocol）是 Flash 和服务器之间传音视频的协议，跑在 TCP 上，默认端口 1935，地址形如 rtmp://服务器/应用名/流名。开播的过程是：

① TCP 握手
  1. 三个包，见握手
② RTMP 握手
  1. 客户端发 C0、C1
  2. 服务器回 S0、S1、S2
  3. 客户端发 C2
③ 命令
  1. connect 连哪个应用
  2. createStream
  3. publish 推流，或 play 播放
④ 数据
  1. 一条元数据
  2. 两个序列头
  3. 音视频消息，一条接一条

C0 和 S0 各 1 字节，是版本号 3。C1、S1、C2、S2 各 1536 字节，内容是时间戳和随机数，C2、S2 把对方发来的原样送回去。两边各发 3,073 字节，作用只是确认对面说的是 RTMP，没有加密，也不验证身份。

分块

一条消息可能很大，一个关键帧就有几万字节。整条发完才轮到别的消息，音频就被堵在后面。所以 RTMP 把每条消息切成块（chunk），不同消息的块可以交替着发。块的大小默认是 128 字节，推流时一般会先发一条控制消息把它调到几千字节。每块前面有块头，时间戳、长度、类型和上一块相同的就省略不写，所以一条消息的第一块通常带 12 字节的头，后面的块可以缩到 1 字节。

消息类型

9视频消息体就是 FLV 视频标签的数据，17 01 …

8、9、18 这三个号和 FLV 标签的类型号是同一套。服务器把 RTMP 转成 HTTP-FLV 时，给每条消息套上 11 字节的标签头就行了。

为什么现在只用来推流

  • 播放这一端没人接了。浏览器里播 RTMP 靠的是 Flash 插件，Flash 在 2020 年底停止支持。App 里还能播，但 1935 端口容易被防火墙拦，协议不是 HTTP，也用不上普通的 CDN 缓存。
  • 推流这一端没有这些问题。主播到服务器只有一条连接。推流软件、硬件编码器和各家直播平台又全都支持 RTMP，换掉它的成本很高。

于是最常见的直播架构是：主播用 RTMP 推到服务器，服务器转成 HTTP-FLV 和 HLS，再交给 CDN 分发。

  • RTMPS 是把 RTMP 放进 TLS 里（见 TLS 握手），一般用 443 端口。
  • Enhanced RTMP。原版规范停在 2012 年，视频标签的编码号只有 4 位，没有给 HEVC 留位置。2023 年的这份扩展改用 4 个字符的编码名（hvc1、av01），才能正式传 HEVC 和 AV1。

RTSP：摄像头用的

RTSP（Real Time Streaming Protocol）是网络摄像头和录像机用的协议，默认端口 554。它本身只是个遥控器：一串长得像 HTTP 的文本命令，DESCRIBE 问有哪些流，SETUP 商量怎么传，PLAY 开始，TEARDOWN 结束。音视频数据另外走 RTP：默认用 UDP 的另外几个端口，过不了防火墙时也可以塞进 RTSP 这条 TCP 连接里一起走。RTP 的包头见第 11 节，WebRTC 用的是同一种。局域网里延迟一般在 1 秒以内。浏览器不支持它，公网上又不好穿过 NAT，所以基本只在监控这个圈子里用。

SRT：在公网上送信号

SRT（Secure Reliable Transport）是 Haivision 公司 2017 年开源的协议，跑在 UDP 上，用来把现场的信号经公网送回演播室或者云端。它定一个固定的延迟窗口，默认 120 毫秒：丢了的包在窗口内重发，赶不上就放弃。延迟因此是固定的，不会像 TCP 那样丢一次包就越拖越久。它自带 AES 加密，里面装的通常是 MPEG-TS。它是 RTMP 推流的替代品之一，播放端很少直接用。

10WebRTC：怎么连上

WebRTC 是做实时音视频通话的一整套东西：浏览器里的一组 API，加上底下的一组网络协议，2021 年成为正式标准。Android 和 iOS 上有同一份实现的原生库。它和前面所有协议最大的不同是跑在 UDP 上：通话等不起重发。两台设备之间建起一条通话要过四关：

① 信令
  1. 交换各自的能力和地址
  2. 怎么传由 App 自己定
② ICE
  1. 收集所有可能的地址
  2. 两两试，找一条通的路
③ DTLS
  1. 在这条路上握手
  2. 算出密钥
④ SRTP
  1. 加密的 RTP 包
  2. 音视频开始流动

信令

两边先要互相告诉对方：我支持哪些编码、我有哪些网络地址、我的证书指纹是什么。这些写成一段叫 SDP 的文本。WebRTC 不规定这段文本怎么送到对方手里，一般是 App 通过自己的服务器用 WebSocket 或 HTTP 转交。

ICE：穿过 NAT

两台手机通常都躲在 NAT 后面，外面的包进不来，谁也没法主动连谁，原因见 转发那一步讲的换地址。ICE 的办法是把所有可能的地址都收集起来，挨个试：

候选地址怎么得到什么时候能通
本机地址网卡上的地址两边在同一个局域网里
反射地址向 STUN 服务器发一个包，它回答"我看到你的地址和端口是这个"，也就是 NAT 换过之后的公网地址多数家用路由器后面可以
中继地址向 TURN 服务器申请一个公网地址，之后所有数据由它转发总能通，但流量全走服务器，多绕一段路

STUN 只在开头问一次，很便宜；TURN 要转发全部音视频，很贵。ICE 按本机、反射、中继的优先顺序把两边的地址两两配对，互相发探测包，用第一条通的。两边各自先往外发一个包，自己的路由器记下这一笔，对方的包就进得来了，这就是打洞。

DTLS 和 SRTP：强制加密

路通了之后，先在这条 UDP 路上做一次 DTLS 握手。DTLS 是 TLS 的 UDP 版本（见 TLS 握手）。证书是每次通话临时生成的，对方拿信令里收到的指纹核对。握手算出的密钥交给 SRTP，此后每个 RTP 包的内容都是加密的。WebRTC 里加密没有关掉的选项。

编码

标准要求所有实现都支持的编码，音频是 Opus 和 G.711，视频是 VP8 和 H.264。Opus 是专为通话设计的音频编码，一般 20 毫秒一个包。VP8 是 Google 开源的视频编码，和 H.264 是同一代。为了低延迟，通话里的视频不用 B 帧，因为 B 帧要等它后面的帧先到（见 I、P、B 和参考关系）；关键帧也不定期发，对方要了才发。

多人：SFU

两个人可以直连。人多了不行：n 个人，每人要给另外 n − 1 个人各发一路。所以多人会议都经过服务器，最常见的是 SFU（选择性转发单元）：每人只往服务器发一路，服务器不解码，只把 RTP 包转给其他人。发送方通常同时发大、中、小三种分辨率，SFU 按每个接收方的网速挑一种转发。

WHIP（推流）和 WHEP（拉流）把信令统一成一次 HTTP POST：请求里放自己的 SDP，响应里拿回对方的。有了它，推流软件可以像填 RTMP 地址那样填一个 WebRTC 地址。工程里的 FFmpeg n8.1.3 源码已经带了 WHIP 的封装器。

视频丢包后的处理是两步：先用 NACK 要求重发，这只在一个来回很短时才来得及；补不回来，这一帧就解不对，后面参考它的帧跟着全错，这时发 PLI 要一个关键帧，从头来过。音频基本不重发：Opus 可以在下一个包里夹带上一个包的低码率副本，实在没有就按前面的波形猜一小段补上。

抖动缓冲

每个包在路上花的时间不一样，到达的间隔忽长忽短，这叫抖动。接收方不能来一个播一个，要先在抖动缓冲（jitter buffer）里攒一小会儿，排好顺序，再按时间戳匀速取出来。攒多久是自动调的：网络稳就缩短，抖得厉害就加长，宁可晚一点也不要断。它通常在几十到几百毫秒之间，是通话延迟里播放端最大的一块。

码率跟着网络变

TCP 自己决定发多快（见拥塞控制），UDP 没有这个机制，WebRTC 得自己做。发送方看两样东西：包与包的到达间隔是不是越拉越大，这说明路上的队列在变长，快堵了；还有丢包率。据此估出一个可用带宽，每秒几次地告诉编码器新的目标码率。码率不够时，编码器先降画质，再降帧率和分辨率。所以视频通话在网络变差时是画面先糊，声音尽量不断。

这和 HLS 的自适应码率目的相同，做法不同。HLS 在几个事先编好的档位里挑，几秒钟换一次；WebRTC 直接改编码器的参数，不到一秒就生效。

RTSPmedia3-exoplayer-rtsp先试 UDP 传 RTP，收不到再改走 TCP
RTMPmedia3-datasource-rtmp只是一个数据源：负责握手和收消息，吐出来的是 FLV 字节流，交给核心模块的 FLV 解封装
HTTP-FLVmedia3-exoplayer当成一个永远下不完的 FLV 文件来播
WebRTC不在 Media3 里见下面

加了模块之后，MediaItem.fromUri() 会按地址的扩展名（.m3u8、.mpd）选对应的实现，下载、换档、缓冲、解码都由它管，解码走系统的 MediaCodec。HLS 和 DASH 的直播还可以用 MediaItem.LiveConfiguration 设一个目标延迟，播放器会略微加速或减速，把自己保持在那个位置。

WebRTC 用的是 Google 开源的 libwebrtc，Android 上是 org.webrtc 这个包：PeerConnectionFactory 建连接，SurfaceViewRenderer 显示画面，采集、编解码、回声消除它全包了。Google 现在不发布官方的预编译包，要么自己从源码编，要么用社区维护的预编译包或者云厂商的 SDK。

工程里的 FFmpeg 能不能播网络流

不能。ffmpeg/configure_android.sh 的裁剪是先全关，再只开用得到的：

--disable-everything
--enable-protocol=file,fd
--enable-demuxer=mov,mp3,flac,wav,ogg,aac,matroska,concat,image2

构建目录里的 config_components.h 可以核对：54 个协议开了 2 个，366 个解封装器开了 9 个。http、tcp、tls、rtmp 这些协议都是 0，hls、flv、mpegts、dash、rtsp 这些解封装器也都是 0。这个 FFmpeg 只能读本地的文件和文件描述符，给它一个 http:// 开头的地址，avformat_open_input 会直接返回 Protocol not found。App 的清单里也没有申请 INTERNET 权限。

想让它播网络流，要补这些：

想播的要加的协议要加的解封装器还要什么
HTTP 上的 MP4http、tcp已有 movhttps 和 rtmps 要 tls 协议，而它要求先有一个 TLS 库
HLShttp、tcp，加密的流还要 cryptohls，configure 会连带选上 mpegts 等
HTTP-FLVhttp、tcpflv
RTMPrtmp，连带 tcpflv
DASHhttp、tcpdashlibxml2，用来解析 MPD
RTSPrtp、udp、tcprtsp—

最麻烦的是 TLS。FFmpeg 自己不实现它，configure 要求 OpenSSL、GnuTLS、mbedTLS 这类库里至少有一个，而 NDK 不提供这些库，得先把其中一个也交叉编译出来。现在几乎所有地址都是 https，这一步绕不开。此外还要申请网络权限，把读数据放到后台线程，自己处理超时、断线重连、换档和追赶直播进度。裁剪列表怎么改见 组件裁剪。

用 Media3 是加一行依赖的事，协议、换档、缓冲都是现成的，TLS 用系统的。合理的分工是：网络流交给 Media3；工程里自己编的 FFmpeg 继续做它现在的事，读本地文件、软解、滤镜和导出。

14常见坑

现象原因处理
点开要等一两秒才出画面播放器只能从关键帧开始解。关键帧隔 4 秒一个，平均就要等 2 秒关键帧间隔设成 1 到 2 秒；服务器缓存最近一个关键帧起的数据，新观众一进来先发这一段
直播的延迟越播越大卡了一下，恢复后从原处接着播，落下的时间再也没补回来。TCP 上的流不丢数据，只会越积越多追赶：缓冲超过阈值就稍微加速，或者直接跳到最新的关键帧。Media3 播 HLS、DASH 用 LiveConfiguration；HTTP-FLV 和 RTMP 要自己做
音画对不上，而且越偏越多推流端的音频和视频时间戳不是按同一个时钟打的；或者播放端没用流里的时间戳，自己按帧率累加一律用流里的 pts，以音频为准，见 同步
换码率时卡一下或者花一下各档的分片边界没对齐，或者分片不是以关键帧开头各档用同一个固定的关键帧间隔，关掉自动加关键帧，就是第 04 节的 -g 和 -sc_threshold 0
丢包后花屏，过一两秒自己好了UDP 上丢了一个包，这一帧解错，后面参考它的帧跟着错，直到下一个关键帧WebRTC 靠 NACK 和 PLI；RTSP 改用 TCP 传；关键帧间隔别太长
播放器报分片时长超限，或者直播频繁卡顿某个 EXTINF 比 TARGETDURATION 大。关键帧间隔不固定，或者比想要的分片时长还长，分片就被拖长了，第 04 节那个 8 秒的分片就是这么来的固定关键帧间隔，并且让分片时长是它的整数倍
直播中途画面定住、进度乱跳主播断线重推，时间戳又从头开始；或者中间插了一段编码参数不同的内容HLS 在变化的地方加 #EXT-X-DISCONTINUITY，告诉播放器时间戳和参数从这里重新算。播放端不要假设时间戳连续或者从 0 开始：ffmpeg 切出来的 TS，第一帧的时间戳就是 1.47 秒
HLS 直播播着播着报 404播放器落后太多，要的分片已经滑出窗口，被服务器删掉了服务器多留几个分片；播放器发现落在窗口外面就跳到最新
http:// 的地址在 Android 上播不了Android 9 起默认禁止明文 HTTP换成 https，或者在网络安全配置里对这个域名放行
网络地址交给工程里的 FFmpeg，报 Protocol not found裁剪时只开了 file 和 fd见第 13 节

播放列表、分片大小、MPD、FLV 标签和 RTP 包头，都是用 ffmpeg 8.0.1（带 libx264）从 music_demo 工程的 landscape_720p.mp4 实际生成的。HLS 用 -f hls -hls_time 2：先 -c copy，再 -c:v libx264 -crf 26 -g 60 -keyint_min 60 -sc_threshold 0 -c:a copy；fMP4 版加 -hls_segment_type fmp4，直播窗口版用 -hls_list_size 3 -hls_flags omit_endlist，两档的主播放列表用 -var_stream_map 和 -master_pl_name。DASH 用 -f dash -seg_duration 2，FLV 用 -c copy -f flv，RTP 用 -an -c:v copy -f rtp -packetsize 1200。帧数和包数用 ffprobe 数；TS 包、fMP4 盒子、FLV 标签和 RTP 头按各自的规范逐字节解析；编码器先吃进多少帧用 ffmpeg -debug_ts 数出。工程的裁剪情况读自 ffmpeg/configure_android.sh 和构建生成的 config_components.h（FFmpeg n8.1.3）。握手过程、报文格式和各协议的延迟范围来自公开的规范（RFC 8216、RFC 3550、RTMP 1.0 等）和常见的经验值，没有实测。
