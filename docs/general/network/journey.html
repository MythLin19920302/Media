先认识路上的设备和四种地址

后面每一步都在和这几样东西打交道。已经熟悉的可以直接跳到第 1 步。

网卡每台设备联网用的那个部件，有线和 Wi-Fi 各是一块。它有一个 MAC 地址，负责把一帧数据变成电信号或无线电发出去，再把收到的信号变回数据。

子网掩码：对方是不是邻居

拿到 IP 之后，手机先判断一件事：对方在不在同一个网里。在，直接送；不在，交给网关。

一个 IP 地址有 32 位，前一段是网络号，后一段是这个网里的主机号。子网掩码说的是从哪一位切开。255.255.255.0 就是前 24 位是网络号，也写成 /24。

绿色是网络号。手机把两个地址的绿色部分逐位比较，全部相同才算同一个网；标成橙色的是第一处不同。把掩码往左拖到 22，隔壁网段的打印机就变成邻居了。

  • 网关是这个网通往外面的出口，一般就是路由器，地址常常是网络号加 1，这里是 192.168.1.1。
  • 192.168.x.x、10.x.x.x、172.16–31.x.x 是私有地址，谁家都可以用，但出不了家门，公网上的路由器见到就丢。怎么出去见第 6 步。
  • 手机自己的 IP、掩码和网关，就是第 1 步从路由器领到的那一套。

MAC：这一步交给谁

IP 说的是最终去哪，MAC 说的是眼前这一步递给哪块网卡。

第 3 步的结论是"交给网关 192.168.1.1"。但网卡发一帧出去，帧头里要填的是对方网卡的 MAC 地址，而手机现在只知道网关的 IP。ARP（地址解析协议）就是用来问这个的：在这个网里喊一声，谁是这个 IP，把你的 MAC 告诉我。

电脑192.168.1.8
网关192.168.1.1
这一帧里写着发送方目标

最容易弄反的一点：发往服务器的包，目的 IP 写的是服务器，目的 MAC 写的却是网关。IP 地址从头到尾不变，MAC 地址每过一台路由器就换一次。

ARP 包里写了什么

ARP 不坐在 IP 上面，它直接装在以太网帧里，帧头的类型写 0x0806。内容固定 28 个字节：

加上 14 字节的帧头是 42 字节，不够以太网一帧最少 60 字节的要求，网卡会在后面补 0。完整的字节在第 5 步里可以点开看。

广播是怎么送到每台设备的

靠交换机。交换机里有一张表，记着每个 MAC 地址在哪个口上。这张表没人替它填，是它自己看出来的：

  • 学：每收到一帧，看一眼源 MAC，记下"这个 MAC 在这个口"。
  • 送：目的 MAC 在表里，只往那一个口送。不在表里，或者目的是广播地址 FF:FF:FF:FF:FF:FF，就往其余所有口各送一份。

所以 ARP 请求全网都收得到，应答却只有手机收得到：请求经过时，交换机已经记下了手机在哪个口。交换机不看 IP，也不改帧里的任何东西。广播出不了这个网，路由器不转发它，这也是 ARP 只能问到邻居的原因。

问到之后记在哪

每台设备都有一张 ARP 缓存表，一行是"某个 IP 对应哪个 MAC"。记录过一阵子会过期，几十秒到几十分钟，各系统不同，到期后下次用到再问。所以发给一个新地址的第一个包会慢一点，后面的就不用等了。

  • 对方是邻居，问的是对方本人；不是邻居，问的是网关。ARP 问的永远是"这一步交给谁"的那个 IP。
  • 没人应答，包就发不出去。这时 ping 报的是 Destination Host Unreachable：不是路上丢了，而是第一步就没迈出去。
  • 路上每台路由器都要做同样的事。它决定了下一跳是谁之后，也得用 ARP 问出下一跳的 MAC，才能装帧发出去。
  • 设备刚连进来时，会主动广播一次自己的 IP 和 MAC。这叫免费 ARP，让别人更新缓存，也用来发现有没有人和自己用了同一个 IP。
  • ARP 不验证应答是谁发的。同一个网里的设备可以冒充网关来回答，让别人把包发给它，这叫 ARP 欺骗。公共 Wi-Fi 不安全，这是原因之一，也是上面还需要 TLS 的原因。

MAC 地址本身

  • MAC 地址是网卡的编号，6 个字节，只在同一个网里有意义，出了这个网没人认识它。
  • Android 10 起，每连一个 Wi-Fi 默认用一个随机的 MAC，不是出厂烧进去的那个，免得被人靠它跟踪。

装包：一层套一层

数据每往下走一层，前面多一段头。真正发出去的，是最外面那一帧。

以太网头14 字节
IP 头20
TCP 头20–60 数据最多 1460
校验4

从橙色算起叫帧，从绿色算起叫包，从蓝色算起叫段。说的是同一份数据的不同范围。

以太网一帧最多装 1500 字节（MTU）。减去 IP 头 20、TCP 头 20，一段最多带 1460 字节的数据，这个数叫 MSS。大文件就是这样被切成一千多字节一段，一段一帧地发出去的。

看哪一帧：

  • 每层的头里都有一个"里面是什么"的号码：以太网头的类型、IP 头的协议、TCP 头的端口。收的一方就靠这三个号码一层层往上交，见第 11 步。
  • 三层各有各的校验。帧校验管整帧，IP 的校验和只管 IP 头，TCP 的校验和管 TCP 头和数据。任何一层验不过，都是直接丢掉，不通知发送方。
  • UDP 的头只有 8 字节（看 DNS 那一帧）：两个端口、长度、校验和。没有序号，没有确认，发出去就不管了。TCP 的头至少 20 字节，多出来的就是为了可靠。
  • 包比路上某一段允许的大怎么办。IP 可以把一个包拆成几片，到终点再拼起来，但又慢又容易出问题。所以 TCP 的包都标着"不许分片"：过不去时路由器把它丢掉，回一条通知，发送方改小了再发。
  • 帧还不是线上的全部。网卡发送时，前面要加 8 字节的前导码让对方对准节拍，两帧之间还要空出 12 字节的间隔。再往下就是信号本身的事了。

转发：一跳一跳地走

没有哪台设备知道完整的路线。每台路由器只决定一件事：下一步交给谁。

跟着这个包走：
手机192.168.1.23
家里的路由器网关 · NAT
运营商的路由器第 2 台
中间 3 台骨干网
机房的路由器第 6 台
服务器185.199.108.153
包头里的字段源目的

橙色底的格子是这一跳改过的。服务器回来的包 TTL 实测是 58，按出发时 64 算，中间正好隔着 6 台路由器。

路由器每一跳做的三件事

  • 查路由表。表里是一条条"去往某个网段，从哪个口出、交给谁"。拿目的 IP 去比，匹配得最长的那条说了算。
  • TTL 减 1，重算 IP 头的校验和。减到 0 就丢掉这个包，并回一条 ICMP 通知。traceroute 就是故意发 TTL 为 1、2、3… 的包，靠这些通知把沿途的路由器一台台问出来。
  • 拆掉旧帧，装一个新帧。源 MAC 换成自己的，目的 MAC 换成下一跳的。链路的种类也可能变：家里是 Wi-Fi，出门是光纤，帧的格式跟着换，里面的 IP 包不动。

家里那台多做一件：换地址（NAT）

192.168.1.23 是私有地址，出不了门。家里的路由器把源 IP 换成自己的公网地址，源端口换成一个它自己挑的号，并记一笔："40001 这个端口对应 192.168.1.23 的 51234"。服务器的回信发到公网地址的 40001，路由器查到这一笔，再换回来交给手机。全家的设备就这样共用一个公网地址。

这里假设路由器领到的就是公网地址。很多家庭领到的是 100.64 开头的地址，运营商那边还要再换一次，几百户共用一个公网地址，这叫 CGNAT。

副作用是外面的机器没法主动连进来，因为路由器的账本里没有对应的记录。视频通话、联机游戏要"打洞"，就是在想办法先让账本里出现这一笔。

路由表是谁填的

家里的路由器只有两三行，是它开机后和运营商商量出来的。运营商的路由器有几十万到上百万行，靠路由协议自动维护：相邻的路由器不停地互相通告"哪些网段从我这里走得通"，各自算出去往每个网段最好的下一跳。运营商之间用的协议叫 BGP。哪条线路断了，通告一变，表跟着变，包就自动绕路走。

出了问题谁来通知：ICMP

IP 自己不保证送达，但路由器丢包时可以回一条 ICMP 消息说明原因，比如"TTL 用完了""这个地址去不了""包太大又不许分片"。ping 用的也是 ICMP：发一个"回显请求"，对方回一个"回显应答"，量出来的就是一个来回的时间。

握手：先确认两边都通

IP 只管送，不管到没到。TCP 在发数据之前，先用三个包确认两个方向都是通的。

TCP 10TLS 15等回应 12
一个来回一个来回 + 加解密一个来回

实测的 41 毫秒花在哪。最前面 2 毫秒是域名解析，最后 2 毫秒是把页面收完。到服务器的一个来回是 10 毫秒，每一段差不多都是它的整数倍。

这 41 毫秒里来回的包

三次握手在确认什么

  • SYN：手机说"我要连你的 443 端口，我这边的字节从 x 开始编号"。
  • SYN + ACK：服务器说"收到，下一个我要 x+1；我这边从 y 开始编号"。
  • ACK：手机说"收到，下一个我要 y+1"。

三个包走完，双方都确认了"我发的对方能收到"，也交换了各自的起始序号。少一个都不行：只有两个包的话，服务器没法知道自己的回复有没有送到。握手时顺便商量好几件事，就是第 5 步那一帧里的选项：一段最多多大、窗口放大多少倍、支不支持选择确认。

一条连接由四个数确定：源 IP、源端口、目的 IP、目的端口。服务器的 443 端口上同时有成千上万条连接，靠这四个数区分谁是谁。

接着是 TLS 的握手

网址是 https，所以 TCP 连上之后还要再握一次：商量加密算法、核对服务器的证书、算出只有两边知道的密钥。这次用的是 TLS 1.3，一个来回就够。之后 HTTP 的请求和响应都是加密的，中间的路由器只看得到 IP 和端口，看不到具体的网址和页面内容。只有域名在握手时还是明文的。

连不上的两种样子

  • 对方机器在，但那个端口没有程序在听：对方的系统立刻回一个带 RST 标志的包，手机这边报 Connection refused。
  • SYN 发出去没有任何回音：对方不在、中途被防火墙丢了，或者回来的路不通。手机隔 1 秒、2 秒、4 秒重发几次 SYN，最后报 Connection timed out。

传输：编号、确认、窗口

TCP 把数据看成一串编了号的字节。对方每收到一段，就回一句"下一个我要第几号"。

首页压缩后是 7722 字节，加上响应头和加密的开销，服务器把它切成 6 段发回来：

第 1 段1–1448第 2 段1449–2896第 3 段2897–4344第 4 段4345–5792第 5 段5793–7240第 6 段7241–8406

每段 1448 字节而不是 1460，因为握手时商量了时间戳选项，每个包的 TCP 头多占 12 字节。总字节数是按页面 7722 字节加响应头 684 字节估的，没算加密多出来的那一点。

  • 序号是字节的编号，不是包的编号。第 3 段的序号是 2897，意思是"这一段的第一个字节是第 2897 个"。
  • 确认号是"下一个我要第几号"。收到前 3 段后回 4345，意思是 4345 之前的全都到齐了。所以确认是累计的，后一个确认包含了前面所有的。
  • 收到的顺序可以是乱的。每个包各走各的路，后发的可能先到。接收方按序号排好，再交给上面的程序。

三个限制发送量的数

MSS · 握手时定一段最多装多少商量的是 1460 字节，扣掉时间戳后每段实际装 1448
接收窗口 · 对方每次告诉你对方还能收多少程序处理得慢，窗口就变小，发送方跟着慢下来
拥塞窗口 · 发送方自己估网络还能扛多少没人告诉它，只能边发边试，见下面

丢包：少了一段怎么办

路上的设备丢包时不通知任何人。发现少了、再补上，全是两端的 TCP 自己的事。

选一种情况：
手机已经收齐到–
服务器收到的重复确认–
服务器的拥塞窗口–

为了看清楚，图上每段数据都回了一个确认。真实的 TCP 通常每两段回一次。

发现丢包的两种办法

  • 重复确认，快。接收方每收到一段不是自己想要的，就把"我要的还是那一号"再说一遍。发送方连着听到三次同样的话，不等超时，立刻把那一段补发。一般只耽误一个来回。
  • 超时，慢。如果丢的是最后一段，后面没有别的包去触发重复确认，发送方只能干等。等多久是按来回时间算出来的，Linux 上最少 200 毫秒，连接刚建立时是 1 秒。对一条来回只要 10 毫秒的线路，这相当于停了二十个来回。新一些的系统会在超时之前先试探着重发最后一段，能救回一部分这种情况。

选择确认（SACK）让重复确认带上更多信息："我要的还是 3，但 4 到 6 我已经有了"。发送方就只补第 3 段，不会把后面的也重发一遍。

丢包之后发得更慢

TCP 把丢包当成"路上堵了"的信号。靠重复确认发现的，拥塞窗口降到原来的七成左右；靠超时发现的，直接降回 1 段，从头慢启动。所以丢包的代价不只是补发那一段，后面一段时间的速度都受影响。Wi-Fi 信号差时网速掉得厉害，多半是这个原因。

包是在哪丢的

  • 路由器的队列满了。进来的比送出去的快，排不下的直接丢。这是最常见的，也是 TCP 设想的那种情况。
  • 无线信号干扰。Wi-Fi 在链路层自己会重发几次，实在送不过去才丢。
  • 校验不过。线路上某一位翻了，帧校验对不上，网卡直接扔掉。

和播放器的关系：TCP 保证不丢、不乱，代价是少了一段就得停下来等，后面已经到了的数据也不能往上交。点播的视频可以等，直播和通话等不起，所以它们常常改用 UDP：晚到的包就不要了。这和播放器里"晚了太多的画面直接丢掉"是同一个取舍。

收的一方按来时相反的顺序拆头。每拆一层，查一个号码，决定交给上面的谁。

TLS、HTTP解密，解压，读出请求或者响应交给浏览器或服务程序

手机收到那 6 段也是走这四步。到最上面一层时，拿到的又是开头那个 21 KB 的页面，路上发生过的事它一概不知道：包被切成几段、走了哪条路、有没有重发过。每一层只和对面的同一层说话，下面的事交给下面。这就是分层的意义。

  • 这个 IP 后面不是一台机器。大网站的同一个地址在全世界很多机房同时存在，路由器把你送到最近的那个。所以同一个网址，不同地方的人连上的不是同一台机器。
  • 回程走的是同一套流程，方向反过来。服务器发回的包，目的地址是你家路由器的公网地址和它挑的那个端口。路由器查到第 6 步记的那一笔，把地址和端口换回手机的，再用手机的 MAC 装帧发过去。
  • 回到你家之前，运营商那边也查了一路的表。骨干网按目的地址找到你家所在城市的那台接入服务器，接入服务器按地址查到你家的拨号会话和线路标签，光纤那头的设备再按标签找到你家的光猫。每一台都是"拿一个号码，查出下一个号码"。

挥手：用完说再见

连接的两头都存着状态：序号、窗口、定时器。不用了要互相说一声，才能把这些都释放掉。

关闭连接的四个包
  • 为什么是四个包，不是三个。连接是双向的，两个方向各关各的。手机说"我没有要发的了"，服务器可能还有数据没发完，所以它先回一个确认，等自己发完了再发 FIN。两边恰好同时没话说时，中间两个包可以并成一个。
  • 最后还要再等一会儿。发出最后一个确认的一方不会马上忘掉这条连接，而是再留一小段时间。万一这个确认丢了，对方会重发 FIN，得有人认得它。
  • 不是每次都好好说再见。程序崩溃了，或者一方认为这条连接早就不存在了，会直接发一个 RST。另一边看到的就是 Connection reset。
  • 也不是每次用完都关。浏览器和 OkHttp 会把连接留着，同一个网站的下一个请求接着用，省掉两次握手。闲置久了才关。路由器里那条 NAT 记录也一样，闲置一阵子就删。
