HTTP/2 与 HTTP/3：一条连接上怎么跑很多请求

全流程的第 8 步里，手机把一个 HTTP 请求交给连接，一个来回之后页面就回来了。这份笔记把那一步放大：请求和响应在连接上长什么样，HTTP/1.1 为什么一次只能跑一个，HTTP/2 怎么把一条连接分给很多个请求，HTTP/3 又为什么连 TCP 都换掉了。

3 个请求，HTTP/1.1 排队42 ms
→
同样 3 个，HTTP/2 一起发18 ms
·
响应头写成文本684 字节
→
同一条连接上第 3 次84 字节

数字是 2026-11-20 对这个知识库的线上地址 mythlin19920302.github.io/Media/ 实测的。三个请求取的是三篇文章的 gzip 版本，共 39,698 字节，不算握手，两种协议各测 12 次取中位数。到这台服务器的一个来回约 12 毫秒。帧和头的字节数来自一个逐帧打印的小脚本，头的压缩用的是 curl 同款的 nghttp2 库。这个站点没开 HTTP/3，那一部分讲的是协议的规定。

01一次 HTTP 交换长什么样

HTTP 是一问一答的协议：客户端发一个请求，服务器回一个响应，这一来一回叫一次交换。握手做完之后，连接上跑的就是它。让 curl 用 HTTP/1.1 取知识库首页，把收发的内容打出来：

$ curl -v --http1.1 --compressed https://mythlin19920302.github.io/Media/ -o /dev/null

> GET /Media/ HTTP/1.1
> Host: mythlin19920302.github.io
> User-Agent: curl/8.7.1
> Accept: */*
> Accept-Encoding: deflate, gzip
>
< HTTP/1.1 200 OK
< Connection: keep-alive
< Content-Length: 7722
< Server: GitHub.com
< Content-Type: text/html; charset=utf-8
< Last-Modified: Fri, 20 Nov 2026 06:36:04 GMT
< ETag: W/"6affea54-52ad"
< Cache-Control: max-age=600
< Content-Encoding: gzip
< Accept-Ranges: bytes
< Age: 502
< Date: Fri, 20 Nov 2026 07:15:38 GMT
< Vary: Accept-Encoding
<
{ 7722 字节的正文 }

> 开头是发出去的，< 开头是收到的。握手的输出略去了；响应里另有 11 个头没列，多数是 CDN 给自己排查问题用的。

HTTP/1.1 的报文是纯文本，每行以回车加换行（\r\n，2 个字节）结束。请求和响应的结构相同，都是四部分：

部分请求里响应里
第一行请求行：方法、路径、版本
GET /Media/ HTTP/1.1		状态行：版本、状态码、一句说明
HTTP/1.1 200 OK
头（header）若干行 名字: 值，名字不分大小写。说明这份报文：给谁、多长、什么格式、能不能缓存
空行单独一个 \r\n，表示头到此结束
正文（body）GET 没有。POST 提交的表单、上传的文件放在这里页面、图片、音视频数据

方法说明要做什么：GET 是取，HEAD 是只要头不要正文，POST 是提交数据。播放器几乎只用 GET。上面这个请求一共 126 字节，响应的头 712 字节，正文 7,722 字节。

这些头在说什么

头这次的值意思
Hostmythlin19920302.github.io要访问哪个站。同一个 IP 上放着很多站点，服务器靠它区分。HTTP/1.1 的请求里唯一必须带的头
Accept-Encodingdeflate, gzip客户端说：这几种压缩我能解
Content-Encodinggzip服务器说：正文用 gzip 压过。21,165 字节的页面压成了 7,722 字节
Content-Typetext/html; charset=utf-8正文是什么。客户端按它决定怎么处理，不看网址的扩展名
Content-Length7722正文多少字节（压缩后的）。连接不关，接收方靠它知道这个响应到哪结束
Connectionkeep-alive发完不关连接，下一个请求接着用，省掉重新握手
Cache-Controlmax-age=600600 秒内可以直接用存下来的那份，不用再问
ETag
Last-Modified		W/"6affea54-52ad"
06:36:04 GMT		这份内容的版本标记和修改时间。客户端以后拿它们来问"变了没有"，见下一节
Accept-Rangesbytes支持只取其中一段字节，见第 03 节
Age502这份响应已经在 CDN 的缓存里放了 502 秒
VaryAccept-Encoding告诉缓存：要压缩的和不要压缩的是两份，分开存
  • 压缩是商量出来的。去掉 --compressed，curl 不发 Accept-Encoding，服务器回的就是没压缩的那份：Content-Length: 21165，没有 Content-Encoding。
  • 这台服务器的 ETag 是拼出来的。6affea54 是十六进制的修改时间，换算过来正是 Last-Modified 那一秒；52ad 是十六进制的 21165，没压缩时的字节数。别的服务器有别的算法，客户端只把它当一个字符串来比。前面的 W/ 表示弱校验：内容等价，不保证逐字节相同。压缩过的那份带 W/，没压缩的不带。
  • 事先不知道长度时不写 Content-Length。边生成边发的响应改用分块传输（Transfer-Encoding: chunked）：每块前面写这一块的长度，长度为 0 表示结束。

02状态码、缓存和条件请求

状态行里的三位数，第一位是大类。下面右边一列都是在这个站点上实际请求到的：

大类意思实测到的
2xx成功200 OK；206 Partial Content，按范围取时
3xx去别处拿，或者用你手里那份301：网址写成 /Media 少了末尾的斜杠，或者用了 http://，响应里的 Location 头给出正确的地址；304 Not Modified
4xx请求有问题，原样重试没有用404：路径不存在；405：对静态站点发 POST；416：要的范围超出了文件大小
5xx服务器这边出了问题，过一会儿重试可能就好没遇到。常见的是 500、502、503
1xx还没完，先通知一声没遇到

缓存：600 秒内不用问

Cache-Control: max-age=600 的意思是这份响应 600 秒内有效。浏览器把它存下来，有效期内再要同一个网址，直接用存的那份，一个包都不发。中间的 CDN 也按这个数缓存，Age: 502 说明 CDN 手里这份是 502 秒前从源站取的，客户端只能再用 98 秒。

条件请求：变了才重发

过了有效期也不必整个重新下载。客户端带上之前记下的 ETag 去问：还是这个版本吗？

$ curl -s -D - --http1.1 -H 'If-None-Match: "6affea54-3170"' \
       https://mythlin19920302.github.io/Media/assets/kb.css -o /dev/null

HTTP/1.1 304 Not Modified
Date: Fri, 20 Nov 2026 07:16:37 GMT
Cache-Control: max-age=600
ETag: "6affea54-3170"
Age: 561
Vary: Accept-Encoding

304 没有正文。这个样式表 12,656 字节，一个字节都没传，代价只是一个来回。客户端把手里那份的有效期再续 600 秒。

  • 用修改时间问也可以。If-Modified-Since: Fri, 20 Nov 2026 06:36:04 GMT 同样得到 304。
  • 版本对不上就正常返回。把 ETag 换成一个瞎写的值，回来的是 200 和完整的 12,656 字节。

03Range：只要其中一段

请求里加一个 Range 头，可以只取文件的一部分。取样式表的前 100 个字节：

$ curl -s -D - --http1.1 -r 0-99 \
       https://mythlin19920302.github.io/Media/assets/kb.css -o part.bin

> Range: bytes=0-99                      请求里多出的一行

HTTP/1.1 206 Partial Content
Content-Length: 100
Content-Type: text/css; charset=utf-8
ETag: "6affea54-3170"
Accept-Ranges: bytes
Content-Range: bytes 0-99/12656

状态码从 200 变成了 206，Content-Range 说明给的是哪一段、整个文件多大。几种写法在这个站点上的结果：

请求头意思实测的响应
Range: bytes=0-99第 0 到第 99 字节，两头都算，共 100 字节206，bytes 0-99/12656
Range: bytes=12000-从第 12000 字节到末尾206，bytes 12000-12655/12656，656 字节
Range: bytes=-100最后 100 字节206，bytes 12556-12655/12656
Range: bytes=999999-起点超出了文件416，Content-Range: bytes */12656
Range: bytes=0-99,200-299一次要两段200 和整个文件：这台服务器不理会多段请求
Range 加 If-Range: "6affea54-3170"文件还是这个版本才给这一段，否则给整个文件版本对：206；换成别的值：200 和 12,656 字节

播放器离不开它，有四个用处：

  • 先读索引。MP4 的索引（moov）如果在文件末尾，播放器要先用 Range 把末尾取回来才能开始播，见 moov 在前还是在后。
  • 拖动进度条。播放器从索引里查出目标时间对应的字节偏移，发 Range: bytes=偏移-，从那里接着下。
  • 断了接着下。已经下了 5 MB 的文件断了，带上 If-Range 从第 5 MB 续上。文件中途被换过的话，服务器会回 200 让客户端从头来。
  • 一个文件里取分片。HLS 和 DASH 可以把所有分片放在一个文件里，清单里写每个分片的字节范围，见 流媒体协议。
范围是按传输的那一份算的。同一个请求再加上 Accept-Encoding: gzip，回来的是 Content-Range: bytes 0-99/3716：总长变成了压缩后的 3,716，拿到的 100 字节是 gzip 数据的开头（1F 8B 08…），单独解不出来。所以取媒体数据时要明确不要压缩，Media3 的 DefaultHttpDataSource 和 OkHttpDataSource 默认发的是 Accept-Encoding: identity。

04HTTP/1.1 卡在哪

HTTP/1.1 的响应上没有编号。一条连接上，客户端只能靠"先问的先答"来对应，所以同一时刻只能有一次交换在进行：上一个响应没收完，下一个请求只能等。

在一条连接上依次取三篇文章，三个响应收完的时刻是：

第 1 个   13.9 ms
第 2 个   28.1 ms
第 3 个   42.4 ms        每个请求一个来回，一个排一个

这叫队头阻塞（head-of-line blocking）：排在前面的那个慢了，后面的全被挡住。前面如果是一个 5 MB 的视频分片，后面 200 字节的接口请求也得等它传完。由此带出一串问题：

问题后果HTTP/2 的办法
一条连接一次只跑一个请求请求排队。规范里有"连着发、按顺序回"的管线化，但响应还是得排队，主流浏览器默认都不开流，第 06 节
只好多开连接浏览器对同一个主机最多开 6 条。每条都要 TCP 和 TLS 各握一次手，在这个站点上是两个来回、约 25 毫秒；每条都从慢启动开始，互相还抢带宽一条就够
头是文本，每个请求重发一遍这个站点的响应头 712 字节，回 304 时整个响应只有头。带着 Cookie 的请求头能到几 KB，而且 gzip 只压正文，不压头HPACK，第 07 节
不想要了只能关连接响应发到一半没法叫停。关掉连接，下次又要重新握手RST_STREAM，第 06 节

05HTTP/2：把文本切成帧

HTTP/2 不改请求和响应的含义，方法、状态码、头都还是那些。改的是它们在连接上的写法：不再是一行行文本，而是一个个带长度的二进制小块，叫帧（frame）。

这个"帧"是 HTTP/2 自己的单位，和全流程里以太网的那一帧不是一回事。一个 HTTP/2 帧可以被 TCP 切进好几个段，一个段里也可以装好几个小帧。

每个帧开头是固定的 9 个字节。下面是服务器发回首页正文的那一帧的头：

00 1E 2A   00   01   00 00 00 01
00 1E 2A长度，3 字节。后面的内容有 7722 字节，不含这 9 个字节
00类型，1 字节。0 是 DATA
01标志，1 字节。DATA 帧上的 0x01 是 END_STREAM：这条流我发完了
00 00 00 01流号，4 字节。最高一位保留，其余 31 位是编号，这里是 1

每一帧都写明了自己多长、属于哪条流，所以不同请求的帧可以穿插着发，接收方按流号各归各位。一帧的内容默认最多 16,384 字节，更大的正文切成多帧。

帧类型号装什么管的范围
HEADERS1请求或响应的头，压缩过的一条流
DATA0正文一条流
SETTINGS4连接的参数。对方收到后回一个带 ACK 标志的空 SETTINGS整条连接
WINDOW_UPDATE8"我又能多收这么多字节"，见第 06 节一条流，或整条连接
RST_STREAM3立刻终止这一条流，带一个错误码一条流
GOAWAY7"这条连接我要关了，编号大于 N 的流我没处理"整条连接
PING68 个字节，对方原样送回。用来测一个来回多久、探测连接还通不通整条连接
CONTINUATION9头太大、一帧放不下时接着放一条流
PRIORITY、PUSH_PROMISE2、5优先级和服务器推送。实际已经基本不用

对这台服务器发了 5 次 PING，回来用了 10.6 到 13.6 毫秒，就是一个来回的时间。

连接开头的那几帧

用不用 HTTP/2 是在 TLS 握手里顺带商量的，这个扩展叫 ALPN：客户端列出自己会的协议，服务器挑一个，不多花来回。

* ALPN: curl offers h2,http/1.1
* ALPN: server accepted h2

握手一完，客户端先发固定的 24 个字节，叫连接前言：PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n。它故意长得像一个不合法的 HTTP/1.1 请求，万一对面其实不懂 HTTP/2，会立刻报错而不是一直等下去。接着双方各发一帧 SETTINGS。取一次首页，连接上先后出现的全部内容是这些：

方向  帧               内容字节   流   标志
→     连接前言               24
→     SETTINGS               6    0
→     HEADERS               49    1   END_STREAM | END_HEADERS
←     SETTINGS              18    0
→     SETTINGS               0    0   ACK
←     WINDOW_UPDATE          4    0
←     SETTINGS               0    0   ACK
←     HEADERS              391    1   END_HEADERS
←     DATA               7,722    1   END_STREAM
  • 请求只有一帧。GET 没有正文，所以 HEADERS 帧上直接带 END_STREAM，表示客户端在这条流上没有别的要发了。END_HEADERS 表示头在这一帧里放完了。
  • 客户端没等对方的 SETTINGS 就把请求发了。所以 HTTP/2 开头这几帧不多占来回。
  • 服务器的 SETTINGS 带了三个参数，每个 6 字节：头部压缩的表最大 8,192 字节，最多同时开 100 条流，外加一个扩展参数。不认识的参数按规定直接忽略，协议靠这一条往后兼容。
  • WINDOW_UPDATE 的增量是 16,711,681。连接的接收窗口初始是 65,535，加上它正好是 16,777,216，也就是 16 MB。

06流：一条连接上的多个请求

一个请求加它的响应，在 HTTP/2 里叫一条流（stream）。每条流有一个编号，属于它的每一帧都带着这个编号。

  • 客户端发起的流用奇数：1、3、5……偶数留给服务器，0 号指整条连接。编号只增不减，用过不再用。
  • 开一条流不用握手。发一帧 HEADERS，流就开了；两边各发一个 END_STREAM，流就关了。

curl 把每条流上发了什么都打了出来，方括号里的数字是流号：

$ curl -v --http2 --compressed https://mythlin19920302.github.io/Media/ -o /dev/null

* using HTTP/2
* [HTTP/2] [1] OPENED stream for https://mythlin19920302.github.io/Media/
* [HTTP/2] [1] [:method: GET]
* [HTTP/2] [1] [:scheme: https]
* [HTTP/2] [1] [:authority: mythlin19920302.github.io]
* [HTTP/2] [1] [:path: /Media/]
* [HTTP/2] [1] [user-agent: curl/8.7.1]
* [HTTP/2] [1] [accept: */*]
* [HTTP/2] [1] [accept-encoding: deflate, gzip]
< HTTP/2 200
< server: GitHub.com
< content-type: text/html; charset=utf-8
< cache-control: max-age=600
< content-encoding: gzip
< accept-ranges: bytes
< content-length: 7722

响应头只留了几行。curl 还会照 HTTP/1.1 的样子把请求再打一遍（> GET /Media/ HTTP/2），那是给人看的，线路上没有这段文本。同一条命令后面再写两个网址，会看到 [3]、[5] 和 Re-using existing connection。

伪头：原来的第一行去哪了

HTTP/2 没有请求行和状态行。原来写在第一行里的东西，改成几个名字以冒号开头的头，叫伪头：

伪头对应 HTTP/1.1 里的这次的值
:method请求行里的方法GET
:scheme网址开头的协议名https
:authorityHost 头mythlin19920302.github.io
:path请求行里的路径/Media/
:status状态行里的状态码200

伪头必须排在普通头前面。头的名字一律小写。状态码后面那句说明（OK）取消了。Connection: keep-alive 这类只对单条连接有意义的头不许出现，上面的输出里也确实没有。

三个请求一起发

在一条连接上连着发出三个请求，把来回的帧按到达顺序列出来：

→ HEADERS        76   流 1   GET …/container/mp4-format.html
→ HEADERS        30   流 3   GET …/overview/playback.html
→ HEADERS        33   流 5   GET …/codec/aac-decoding.html
← HEADERS       386   流 5
← HEADERS       149   流 1
← HEADERS       124   流 3
← DATA       15,670   流 1
← DATA       15,670   流 3
← DATA       16,384   流 5
← DATA       16,384   流 5
← DATA        1,923   流 5   END_STREAM
← DATA       16,384   流 1
← DATA       16,384   流 3
← DATA        4,532   流 1   END_STREAM
← DATA       15,687   流 3   END_STREAM

为了让每个响应都超过一帧，这一次要的是没压缩的版本，三个页面共 119,018 字节。

  • 请求不用等。三帧 HEADERS 连着发出去，谁也不等谁的响应。
  • 响应的顺序和请求的顺序无关。最后发的 5 号最先回来。谁先准备好谁先发，慢的不挡快的。
  • 三条流的 DATA 帧是交错的，没有一帧超过 16,384 字节。接收方按流号把它们拼回三个文件。

这就是多路复用（multiplexing）。换成 gzip 版本再测耗时：HTTP/1.1 一个排一个是 42 毫秒，三个来回还多；HTTP/2 一起发，三个全部收完是 18 毫秒，一个半来回。多出来的半个来回，是因为新连接第一轮只能发 10 段、约 14 KB，三个响应加起来 39 KB，要第二轮才发得完，见拥塞控制。

取消一条流

不想要某个响应了，发一帧 RST_STREAM，服务器停掉这一条流，连接和别的流照常。用户拖动进度条时，播放器正在下的那个分片就是这样取消的。HTTP/1.1 只能关连接，下一个请求再多花两个来回握手。

每条流有自己的窗口

TCP 有接收窗口：接收方来不及处理时，让发送方慢下来。但它管的是整条连接。HTTP/2 一条连接上有很多流，如果应用暂时不读其中一条，比如播放器的缓冲满了，TCP 的窗口会把整条连接一起堵住。所以 HTTP/2 在上面又做了一层流量控制：

  • 每条流一个窗口，整条连接还有一个总的。初始都是 65,535 字节。
  • 只管 DATA 帧。发送方每发出一帧 DATA，就从这条流的窗口和连接的窗口里各扣掉相应的字节数，任何一个扣到 0 就得停。
  • 接收方用 WINDOW_UPDATE 把额度还回去。数据交给应用之后才还。

不还会怎样，可以直接测。让脚本故意不发 WINDOW_UPDATE，再要上面那三个没压缩的页面：

← DATA       16,384   流 3
← DATA       16,384   流 3
← DATA       14,973   流 3   END_STREAM
← DATA       15,670   流 1
← DATA        2,124   流 5
                             之后再没有数据，直到脚本超时

16,384 + 16,384 + 14,973 + 15,670 + 2,124 = 65,535。连接的总窗口一个字节不剩，服务器就停在那里等。先发一帧 WINDOW_UPDATE 把连接的窗口加大 1 MB，同样的请求就走完了，也就是上一小节那份记录。

窗口有两层。一条流的数据收了却不读，占住的是连接的总额度，别的流也会跟着停。这是 HTTP/2 客户端常见的一类故障，见最后一节。

07HPACK：重复的头只发一次

同一条连接上的请求，头大同小异：主机名、客户端名字、能接受的格式，每次都一样。HTTP/2 用一套专门的办法压缩头，叫 HPACK。它有三样工具：

工具做法例子
静态表规范里预先列好 61 个最常见的头，编号 1 到 61。命中了只发编号2 号是 :method: GET，7 号是 :scheme: https，8 号是 :status: 200，各用 1 个字节
动态表每条连接、每个方向各有一张。发过的头记进去，编号从 62 起，最新的排最前，以后只发编号主机名第一次发 20 字节，之后 1 个字节
哈夫曼编码头里的字符串按一张固定的码表重新编码，常见的字符用 5 位，少见的用得多25 个字符的主机名编成 18 字节

第 05 节里那个 49 字节的 HEADERS 帧，内容逐段拆开是这样的。同一个请求写成 HTTP/1.1 的文本是 117 字节。

41 64 30 D8 7A 88 25 B6 50 C3 CB BA B8 7F 53 03 2A 2F 2A 50 83 9B D9 AB
字节共写法解出来
821整个头用编号静态表 2 号：:method: GET
871整个头用编号静态表 7 号：:scheme: https
41 92 + 18 字节20名字用编号，值照写，并记进动态表名字是静态表 1 号 :authority；值是哈夫曼编码的主机名
04 85 + 5 字节7名字用编号，值照写，不进表:path: /Media/。7 个字符编成 5 字节
7A 88 + 8 字节10同第三行user-agent: curl/8.7.1

在这条连接上第三次请求同一个地址，整个头只剩 13 字节：

82 87 C1 04 85 63 41 64 30 D8 C0 BF BE

C1、C0、BF、BE 是动态表的 65、64、63、62 号，就是第一次记进去的主机名、客户端名字和两个 accept。只有路径还在照写，因为编码器认为路径每次都不同，不值得占表。

响应那一边压得更明显。同一条连接上先后取首页、样式表、再取一次首页：

写成文本第 1 个响应第 2 个（另一个文件）第 3 个（又是首页）
整个头68439116984
last-modified: Fri, 20 Nov…462411
content-type: text/html; charset=utf-8402019（值不同）1
cache-control: max-age=600281011
content-length: 772222777

单位是字节。第 3 个响应的 23 个头里，19 个各用 1 个字节；剩下的是 content-length 和三个每次都变的值。

  • 压缩是有状态的。两端的动态表必须一模一样，所以头必须按发出的顺序解。TCP 保证顺序，这一点在 HTTP/2 里不成问题，到了 HTTP/3 要另想办法。
  • 动态表跟着连接走。新开一条连接，表是空的，头又要从 391 字节发起。这是尽量复用连接的又一个理由。
  • 不直接用 gzip 压头是为了安全。把 Cookie 和攻击者能控制的内容放在一起压缩，密文的长度会泄露 Cookie 的内容。HPACK 只做整项匹配，没有这个问题。

08HTTP/2 没解决的那一层

HTTP/2 让请求之间不再互相排队，但所有流还是挤在同一条 TCP 连接里。TCP 不知道上面有流，它只负责把一串字节按顺序交给应用。丢了一个段，后面的段即使已经到了，也只能压在内核里等它重传回来，快的话一个来回，慢的话要等超时。这期间所有的流一起停。队头阻塞从 HTTP 这一层挪到了 TCP 这一层。

丢包的代价还有另一半：TCP 把丢包当成拥堵的信号，把拥塞窗口砍小。六条 HTTP/1.1 连接里丢一个段，只有那一条降速；HTTP/2 只有一条连接，一降就是全部。所以在丢包多的网络上，比如信号差的 Wi-Fi 和移动网络，HTTP/2 有可能比 HTTP/1.1 开多条连接还慢。

这个问题在 HTTP 这一层修不了，得改 TCP。而 TCP 在操作系统内核里，路上的防火墙和 NAT 还会检查它的格式，改不动。于是有了下一节的做法：换掉它。

09HTTP/3：把 TCP 换成 QUIC

HTTP/3 的请求、响应、头、状态码和前两个版本完全一样，变的是下面的传输层：不用 TCP，改用一个叫 QUIC 的新协议。QUIC 跑在 UDP 上，端口还是 443。

HTTP/2 的一摞HTTP/3 的一摞
请求和响应HTTP/2：帧、流、HPACKHTTP/3：帧、QPACK
加密TLSQUIC：流、重传、拥塞控制、流量控制，TLS 1.3 也在里面
可靠传输TCP
外壳UDP
寻址IPIP

选 UDP 当外壳，是因为路上的设备只放行 TCP 和 UDP 两种，全新的协议过不去。UDP 的头只有 8 字节，除了端口和校验什么都不管，重传、排序、拥塞控制都由 QUIC 自己在上面重做一遍。重做的时候，把 TCP 的几个老问题一起改了：

事情TCP 加 TLSQUIC
握手TCP 一个来回，TLS 1.3 再一个，之后才能发请求两件事合在一个来回里
再次连接同一个服务器TCP 那一个来回省不掉0-RTT：请求跟着第一个包一起发，不用等
流没有，只有一串字节传输层自己有流，每条流各自编号、各自排序
丢了一个包后面的全部等只有数据在这个包里的那几条流等
靠什么认一条连接两端的 IP 和端口，四个数连接 ID，写在包里
手机从 Wi-Fi 换到流量源 IP 变了，连接作废，重新握手连接 ID 没变，验证一下新路径，接着传
路上的设备能看到什么TCP 头是明文：序号、确认号、窗口包头的大部分也加密了，包括包的编号
代码在哪操作系统内核应用自己带的库
  • 握手省一个来回。全流程里量到的 TCP 握手是 10 毫秒，换成 QUIC 省掉的大约就是这一段。这个站点没开 HTTP/3，这是按一个来回推的，不是测的。来回要 100 多毫秒的移动网络上，省下的就很可观。
  • 0-RTT 有条件。第一个包里的请求可能被人截下来原样重放，所以只适合 GET 这种重复执行也无害的请求，服务器也可以拒绝。
  • 流独立不等于丢包没影响。拥塞控制还是整条连接一份，丢了包所有流的发送速度都会降。一个包里如果装了好几条流的数据，这几条都要等。
  • 连接迁移对手机最实在。出门时 Wi-Fi 断开、切到流量，TCP 上的播放器会收到一个网络错误，要重连、重新握手；QUIC 的连接可以接着用。
  • 重传的包用新编号。QUIC 的包编号只增不减，重发的数据放进一个新编号的包里，所以确认回来时不会分不清对应的是哪一次发送，来回时间量得更准。
  • 在应用里实现，改起来快。TCP 的拥塞控制算法要跟着系统升级，Android 上就是等厂商推送。QUIC 跟着应用或者网络库更新。代价是同样的流量更费 CPU。
  • UDP 可能不通。有些公司网络和防火墙会拦掉或限速 UDP 443。客户端发现 QUIC 连不上就退回 TCP 上的 HTTP/2，所以服务器总是两个一起开。

HTTP/3 自己还剩什么

  • 帧简单了。流、流量控制、取消、探活都交给了 QUIC，HTTP/3 的帧里不再有流号，也没有 WINDOW_UPDATE、RST_STREAM 和 PING。常用的只剩 HEADERS、DATA、SETTINGS、GOAWAY。
  • 流号换了规则。客户端发起的请求流编号是 0、4、8……每次加 4，低两位用来区分是谁发起的、单向还是双向。
  • 头部压缩换成 QPACK。HPACK 要求头按顺序解，而 QUIC 的流谁先到不一定。QPACK 把"往动态表里加东西"单独放到一条专用的流上，每个头块注明自己依赖表的哪个状态；编码器也可以选择只引用对方已经确认收到的表项，压缩率低一点，换来不被别的流挡住。静态表从 61 项扩到 99 项。

10怎么知道对方会 HTTP/3

网址只写了 https://，看不出版本。HTTP/2 好办，TCP 连上之后在 TLS 握手里商量。HTTP/3 走的是 UDP，客户端得在连接之前就知道对方的 UDP 443 上有没有 QUIC。有两个途径。

Alt-Svc：先用 TCP 连上，服务器在响应里说

$ curl -sI https://www.cloudflare.com/ | grep -i alt-svc
alt-svc: h3=":443"; ma=86400

$ curl -sI https://www.google.com/ | grep -i alt-svc
alt-svc: h3=":443"; ma=2592000,h3-29=":443"; ma=2592000

意思是：同一个主机的 UDP 443 端口上有 HTTP/3（h3），这条消息可以记 86,400 秒，也就是一天。Google 那条多出来的 h3-29 是给只会旧草案版本的客户端看的。客户端记下来，下一次连接就去试 QUIC。所以靠 Alt-Svc 的话，第一次访问一定不是 HTTP/3。

DNS 的 HTTPS 记录：查域名时就知道

域名解析时除了问 IP 地址，还可以问一种类型号为 65 的记录，叫 HTTPS 记录。手头这个 dig 版本较老（9.10.6），不认识这个名字，只能按类型号查，拿到的是原始字节：

$ dig +short TYPE65 www.google.com
\# 13 00010000010006026832026833
00 01优先级 1
00目标为空
就是这个域名自己
00 01参数 1
alpn
00 06参数值

"h2"

13 个字节说的是：这个域名支持 h2 和 h3。www.cloudflare.com 的这条记录有 61 字节，除了 h3、h2，还附带了几个 IP 地址当提示。浏览器查地址时顺便查它，第一次连接就能直接用 QUIC。

这个站点两样都没有

$ curl -sI https://mythlin19920302.github.io/Media/ | grep -i alt-svc
$ dig +short TYPE65 mythlin19920302.github.io

两条命令都没有输出，所以任何客户端访问这个知识库用的都是 HTTP/2。

12对播放器意味着什么

点播和大部分直播是用 HTTP 传的。HLS 和 DASH 把视频切成几秒一个的小文件，叫分片，另有一个清单列出它们的地址。播放就是不停地发 GET，见流媒体协议。所以 HTTP 的版本直接决定这些请求怎么排。

播放器在做的事HTTP/1.1HTTP/2HTTP/3
同时下视频分片和音频分片，直播时还要定时刷新清单要两三条连接，每条各握各的手、各自慢启动一条连接上的三条流。连接早就热了，新请求不用从慢启动开始
拖动进度条、切换清晰度，正在下的分片不要了关连接，下一个请求多两个来回RST_STREAM，连接留着重置那条流，连接留着
起播TCP 和 TLS 两个来回之后才发出第一个请求一个来回；连过的服务器可以不等
信号差，丢包多哪条连接丢包哪条停音频、视频、清单一起停只有丢了数据的那条流停
播到一半 Wi-Fi 换成流量连接断开，播放器报错后重试连接迁移，下载不中断
  • Range 在三个版本里一样用。它是头，不是连接层的东西。单个 MP4 文件的边下边播、拖动，靠的都是第 03 节那几种写法，HTTP/2 下服务器同样回 206。
  • 播放器有几秒到几十秒的缓冲。丢一个包停一个来回，观众看不出来。HTTP/3 帮得上忙的是起播时间、弱网下的下载速度和换网络这三件事。
  • 真正低延迟的场景不走这条路。通话和连麦用的是 UDP 上的 RTP、WebRTC，晚到的数据直接不要，理由见全流程的丢包一步。

13Android 上谁说哪个版本

用哪个版本取决于用哪个网络库。Media3（ExoPlayer）把网络库包成 DataSource，换库就是换一个工厂：

网络库能说的版本Media3 里对应的类

14常见坑

现象原因处理
换成 HTTP/2 之后，弱网用户反而更卡所有请求在一条 TCP 连接上，丢一个段全部流一起等，拥塞窗口也只有一份。原来的六条 HTTP/1.1 连接是各丢各的上 HTTP/3。上不了时，把大文件下载和小请求放到不同的主机名上，让它们走不同的连接
一条流卡住，别的流也跟着不动某个响应的正文没读完也没关，它占着连接的流量控制额度。第 06 节实测过，65,535 字节用完服务器就停响应体要么读完要么关掉。OkHttp 里忘记 close() 是常见的原因
抓包看到的全是 HTTP/1.1，线上明明是 HTTP/2 或 HTTP/3设了代理之后，客户端到代理、代理到服务器是两条连接，版本各自商量。HTTP/3 走 UDP，普通的 HTTP 代理转不了，客户端会退回 TCP抓包的结果只说明经过代理时的行为。要看真实的版本，用客户端自己的日志，或者在服务器一侧看
第一次请求总是 HTTP/2，之后才是 HTTP/3Alt-Svc 要先通过 TCP 上的一次响应才拿得到给域名加 HTTPS 记录；Cronet 用 addQuicHint
请求被拒，返回 431 或 400，或者连接直接断掉头太大，多半是 Cookie 或令牌。服务器和中间的代理各有上限，很多默认在 8 KB 上下精简头。这个站点比较宽：实测 6 万字节的头两个版本都回 200；到 7 万字节，HTTP/1.1 还是 200，HTTP/2 这边 curl 报发送失败
偶尔有请求失败，日志里有 GOAWAY服务器要重启，或者这条连接用得够久了，通知客户端不再接新的流编号比 GOAWAY 里那个数大的流没被处理，换一条连接原样重发是安全的。成熟的网络库会自己做；自己重试 POST 时要先确认它没被处理过
改了页面，刷新还是旧的max-age=600：浏览器和 CDN 在 600 秒内都不回源等过期，或者换一个网址。这个知识库的样式表链接写成 kb.css?v=5，就是为了改样式时换个号绕开缓存
视频能播，但不能拖动，或者要等很久才起播服务器不支持 Range，对带 Range 的请求回 200 和整个文件用 curl -r 0-99 检查，要看到 206 才算支持。只看 Accept-Ranges 头不够
按范围取回来的数据对不上请求带了 Accept-Encoding: gzip，范围是按压缩后的数据算的，见第 03 节取媒体数据时发 Accept-Encoding: identity
明文的 http:// 地址用不上 HTTP/2浏览器和 OkHttp 默认只在 TLS 上用 HTTP/2，版本是在 TLS 握手里商量的上 HTTPS

2026-11-20 对 https://mythlin19920302.github.io/Media/ 实测。请求和响应的文本、状态码、缓存和 Range 的行为来自 curl 8.7.1：curl -v --http1.1 --compressed、curl -v --http2 --compressed，以及 curl -s -D - 加上 -r 0-99、-H 'If-None-Match: …' 等参数。帧的顺序和长度、HPACK 的字节数、65,535 字节处的停顿、PING 的往返时间，来自一个用 Python 的 ssl 模块直接收发 HTTP/2 帧的脚本（TLS 1.2，ALPN 选 h2），头的压缩和解压调用的是系统自带的 nghttp2，和 curl 用的是同一个库。三个请求的耗时是这个脚本对两种协议各测 12 次的中位数，不含握手。Alt-Svc 用 curl -sI 查，HTTPS 记录用 dig TYPE65 查，www.cloudflare.com 的协议版本取自它的 /cdn-cgi/trace。本机的 curl 没有编译 HTTP/3，所以没有 HTTP/3 的耗时数据；QUIC 和 HTTP/3 的内容依据 RFC 9000、9114、9204，HTTP/2 依据 RFC 9113 和 7541。
