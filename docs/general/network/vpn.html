VPN：在公网上再套一层

全流程那一页里，一个请求从手机走到网站用了十二步。打开 VPN 之后还是这十二步，只是手机发出的每个包先被加密，再整个装进另一个包，寄给 VPN 服务器，由它拆开后替你送出去。这份笔记讲多出来的这一层是怎么套上去的，以及十二步里每一步因此变了什么。

地址只作示意，和全流程那一页用同一组：手机 192.168.1.23/24，网关 192.168.1.1，家里的公网地址 203.0.113.7，网站 185.199.108.153:443。VPN 这边另加四个：服务器 198.51.100.20，UDP 端口 51820，隧道里手机是 10.8.0.2，服务器是 10.8.0.1。字节数以 WireGuard 为例，按协议定义逐项相加得出。这一页没有做任何实测。

01VPN 解决什么问题

全流程里有两件事没有解决，VPN 是为它们准备的。

第一件：私有地址在公网上不通。192.168.x.x、10.x.x.x 这类地址谁家都能用，公网上的路由器见到就丢（第 3 步）。家里的路由器做了 NAT 之后，外面的机器也没法主动连进来（第 6 步）。人在外面时，办公室内网的代码仓库、家里的 NAS 都够不着：它们只有私有地址，公网上没有一条路指向它们。

第二件：本地网络看得到你的流量。连上咖啡店的 Wi-Fi，你的每个包都由那台热点转发。DNS 查询默认是明文，它看得到你查了哪些域名；IP 头和端口不加密，它看得到你连了谁；没有用 HTTPS 的内容，它能读也能改。ARP 的应答不做验证，同一个 Wi-Fi 里的另一台设备还可以冒充网关，让你的包先经过它。

用法要解决的VPN 怎么做
远程接入：人在外面，要用内网里的机器私有地址过不了公网把发往内网地址的包，装进一个发往公网地址的包里，送到内网门口的 VPN 服务器，由它拆开送进内网
不可信的本地网络：公共 Wi-Fi本地网络能看、能改流量把所有的包加密后送到一台自己信得过的 VPN 服务器，从那里再上公网
站点互联：两个办公室的内网连成一个同第一行，只是两头都是整个网段两边的路由器之间建隧道，网里的设备什么都不用装

三种用法底下是同一个机制：在公网上建一条隧道。VPN 是 Virtual Private Network（虚拟专用网）的缩写：早年企业连接两地的网络要向运营商租专线，现在在公用的互联网上用隧道"虚拟"出一条。它不会让网速变快，多数时候还慢一点（第 07、12 节）；也不等于匿名（第 10 节）。

02隧道：封装加上加密

全流程第 5 步（装包）里，数据每往下走一层，前面多一段头：数据外面是 TCP 头，再外面是 IP 头，最外面是帧头。隧道只是把这件事多做了一轮：一个已经装好的、完整的 IP 包，被当成"数据"，再装一次。

  • 内层是手机原本要发的那个包，目的 IP 是网站。
  • 外层是新套上去的包，目的 IP 是 VPN 服务器。路上的路由器只按外层转发。
不开 VPN
IP 头20TCP 头20–60数据最多 1460
开了 VPN
外层 IP 头20UDP 头8WireGuard 头16
内层 IP 头20TCP 头20–60数据最多 1380
认证标签16

画的是 IP 包，没画最外面的帧头；外层走的是 IPv4。虚线框里是加密的，只有手机和 VPN 服务器解得开；框外的部分路上每台设备都能读。

外层的每一段各有用处。外层 IP 头让路由器把包送到 198.51.100.20，里面的协议号是 17（UDP）。UDP 头的目的端口 51820 让 VPN 服务器把包交给 VPN 程序，也让家里路由器的 NAT 有端口可记。WireGuard 头的 16 字节是类型、会话编号和计数器：服务器按会话编号找到密钥，按计数器拒收重复的包。末尾 16 字节的认证标签是对密文算出的校验值，路上改过一个比特，收的一方就验不过，直接丢掉。

路上的设备只认外层：路由器按外层的目的 IP 转发，NAT 改的是外层的源地址和端口。内层的地址、端口和内容，在手机和 VPN 服务器之间谁也读不到、改不了。

封装和加密是两件事

只封装不加密也叫隧道，比如 GRE 和 IP-in-IP。它们能让私有地址过公网，但路上谁都能读。VPN 多做了两样：加密，让路上的人读不了；认证，让路上的人改不了，也冒充不了对端。密钥是两端建隧道时握手算出来的，握手同时确认了对方的身份（第 09 节）。

拿握手的第一帧算一遍

全流程里手机发出的 SYN 是一帧 74 字节：帧头 14，IP 头 20，TCP 头 40。开了 VPN 之后，里面那个 60 字节的 IP 包不直接交给网卡，先进隧道：

  60   内层 IP 包：IP 头 20 + TCP 头 40
+  4   补零到 16 的整数倍，变成 64
+ 16   WireGuard 头
+ 16   认证标签
+  8   UDP 头
+ 20   外层 IP 头
────
 124   外层 IP 包
+ 14   帧头
────
 138   发出去的一帧。不开 VPN 时是 74

多出来的 64 字节里，60 是固定开销，4 是补齐。补齐不会让包超过隧道的 MTU，所以装满的包不补，只多 60 字节。

03虚拟网卡：包怎么进隧道

App 用的是普通的 socket，不知道有 VPN 存在。它发的包能拐进隧道，靠的是一块假的网卡。

TUN 是操作系统提供的虚拟网络接口。对内核来说它和 Wi-Fi 网卡一样：有名字（常见的是 tun0），有 IP 地址，有 MTU，路由表可以把包指给它。区别是它后面没有硬件，接着的是一个程序。内核"发"给 tun0 的包，这个程序用 read() 读得到；这个程序用 write() 写进去的数据，内核当成是从 tun0 收到的包。

① 照常装包
  1. App 往 socket 里写数据
  2. 内核加 TCP 头和 IP 头：10.8.0.2 → 185.199.108.153
② 路由表指向 tun0
  1. 内核查路由表，出口是 tun0（下一节）
  2. 这个包不去 Wi-Fi 网卡
③ VPN 程序加密
  1. 从 tun0 读到一个完整的 IP 包
  2. 加密，加上 VPN 头
④ 再装一次，发出去
  1. VPN 程序用自己的 UDP socket 发给 198.51.100.20 的 51820 端口
  2. 内核加 UDP 头、外层 IP 头、帧头，交给 Wi-Fi 网卡

回来的方向反过来：Wi-Fi 网卡收到 UDP 包，内核交给 VPN 程序；它验证、解密出内层包，写进 tun0；内核把它当成刚从网卡收到的包，找到对应的 TCP 连接，交给 App。

  • 内层的源地址是隧道地址。包从哪个接口出去，内核就用哪个接口的地址当源 IP。所以内层包的源是 10.8.0.2，不是 192.168.1.23。
  • 每个包过两遍协议栈。第一遍装出内层包，第二遍装出外层包。VPN 程序如果是普通进程，每个包还要在内核和进程之间拷贝一个来回，这是用户态 VPN 比内核态慢的主要原因。Linux 上的 WireGuard 和各系统的 IPsec 把收发做在内核里，省掉了这一趟。
  • TUN 收发的是 IP 包。没有帧头，没有 MAC 地址，也就没有 ARP。另一种虚拟网卡叫 TAP，收发的是完整的以太网帧，能传 ARP 和广播，用来把两个局域网桥接成一个。Android 给 VPN App 的只有 TUN。

04路由表：哪些包进隧道

全流程第 3 步里，"对方是不是邻居"是查路由表得出的：拿目的地址一行行去比，对上的位数最多的那一行说了算。连上 Wi-Fi 时这张表只有两行：本地网段 192.168.1.0/24 直接送，其余所有（0.0.0.0/0，默认路由）交给网关 192.168.1.1。VPN 连上之后，客户端改的就是这张表，改法有两种。

全隧道：默认路由指向隧道

去往哪个网段怎么走
198.51.100.20/32（VPN 服务器本身）交给 192.168.1.1，从 Wi-Fi 网卡出去
192.168.1.0/24直接从 Wi-Fi 网卡发出去
0.0.0.0/0（其余所有）交给 tun0，进隧道

访问 185.199.108.153 只对得上最后一行，进隧道。所有不在本地网段里的流量都一样。

第一行不能少。加密好的外层包，目的地址是 198.51.100.20。没有这一行，它也只对得上默认路由，又被送回 tun0，再加密一次，再送回去，永远出不了手机。/32 是 32 位全部对上，比默认路由的 0 位长，所以去 VPN 服务器的包留在真实网卡上。有的系统不加这条路由，而是给 VPN 程序自己的那个 socket 打一个标记，带标记的包不进隧道，效果相同。Android 是后一种，见第 11 节。

192.168.1.0/24直接从 Wi-Fi 网卡发出去
0.0.0.0/0（其余所有）交给 192.168.1.1（默认网关）

访问内网的 10.20.3.5 进隧道。访问 185.199.108.153 还是走家里的路由器，和没开 VPN 时一样。

全隧道分流
进隧道的本地网段和 VPN 服务器本身以外的全部路由表里列出的网段
适合不可信的本地网络远程接入内网
本地网络还看得到只有去 VPN 服务器的加密包没进隧道的那部分，和平时一样
代价所有流量绕路，VPN 服务器的带宽是上限路由和 DNS 配错的机会更多
  • 两边网段相同就不通。家里是 192.168.1.0/24，办公室内网恰好也是。手机访问办公室的 192.168.1.50 时，路由表认为它是邻居，在家里的 Wi-Fi 上发 ARP 找它，包进不了隧道。给内网和隧道选网段时，要避开家用路由器最常见的那几个。
  • 隧道断了，路由就退回去。tun0 消失时，指向它的路由一起消失，流量改走原来的默认路由，没有任何提示。要不要拦住见第 13 节的断开保护。

05DNS：问谁，从哪条路问

DNS 查询是一个普通的包：UDP，对方端口 53，发给系统里"DNS 服务器"那一项填的地址。它进不进隧道，和别的包一样由路由表决定。所以 DNS 有两件事要对：问的是谁，从哪条路去问。

入网时 DHCP 给的 DNS 服务器是家里的路由器 192.168.1.1。VPN 连上之后，客户端把它换成 VPN 这边指定的解析器，比如隧道对端 10.8.0.1，或者内网里的一台。这个地址写在 VPN 的配置里，或者握手时由服务器下发。要换的理由有两个：

  • 内网的域名只有内网的解析器知道。远程接入时访问 git.corp.example（示意），去问公网的解析器，得到的是"没有这个域名"。
  • 全隧道时不换，域名就漏出去了。见下面。

DNS 泄漏

DNS 泄漏指的是：访问网站的流量走了隧道，DNS 查询却还是明文发给了隧道外面的解析器。本地网络和运营商看不到内容，但你访问的每个域名它们照样看得到。

怎么漏的原因
VPN 没有指定解析器系统继续问 192.168.1.1。它是邻居，/24 那一行比默认路由长，这个包直接从 Wi-Fi 出去
分流时解析器不在隧道的网段里查询按默认路由走了真实网卡
App 自己解析浏览器或 App 内置了加密的 DNS（DNS over HTTPS），不用系统的设置。路上看不到域名，不算泄漏，但它绕过了 VPN 指定的解析器，内网域名会解析不出来

检查时对照两样东西：系统现在用的 DNS 服务器地址，以及路由表里去这个地址的那一行指向哪个接口。DNS 本身的细节见 DNS：域名是怎么查到 IP 的。

06开着 VPN 再走十二步

设定：全隧道，协议是 WireGuard，VPN 服务器在公网上的 198.51.100.20。手机还是连着家里的 Wi-Fi，访问的还是 185.199.108.153:443。

第 0 步：先有隧道

十二步开始之前，VPN 客户端要把隧道建起来，一共三件事。找到服务器：配置里写的是域名时先要解析，这一次只能走隧道外面，因为隧道还不存在。握手：两边互相确认身份，算出同一组密钥；WireGuard 是一个来回，手机发 148 字节的握手发起，服务器回 92 字节的握手回应。建 tun0、改路由表、换 DNS：就是前三节讲的那些。

十二步逐个对照

网站看到的是谁

网站收到的包，源地址是 198.51.100.20。它不知道 203.0.113.7，更不知道 192.168.1.23 和 10.8.0.2。回信按来路倒着走：VPN 服务器查自己的 NAT 记录，把目的换回 10.8.0.2，加密后发给 203.0.113.7；家里的路由器再查它的记录，换回 192.168.1.23。去和回各过两次 NAT。

TTL 怎么变

内层包的 TTL 在隧道里不变。它被加密了，路上的路由器看不到也改不了，减的是外层包的 TTL。整条隧道对内层包来说只算一跳，在 VPN 服务器转发时减 1。所以开着 VPN 跑 traceroute，第一跳就是 10.8.0.1，手机和 VPN 服务器之间的那些路由器一台也不出现。

一个来回变成多久

直连时一个来回是手机到网站再回来，全流程里量到的是 10 毫秒。开了 VPN 是两段相加：

一个来回 = 手机 ⇄ VPN 服务器  +  VPN 服务器 ⇄ 网站  +  两头加解密的时间

全流程里那次访问用了三个来回：TCP 握手、TLS 握手、请求和响应，每一个都按这个式子变长。VPN 服务器正好在手机去网站的路上时，多出来的很少；在相反的方向时，每个来回都多绕一圈。

07开销和 MTU

以太网一帧最多装 1500 字节的 IP 包，这个上限叫 MTU。外层包也得守这个上限，留给内层包的地方就变小了：

怎么算结果不开 VPN
开销，外层走 IPv4IP 头 20 + UDP 头 8 + WireGuard 头 16 + 认证标签 16600
开销，外层走 IPv6IP 头 40 + 8 + 16 + 16800
隧道的 MTU1500 − 80，按开销大的那种留14201500
内层的 MSS1420 − IP 头 20 − TCP 头 2013801460
带时间戳选项时每段的数据1380 − 1213681448

1420 就是 WireGuard 接口默认的 MTU。IPsec 和 OpenVPN 的开销随加密算法和模式变化，不是一个固定的数，算法相同：链路的 MTU 减去全部外层头。

手机上的 TCP 知道 tun0 的 MTU 是 1420，握手时在 SYN 里申报的 MSS 就是 1380，网站发回来的每一段都不会超过它。全流程里那个首页连响应头一共 8406 字节，直连时每段 1448，分 6 段。现在每段 1368，8406 = 6 × 1368 + 198，要 7 段。还在慢启动第一轮的 10 段以内，来回数没变，只是多了一个包。

MTU 配大了会怎样

MTU 是隧道接口上的一个设置，系统不会替你验证它对不对。真实链路的 MTU 比 1500 小时，1420 就偏大了。比如宽带拨号（PPPoE）每帧再占 8 字节，链路 MTU 是 1492：外层走 IPv4 时 1420 + 60 = 1480，装得下；外层走 IPv6 时 1420 + 80 = 1500，超出 8 字节。蜂窝网络、外面还套着另一层隧道时，这个数可能更小。

装不下的外层包，要么被路由器切成两片（IPv4 允许，能通但更慢，有的防火墙见到分片就丢），要么被直接丢掉（IPv6 的路由器从不分片）。被丢时的现象很有特点：ping 得通，DNS 正常，TCP 握手成功，因为这些包都很小。等对方开始发装满的段，包在某一跳被丢，连接停在"连上了但收不到数据"。小页面和小接口一个包就装完，不受影响。所以表现成一部分网站打不开、图片和视频加载不出来，而不是整个断网。

两种补救

  • 路径 MTU 发现。TCP 的包都标着"不许分片"。路由器遇到装不下的，丢掉它并回一条 ICMP 通知，写明这一跳最多能过多少字节（IPv4 叫"需要分片"，IPv6 叫"包太大"）。发送方收到后把段改小重发。问题是这条 ICMP 常被路上的防火墙过滤掉，发送方收不到，一直按原来的大小重发，一直被丢。这种情况叫 MTU 黑洞。
  • MSS 钳制（MSS clamping）。隧道的网关在转发 SYN 时，直接把里面的 MSS 选项改小，比如改成 1380，两端从握手起就不会发出过大的段。它不依赖 ICMP，比上一种可靠，但只对 TCP 有效。VPN 给整个局域网当出口时必须做这一步：局域网里的设备以为 MTU 是 1500，申报的是 1460。

拿不准时把隧道的 MTU 往下调。1280 是 IPv6 规定每条链路都必须支持的最小 MTU，隧道设成 1280 时外层最大 1360 字节，基本不会再装不下，代价是每个包少带 140 字节。

08隧道为什么走 UDP

内层已经是 TCP 了，它自己会编号、确认、重传。外层如果也用 TCP，同一件事有两层在做，丢包时互相添乱。外层用 TCP 时丢一个包，会依次发生这些事：

  1. 外层的 TCP 发现丢了，开始重传。补上之前，后面已经到的数据不能往上交（第 10 步里的规则）。
  2. 隧道里所有内层连接的包，都排在这一个缺口后面。对内层的 TCP 来说，包没有丢，只是全都迟到了。
  3. 内层等不到确认，定时器超时，也开始重传，并把自己的拥塞窗口降到 1 段。
  4. 内层重传的包同样排进外层那条已经堵住的连接，同一份数据最后送了两遍。外层恢复之后，内层还得从慢启动重新往上爬。

这叫 TCP 套 TCP 的重传堆积。网络越差它越严重，而网络差的时候正是最需要稳的时候。

外层用 UDP 时，隧道本身不可靠：外层包丢了就丢了，隧道不补。内层的 TCP 看到的是一次普通的丢包，按第 10 步的办法处理，拥塞控制也只有一层在起作用。内层是通话这类本来就不要重传的流量时，UDP 隧道也不会硬给它加上重传。

外层 UDP外层 TCP
丢一个包只丢那一个内层包，别的连接不受影响整条隧道停下来等重传，所有内层连接一起卡
重传一层：内层自己两层，互相叠加
谁在用WireGuard；IPsec 过 NAT 时；OpenVPN 的默认模式OpenVPN 的 TCP 模式，留给 UDP 不通的网络

UDP 隧道要自己操心一件事：家里的路由器给 UDP 记的那条 NAT 记录，一段时间没有包经过就删掉。隧道空闲久了，服务器发来的包就进不来。所以客户端隔一会儿发一个很小的保活包。WireGuard 里这个设置叫 PersistentKeepalive，常见的值是 25 秒。

10藏住什么，藏不住什么

VPN 改变的是谁在什么位置能看到什么，没有让能看到的人消失。

同一个 Wi-Fi 里的人、热点的主人明文 DNS 里的域名；每条连接的目的 IP 和端口；TLS 握手里的域名；没有 HTTPS 的内容手机在和 198.51.100.20 的 UDP 51820 端口收发加密的包；包的大小、数量和时间
家里的路由器、运营商同上同上。知道你在用 VPN，知道用了多少流量
VPN 服务器的运营者不在路上以前运营商看到的，现在归它：你的公网地址 203.0.113.7，每条连接的目的 IP 和端口，DNS 查询（用它的解析器时），TLS 握手里的域名，没有 HTTPS 的内容

  • 信任换了地方。本地网络和运营商看不到了，VPN 的运营者看得到了。公司的 VPN，看得到的是公司；自己在家里搭的，看得到的是自己和家里的运营商。
  • HTTPS 照样需要。隧道只保护手机到 VPN 服务器这一段。出了隧道，内容靠的还是 TLS。没有 HTTPS 的请求，VPN 服务器和它后面的每一跳都能读能改；有 HTTPS 时它们还看得见域名、包的大小和时间（网络上还看得见什么）。

  • 问题多半出在配置上。流量没进隧道（路由、DNS、IPv6），或者隧道断了没人拦，比加密算法被攻破常见得多。

11Android：VpnService

Android 上的 VPN App 不需要 root，也不用自己建 TUN 设备。系统提供了 VpnService 这个 API：App 向系统要一块 TUN 网卡，系统把别的 App 的包路由进去，这个 App 从一个文件描述符里读到它们。

class TunnelService : VpnService() {
  fun connect() {
    val udp = DatagramSocket()
    protect(udp)                          // 这个 socket 不进隧道，否则外层包会绕回来
    udp.connect(InetSocketAddress("198.51.100.20", 51820))

    val tun = Builder()
      .setSession("demo")
      .addAddress("10.8.0.2", 32)         // tun0 的地址
      .addRoute("0.0.0.0", 0)             // 全隧道。分流就只加内网的网段
      .addDnsServer("10.8.0.1")
      .setMtu(1420)
      .establish() ?: return              // 系统建好 tun0，返回它的文件描述符

    val fromApps = FileInputStream(tun.fileDescriptor)   // 每次 read 得到一个 IP 包
    val toApps = FileOutputStream(tun.fileDescriptor)    // 每次 write 交回一个 IP 包
    // 之后是两个循环：fromApps → 加密 → udp；udp → 解密 → toApps
  }
}

Service 要在清单里声明，带上 BIND_VPN_SERVICE 权限和 android.net.VpnService 这个 action。Builder 的几个方法正好对上前面几节：地址（第 03 节）、路由（第 04 节）、DNS（第 05 节）、MTU（第 07 节）。

去 VPN 服务器的包怎么留在真实网卡上，Android 不靠那条 /32 的路由，而是按 socket 做例外：protect() 给这个 socket 打上标记，系统的路由规则见到标记就不把它的包交给隧道。Android 上每张网各有一张路由表，再用规则决定哪个 App、哪个 socket 查哪张。所以 adb shell ip route 看到的不是全部，要配合 ip rule 一起看。

用户看得到的部分

  • 授权对话框。第一次连接前，App 调 VpnService.prepare()。它返回一个 Intent，启动之后系统弹出对话框，说明这个 App 将能监控网络流量，用户点确定才算数。已经授权过时它返回 null。
  • 状态栏的钥匙图标。隧道存在期间一直显示，App 关不掉它。
  • 同一时间只有一个 VPN。另一个 App 拿到授权时，前一个的隧道被系统收回，它的 Service 收到 onRevoke()。工作资料里可以另有一个。
  • 始终开启（Android 7.0 起）。系统设置里可以把一个 VPN App 设成始终开启：开机后系统自己拉起它，被杀掉了再拉起来。旁边还有一个"屏蔽未使用 VPN 的所有连接"的开关：隧道没建好时，流量被直接丢弃，不改走直连。这就是系统级的断开保护。
  • 按 App 分流。Builder 的 addAllowedApplication() 只让列出的 App 进隧道，addDisallowedApplication() 反过来只排除列出的。两个只能用一个。

自己的 App 怎么知道开着 VPN

val cm = getSystemService(ConnectivityManager::class.java)
val caps = cm.getNetworkCapabilities(cm.activeNetwork)
val onVpn = caps?.hasTransport(NetworkCapabilities.TRANSPORT_VPN) == true

需要 ACCESS_NETWORK_STATE 权限。播放器关心这个，是因为开着 VPN 时几个平常的判断会变：

  • VPN 网络同时带着底下那张网的类型。开着 VPN 连 Wi-Fi，TRANSPORT_VPN 和 TRANSPORT_WIFI 都是 true。只判断"是不是 Wi-Fi"不会出错，判断"是不是只有 Wi-Fi"会。
  • "按流量计费"可能变成 true。VPN App 以 API 29 及以上为目标时，系统默认把 VPN 网络当成按流量计费的，除非它调了 setMetered(false)。"只在不计费的网络下自动缓存"这类逻辑，在 Wi-Fi 加 VPN 时可能不触发。

不用 root 的抓包也靠它

establish() 之后，这个 App 拿到的是手机上别的 App 发出的每一个原始 IP 包。VPN App 把它们加密后送去服务器。抓包 App 拿到同样的包，做的是另一件事：把包记下来（比如存成 pcap 文件），再替它把数据送到真正的目的地。没有服务器，也没有加密，只是借用了"所有的包都先经过我"这个位置。调试自己 App 的流量时很有用，几个特点要知道：

  • 看到的是 IP 包。没有帧头和 MAC，也看不到别的设备的流量。
  • 它在 App 里实现了半个协议栈。普通 App 无权直接发原始 IP 包，所以它得自己解析内层的 TCP 和 UDP，再用 protect() 过的普通 socket 去连目的地。
  • HTTPS 的内容还是密文。要看明文，得让抓包工具冒充服务器，并在手机上装它的根证书。以 API 24 及以上为目标的 App 默认不信任用户装的证书，要在自己 App 的网络安全配置（network_security_config）里给调试版放开，写法见 抓包和证书锁定。
  • 它占着唯一的 VPN 名额。抓包时不能同时开着另一个 VPN。

12对音视频的影响

环节开了 VPN 之后看到的现象
起播出画面之前要走完域名解析、TCP 握手、TLS 握手和第一个请求，每个来回都绕道首帧变慢，绕得越远越明显
吞吐上限是"手机到 VPN 服务器"和"VPN 服务器到 CDN"里窄的那一段。VPN 服务器的带宽还是所有用户分着用的自适应码率选到更低的一档（流媒体协议）
丢包多一段路，多一处排队。无线那一段本来的丢包也还在（物理层）内层的 TCP 降窗口，下载速度一阵一阵地掉
MTU媒体分片的每个包都是装满的，最先碰上 MTU 问题播放列表很小，拿得到；媒体分片卡住不动
直播互动、通话多出来的来回时间直接加在端到端延迟上。外层是 TCP 时，丢一个包整条隧道都停延迟变大，卡顿变多（延迟从哪来）

CDN 给的节点离谁近

视频网站用 CDN 把内容放在很多机房，让每个用户连最近的一个。"最近"有两种判断办法，开了 VPN 都会变：

  • 靠 DNS。CDN 的域名服务器看是哪个解析器来问的，返回离它近的节点。开了 VPN 问的是 VPN 那边的解析器，拿到的是离 VPN 出口近的节点。
  • 靠路由。同一个 IP 在很多机房同时存在，路由器把包送到最近的那个（全流程第 11 步）。包是从 VPN 服务器出发的，所以也是离出口近的。

全隧道时这是对的：流量本来就从 VPN 出口出去，离出口近的节点就是最快的。出问题的是两者不一致的时候：

  • DNS 走隧道，视频流量不走（分流）：拿到离 VPN 出口近的节点，却从家里直连过去，可能绕很远。
  • DNS 没走隧道，流量走隧道（也就是 DNS 泄漏）：拿到离家近的节点，流量却从 VPN 出口过去。

用户反馈"开了 VPN 就卡"时，先看解析到的节点和流量的出口是不是在同一个地方。解析器怎么影响结果见 DNS：同一个名字，不同的答案。

隧道里的 QUIC

HTTP/3 用的 QUIC 跑在 UDP 上（HTTP/2 与 HTTP/3）。UDP 隧道里跑 QUIC，是 UDP 套 UDP：

  • 没有第 08 节的重传堆积。两层里只有 QUIC 自己在重传。
  • 包的大小 QUIC 自己定，而且不许分片。规范要求路径至少能过 1200 字节的 UDP 数据，加上 UDP 头 8、IP 头 20 是 1228 字节（IPv6 是 1248），1420 的隧道装得下。隧道 MTU 被调得太小时 QUIC 连不上，客户端会退回 TCP。MSS 钳制帮不上它，因为它不是 TCP。
  • 换网时隧道可以不断。手机从 Wi-Fi 切到蜂窝，外层的源地址变了。WireGuard 靠密钥认对端，收到新地址发来的合法的包，就把回程地址改成新的。内层的地址 10.8.0.2 没变，隧道里的 TCP 和 QUIC 连接都不用重建。
