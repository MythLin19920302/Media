DNS：域名是怎么查到 IP 的

网络上的机器靠 IP 地址找到对方，人记的却是域名。把域名换成 IP 的这一步叫 DNS 解析，每次连接之前都要先做它。这份笔记拿这个知识库自己的域名当例子，把一次查询从头跟到尾：问了谁，问题和答案的每个字节是什么，答案能用多久，在 Android 上又是谁替你问的。

示例是这个知识库的域名 mythlin19920302.github.io（托管在 GitHub Pages）。记录、TTL、报文大小和耗时，是用 dig、python3 和 curl 向公共 DNS 服务器实测的；报文按 RFC 1035 逐字节拆开。这一页是 一个请求是怎么送到的 里"域名"那一步的展开。

01为什么要有域名

IP 包的头里，目的地是一个 4 字节的数字（装包那一帧里是 b9 c7 6c 99，即 185.199.108.153）。路由器只认它。域名是加在上面的一层名字，解决四件事：

需求只有 IP 会怎样有了域名
好记要记 185.199.108.153记 mythlin19920302.github.io
地址能换服务器搬一次家，写着旧地址的链接和 App 全部失效名字不变，改一条记录
一个名字对多台机器一个地址只能指一处一个名字可以给出几个地址，还能按提问的人在哪给不同的地址
一个地址放很多网站服务器分不出你要哪一个请求里带着域名。实测 github.io 前面换成任何用户名，解析到的都是同样的四个地址，服务器靠域名区分是谁的站

管这层名字的系统叫 DNS（Domain Name System，域名系统）。它是一个分散在全世界的数据库：拿"名字 + 类型"去查，得到一条或几条记录。没有哪台机器存着全部数据，每一段名字由它的主人自己管，查的时候一级一级问下去。

它排在所有连接之前。先解析出 IP，才轮得到握手；解析失败，后面什么都不会发生。

02域名从右往左读

域名用点分成几段，每一段叫一个标签（label）。越靠右管的范围越大，所以要从右往左读：

最右边其实还有一个点，代表根，平时省略不写。写全了是 mythlin19920302.github.io.，叫完全限定域名（FQDN）。dig 输出里的名字都带着这个点。

层这个域名里谁管它的服务器（实测）
根.全球共用的一份根区a.root-servers.net 到 m.root-servers.net，13 个名字
顶级域（TLD）ioio 的注册局a0.nic.io、a2、b0、c0，4 台
二级域github.ioGitHub8 台，分在两家托管商：dns1–dns4.p05.nsone.net 和 4 台 awsdns
主机名mythlin19920302还是 GitHub是 github.io 里的记录，不再往下分
  • 上一级不存下一级的数据，只存"这一段归哪几台服务器管"。这叫授权（delegation）。根只知道 io 归谁，io 的服务器只知道 github.io 归谁。
  • 一个管理者负责的那一片名字叫一个区（zone）。github.io 是一个区，所有 xxx.github.io 的记录都在 GitHub 的那 8 台服务器上。
  • 这个区里放的是一条通配记录。实测在 github.io 前面随便编一个名字，得到的都是同样的四个地址。GitHub 没有给每个用户单独建一条。
  • 每个标签最多 63 字节，整个名字最多 255 字节，不区分大小写。63 这个数的来历见第 06 节。

03谁在问，谁在答

一次解析里有三种角色。手机只和第一种、第二种打交道。

角色在哪做什么不做什么
存根解析器（stub resolver）手机、电脑的系统里把问题发给配置好的那台解析器，等最终答案不会自己从根问起
递归解析器（recursive resolver），下文简称解析器运营商的机房，或者公共的 1.1.1.1、8.8.8.8、223.5.5.5从根开始一级级问到答案，把沿途问到的都缓存下来不存任何域名的原始数据
权威服务器（authoritative server）域名的主人或托管商那里回答自己那个区里的名字；不归自己管的，告诉对方该去问谁不替别人查
  • 手机用哪台解析器，是连上网时 DHCP 发下来的（入网）。家里一般是路由器自己，例如 192.168.1.1。路由器并不递归，它把问题转给运营商的解析器，顺便缓存一下，这种叫转发器（forwarder）。
  • 手机问解析器，是递归查询：头里有一位写着"请替我查到底"（RD，见第 06 节），对方要给最终答案。
  • 解析器问权威服务器，是迭代查询：对方只回答自己这一级知道的，下一步由解析器自己接着问。
所以"DNS 慢"可能慢在两段：手机到解析器（每次都有，一个来回），解析器到各级权威服务器（缓存没命中时才有，好几个来回）。换一台解析器，两段都跟着变。

步问了谁它回答的是字节耗时
准备公共解析器 1.1.1.1根服务器的名单。真正的解析器把这份名单写在程序里，不用问23913 ms
1根：g.root-servers.net不知道，io 归这 4 台管，并附上它们的地址302230 ms

  • 每一级问的都是同一个完整的问题。根不知道答案，但知道 io 归谁，于是回一份名单。这种"我不知道，去问它们"的回答叫转介（referral）。新一些的解析器为了少泄露信息，问根时只问到 io 为止。
  • 根的回答附带了地址，叫胶水记录（glue）。a0.nic.io 这个名字本身就在 io 下面，不给地址就成了死循环。所以根把 4 台服务器的 IPv4 和 IPv6 地址一起给了，共 8 条。
  • io 的回答没有地址。那 5 台服务器的名字在 nsone.net、awsdns-10.co.uk 这些别的域下面，io 管不着。解析器要另外把 dns1.p05.nsone.net 的地址查出来，才能问第 3 步。
  • 只有第 3 步的回答带 aa 标志（authoritative answer）。从解析器转手拿到的同一份答案没有它，nslookup 会注明 Non-authoritative answer。
  • 耗时看问到了哪一台。dig 每一级随机挑一台。另外三次里，根这一步分别是 10、99、12 ms，最后一步问到 nsone 是 17 到 24 ms，问到 awsdns 是 171 ms。真正的解析器会记住哪台快。

真正的解析器很少走完这几步，因为每一级的名单都能缓存：根的名单 518400 秒（6 天），io 的 172800 秒（2 天），github.io 的 3600 秒。平时只用问最后一步，热门的域名连最后一步也省了。

命令里的 +tcp 让每一步都走 TCP。有些网络会替别人回答 UDP 53 上的查询（见第 09 节），走 TCP 能保证每个答案确实来自被问的那台服务器。+nodnssec 是不显示签名记录，免得输出太长。

05记录类型

DNS 里存的不只是 IP。每条记录有五个字段：名字、TTL（能缓存多少秒）、类（几乎只用 IN，Internet）、类型、数据。类型决定了数据是什么。

类型编号存的是实测的例子
A1IPv4 地址，4 字节mythlin19920302.github.io. A 185.199.108.153，共 4 条
AAAA28IPv6 地址，16 字节… AAAA 2606:50c0:8000::153，到 8003::153 共 4 条
CNAME5别名：这个名字等同于另一个名字www.github.com. CNAME github.com.
NS2这个区归哪些服务器管github.io. NS dns1.p05.nsone.net. 等 8 条
SOA6区的管理信息：主服务器、管理员邮箱、版本号、几个定时器github.io. SOA dns1.p05.nsone.net. hostmaster.nsone.net. 1647625169 43200 7200 1209600 3600
TXT16任意文本，常用来证明域名归属、声明谁能用这个域名发邮件github.io. TXT "v=spf1 a -all"
MX15收邮件的服务器和优先级github.com. MX 0 github-com.mail.protection.outlook.com.；github.io 没有
PTR12反过来查：IP 对应什么名字153.108.199.185.in-addr.arpa. PTR cdn-185-199-108-153.github.com.
HTTPS、SVCB65、64连这个服务要用的参数：支持哪些协议、地址提示这个域名没有。cloudflare.com. HTTPS 1 . alpn="h3,h2" ipv4hint=104.16.132.229,104.16.133.229 ipv6hint=…
  • 一次查询只问一种类型。App 要同时拿到 IPv4 和 IPv6 地址，系统就发 A 和 AAAA 两个查询。
  • CNAME 让解析多走一步。解析器查到别名，会接着查它指向的名字，两条记录一起返回。给 GitHub Pages 绑自己的域名，就是加一条 www.自己的域名 CNAME 用户名.github.io。同一个名字有了 CNAME 就不能再有别的记录，所以不带 www 的根域名用不了它。
  • PTR 的名字是把 IP 倒过来写，再接上 in-addr.arpa。日志里把 IP 显示成主机名靠的是它。它由 IP 的主人设置，和正向的 A 记录不保证对得上。
  • HTTPS 记录让浏览器在连接之前就知道对方支持 HTTP/3，不用先连一次 HTTP/2 再升级，见 HTTP/2 与 HTTP/3。旧版 dig 不认识这个类型名，要写成 dig 域名 TYPE65。

问和答用的是同一种格式：12 字节的头，后面最多四段，每段有几条由头里的四个计数说明。

c0 0c 写成二进制是 1100 0000 0000 1100。最高两位是 11，表示这是一个指针，后面 14 位是从报文开头数起的偏移：12，正好是问题里那个名字的位置。意思是"名字和那里的一样"。这叫名字压缩。不压缩的话，每条记录要把 27 字节的名字重写一遍，4 条多出 100 字节。

  • 四个地址的顺序每次都可能不一样。连着问几次，108 到 111 轮流排在第一个。只取第一个地址的程序因此会被分散到不同的地址上。
  • dig 报的是 MSG SIZE rcvd: 118，多 11 字节。dig 发的查询在附加段里多带一条 11 字节的记录（EDNS，见第 08 节），回答里也回了一条。AAAA 的回答 dig 报 166 字节：每条记录的数据从 4 字节变成 16 字节，12 + 31 + 4 × 28 + 11。
  • ID 只有 16 位，报文没有任何签名。谁先把一个 ID 对得上的回答送到，谁就算数。第 09 节的问题都是从这里来的。

07TTL 和几层缓存

每条记录带一个 TTL，单位是秒：拿到之后可以存这么久，过期前不用再问。这个域名的 A 记录是 3600。缓存里的 TTL 会倒着数：

$ dig @8.8.8.8 +tcp mythlin19920302.github.io A      连问 6 次，每次隔 2 秒，只看 TTL

3225   3063   3221   3569   3600   2943

没有一个数超过 3600。出现 3600 的那次，多半是回答的机器手里没有缓存，刚现查的；其余几次是各自那份缓存还剩的秒数。数字忽大忽小，是因为 8.8.8.8 背后有很多台机器，每台各存各的。

从手机到权威服务器，中间每一层都可能存一份：

哪一层存多久怎么清
浏览器自己存一份Chrome 在 chrome://net-internals/#dns
App 的运行时Android 的 InetAddress 存 2 秒，最多 16 条。OkHttp 不缓存解析结果，但连接复用期间不会再解析等 2 秒
操作系统按 TTLAndroid 换一个网络就是新的一份；macOS 用 sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
路由器按 TTL。家用路由器多半是带缓存的转发器重启
递归解析器按 TTL，一群机器各存各的等它过期

命中缓存和没命中差得很远。在这台电脑上用系统的解析接口实测：

情况耗时发生了什么
刚查过的名字再查一次0.5–0.9 ms系统缓存里有，不发任何包
一个从没查过的 xxx.github.io，第一次15 ms到解析器一个来回，解析器再去问权威
同一个名字第二次0.7 ms又回到系统缓存

全流程那一页里的 2 毫秒属于第一种情况。解析器自己也没缓存、要从根问起时，就是第 04 节那几步，几十到几百毫秒。

"不存在"也会被缓存

把 io 错打成 oi，根服务器回答"没有这个顶级域"，结果码是 NXDOMAIN，同时在权威段里附上自己的 SOA 记录：

$ dig @1.1.1.1 +tcp mythlin19920302.github.oi A
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN
.   86400  IN  SOA  a.root-servers.net. nstld.verisign-grs.com.
                    2026112000 1800 900 604800 86400

"不存在"这个结论能缓存多久，取 SOA 的 TTL 和它最后一个数里较小的那个。这里两个都是 86400，也就是一天。io 下面不存在的名字是 3600 秒。系统这一层同样会记：上面那个拼错的名字第一次查用了 32 ms，第二次 0.8 ms 就返回了失败。

拼错了不一定报错。github.io 是通配的，用户名拼错照样解析成功，连上去才得到 HTTP 404。不要用"能不能解析"来判断一个地址存不存在。

改了记录要多久生效

没有一个统一的生效时刻。权威服务器上改完立刻就是新的，但每一份缓存都会把手里的旧记录用到过期为止。最坏的情况是：有人在你修改的前一秒刚查过，那他还要用旧地址 3600 秒，再加上各层缓存自己多留的时间。

  • 迁移之前先把 TTL 改小，比如 300，并且至少等够一个旧 TTL，让所有缓存都换成短的。切换完成后再改回去。
  • 旧地址上的服务多留一段时间。已经建好的长连接不会重新解析，会一直连着旧地址。
  • TTL 是一个取舍。短了切换快，但缓存命中少，首次连接慢的机会多；长了相反。实测维基百科按地区调度的那条记录是 180 秒，这个域名是 3600 秒。
  • 换权威服务器（改 NS）看的是上一级的 TTL。io 里 github.io 的授权是 3600 秒，com 里 github.com 的授权是 172800 秒。"改 DNS 服务器要等 48 小时"的说法就是这么来的。

08UDP、TCP 和 512 字节

DNS 默认走 UDP，对方端口 53。一问一答各一个包，不用先握手，一个来回就结束。代价是 UDP 不管丢没丢，问题或答案丢了，只能由提问的一方等超时后再发一遍。

最早的规定是 UDP 上的 DNS 报文不超过 512 字节。根服务器只有 13 个名字，就是当年为了让名单和地址能放进一个 512 字节的回答。现在这份名单加上 IPv6 地址，实测是 992 字节。放不下的时候有两个办法：

办法怎么做实测
EDNS提问的一方在附加段里放一条特殊的 OPT 记录（类型 41，11 字节），写上"我能收多大的 UDP 报文"。对方就可以发超过 512 字节的回答各家服务器回答里写的上限：1.1.1.1 是 1232，根服务器 1472，awsdns 4096
改走 TCP还是放不下，服务器把 TC 位置 1，回一个截短的回答。提问的一方看到 TC，改用 TCP 53 重问一次。TCP 上每个报文前面多 2 字节的长度见下面

github.com 有 24 条 TXT 记录，回答是 1928 字节，UDP 放不下：

$ dig @1.1.1.1 github.com TXT +bufsize=1232 +ignore        +ignore：看到 TC 也不重试
;; flags: qr tc rd ra; QUERY: 1, ANSWER: 0, AUTHORITY: 0, ADDITIONAL: 1
;; MSG SIZE  rcvd: 39

$ dig @1.1.1.1 github.com TXT +bufsize=1232
;; Truncated, retrying in TCP mode.
;; flags: qr rd ra; QUERY: 1, ANSWER: 24, AUTHORITY: 0, ADDITIONAL: 1
;; MSG SIZE  rcvd: 1928
  • 1232 这个数是算出来的。IPv6 保证能通过的最小包是 1280 字节，减去 IPv6 头 40 字节和 UDP 头 8 字节。再大的 UDP 包可能在路上被分片，分片的包很容易被防火墙丢掉。
  • 改走 TCP 要多花一个来回握手，所以常用的记录都尽量做小。这个域名的 A 回答 107 字节，AAAA 回答 155 字节，离 512 很远。
  • TCP 53 必须是通的。只放行 UDP 53 的防火墙会让大的回答永远拿不到，表现是个别域名解析失败，别的都正常。

09明文的问题和加密 DNS

UDP 53 上的 DNS 是明文，也没有签名。路上的每一台设备都能看到你在查哪个域名，也都能替对方回答。有些网络就是这么做的：把经过的 DNS 查询截下来，交给自己的解析器代答。

想知道自己的网络有没有这样做，可以向一个根本不存在的服务器提问。192.0.2.1 是留给文档举例用的地址，那里没有任何机器：

$ dig @192.0.2.1 mythlin19920302.github.io A
$ dig @192.0.2.1 mythlin19920302.github.io A +tcp

正常的结果是两条都超时。如果第一条居然很快拿到了答案，而第二条超时，说明路上有设备把 UDP 53 上的查询截走代答了。代答的地址多半是对的，但它想给什么都可以。

问题是什么后果
劫持路上的设备或者解析器自己，把回答换成别的地址打开的是别的页面；不存在的域名被指到广告页
污染有人抢在真回答之前，送来一个 ID 对得上的假回答假地址还会被缓存，过期之前一直错
窥探查了哪些域名，路上都看得见即使后面的连接是 HTTPS，访问了哪些网站也是公开的

把报文装进加密的连接

名字端口做法路上的设备看到的
DoT，DNS over TLSTCP 853先建一条 TLS 连接，里面还是原来的报文，前面加 2 字节长度看得出是 DNS，看不到内容。可以把 853 整个封掉
DoH，DNS over HTTPSTCP 443报文当作 HTTP 请求的内容发出去，类型是 application/dns-message和普通的 HTTPS 流量混在一起，分不出来
DoQ，DNS over QUICUDP 853换成 QUIC 来装同 DoT

把第 06 节那 43 个字节原样发给 1.1.1.1，三种走法拿回来的都是同一个 107 字节的报文，区别只在外面套了什么：

走法第一次查询时间花在哪
TCP 53，明文24 msTCP 握手 11 + 一问一答 13
DoT，TCP 85354 msTCP 握手 14 + TLS 握手 26 + 一问一答 14
DoH，HTTP/254 msTCP 握手 15 + TLS 握手 20 + 请求和响应 19

到 1.1.1.1 的一个来回在 11 到 15 毫秒之间。DoT 那次用的测试脚本只支持 TLS 1.2，握手要两个来回；curl 发的 DoH 用的是 TLS 1.3。UDP 只有最后那一个来回。握手的细节见 TLS 握手。

加密只在第一次贵。连接建好之后留着复用，后面每次查询还是一个来回。DoH 用 GET 时，报文做成 base64url 放在网址里。上面那 43 个字节变成 58 个字符：

GET /dns-query?dns=GisBAAABAAAAAAAAD215dGhsaW4xOTkyMDMwMgZnaXRodWICaW8AAAEAAQ

Android 的"私人 DNS"

Android 9 起，设置里的"私人 DNS"就是 DoT，有三档：

选项行为
关闭明文，UDP 53
自动当前网络给的解析器支持 DoT 就用，不支持就退回明文
指定主机名只用这台服务器的 DoT，例如 dns.google、one.one.one.one。连不上 853 端口时不会退回明文，所有解析都失败
  • 它只对走系统解析的 App 生效。自己发 UDP 53 或者自带 DoH 的 App 不受这个开关影响。代码里可以用 LinkProperties.isPrivateDnsActive() 看当前网络是不是在用它。
  • 加密的只是手机到解析器这一段。解析器再去问权威服务器，多数还是明文。之后连网站时，TLS 握手里的域名也还是明文。
  • 另一条路是给记录签名（DNSSEC），让解析器能验出回答被改过。它要求域名一路签下来。实测根和 io 签了，github.io 没签，所以这个域名的回答验不了。
  • 开了 VPN 之后，DNS 一般也跟着换成 VPN 那边的解析器，见 VPN。

同一个域名，在不同地方、不同时间查，得到的 IP 可以不一样。有三种做法，可以叠着用：

做法谁在做选择实测的例子
轮转权威服务器或解析器每次把几个地址换个顺序这个域名的 4 个地址
按提问者的位置给地址权威服务器看是谁在问，给离他近的机房的地址。CDN 的调度多半是这样做的www.wikipedia.org，见下表
任播（anycast）DNS 不选。同一个 IP 在很多机房同时对外宣告，路由器把包送到最近的一处这个域名的 4 个地址；1.1.1.1、8.8.8.8 和根服务器也是

它看到的是解析器的地址，不是手机的。如果你用的解析器离你很远，就会被分到离解析器近、离你远的机房。补救办法是 EDNS 客户端子网（ECS）：解析器把用户地址的前面一段（一般是前 24 位）附在查询里，一起交给权威服务器。

dig 的 +subnet 可以假装自己从别的网段来。通过 8.8.8.8 问 www.wikipedia.org：

假装来自得到的地址反查这个地址得到的名字

用同样三个网段问这个知识库的域名，得到的都是那四个地址，适用范围写的是 /0，意思是"对谁都一样"。GitHub Pages 的就近访问不靠 DNS，靠任播：全流程那一页里到 185.199.108.153 的一个来回只有 10 毫秒，回答的机器显然就在附近，而不是在大洋对岸。这在到站那一步也提到过。

对播放器来说，这一节决定了视频从哪个机房下载。解析器选得不对，会被调度到很远的 CDN 节点，起播慢、容易卡，而问题根本不在码率和缓冲策略上。流媒体怎么分片下载见 流媒体协议。

11hosts 文件

hosts 是本机上一张手写的"名字对 IP"的表。系统解析一个名字时先查它，查到就不再问 DNS。DNS 出现之前，整个网络靠的就是一份这样的文件。

127.0.0.1         localhost
::1               localhost
185.199.108.153   mythlin19920302.github.io     # 加上这一行，这个域名就不再走 DNS
系统位置能不能改
macOS、Linux/etc/hosts要管理员权限
WindowsC:\Windows\System32\drivers\etc\hosts要管理员权限
Android/system/etc/hosts在只读的系统分区里，没有 root 改不了
  • 没有 TTL，没有通配。一行只管一个确切的名字，改完就生效，只对这台机器有效。
  • 常见用途：开发时把线上域名指到测试服务器；把不想访问的域名指到 0.0.0.0。
  • Android 上改不了 hosts，同样的事在 App 里做。调试时要把域名指到某个 IP，用第 12 节 OkHttp 的 Dns 接口。

把前面几节连起来，一个名字的完整查找顺序是：本身就是 IP 的不用查 → App 运行时的缓存 → hosts → 系统缓存 → 解析器 → 各级权威服务器。哪一步有答案就停。

12Android 上的解析

App 里一句 InetAddress.getAllByName(host)，往下经过四层：

① App
  1. InetAddress，或者 OkHttp 的 Dns.SYSTEM
  2. 在调用它的线程上阻塞
② Java 层
  1. 查自己的缓存：16 条，2 秒
  2. 没有就调 getaddrinfo
③ 系统的解析器
  1. 在系统进程 netd 里
  2. hosts、按 TTL 的缓存、私人 DNS
④ 网络给的解析器
  1. DHCP 发的，如 192.168.1.1
  2. UDP 53 或 DoT 853

App 进程自己不发 DNS 包。getaddrinfo 把请求通过本地 socket 交给 netd，由它去查、去缓存。所以系统这层缓存是所有 App 共用的，并且按网络分开：Wi-Fi 一份，蜂窝一份，换了网络不会用到上一个网络查来的结果。

接口返回用在哪
InetAddress.getByName(host)一个地址，就是下面那个数组的第一项简单场景。别的地址都被丢了
InetAddress.getAllByName(host)全部地址，IPv4 和 IPv6 都在，系统已经排好序OkHttp 默认用它
Network.getAllByName(host)同上，但指定在哪个网络上解析手机同时连着 Wi-Fi 和蜂窝时
android.net.DnsResolver（Android 10 起）异步回调，可以取消要指定类型、跳过缓存，或者发自己构造的报文（rawQuery）
  • 前三个是阻塞调用。在主线程上调会抛 NetworkOnMainThreadException。
  • 查不到抛 UnknownHostException，失败的结果同样在 Java 层缓存 2 秒。没声明 INTERNET 权限时抛的是 SecurityException。
  • 传进去的如果本身就是 IP，只检查格式，不发查询。
  • 想知道手机现在用的是哪台解析器：adb shell dumpsys connectivity 里每个网络的 DnsAddresses。

OkHttp 的 Dns 接口

OkHttp 把"域名怎么变成地址"抽成一个只有一个方法的接口。默认实现 Dns.SYSTEM 就是调 InetAddress.getAllByName：

interface Dns {
    // 返回的顺序，就是 OkHttp 尝试连接的顺序
    fun lookup(hostname: String): List<InetAddress>
}

val client = OkHttpClient.Builder()
    .dns(myDns)        // 换成自己的实现
    .build()
  • 换解析方式：在 lookup 里用 HttpDNS，或者用官方的 okhttp-dnsoverhttps 模块走 DoH，失败时再退回 Dns.SYSTEM。
  • 改顺序、加缓存、做预解析：启动时把要用的域名先查一遍，第一个请求就不用等。
  • 调试时指定 IP：对某个域名直接返回测试服务器的地址，相当于一份只在这个 App 里生效的 hosts。
  • 量耗时：EventListener 的 dnsStart 和 dnsEnd 之间就是这一次解析花的时间。连接被复用时不会解析，这两个回调不触发。

为什么大的 App 用 HttpDNS

HttpDNS 是绕开系统解析的一种做法：App 用 HTTP 或 HTTPS 直接访问服务商的一个固定 IP，问"这个域名该连哪个地址"，拿到结果后通过上面的 Dns 接口交给网络库。

系统解析的问题HttpDNS 怎么绕开
被劫持、被污染（第 09 节）不走 UDP 53，用 HTTPS 时路上改不了
调度不准：权威服务器只看到解析器的地址（第 10 节）服务端直接看到手机的出口 IP，按它调度
偶尔很慢：解析器缓存过期要重新递归，UDP 丢了要等超时App 自己缓存、提前刷新，过期的结果先用着同时去更新
改了记录迟迟不生效：各层缓存不一定守 TTL缓存多久由自己定
用 Dns 接口接入，不要改网址。把网址里的域名直接换成 IP，TLS 握手时发给服务器的名字和证书校验用的名字都成了 IP，结果是证书错误，Cookie 和 Host 头也跟着乱。走 Dns 接口时网址里还是域名，只有"连哪个地址"换了。另外要自己处理三件事：失败时退回系统解析；网络切换时清掉缓存；WebView 和播放器不走 OkHttp，要另外接。

music_demo 里的 FFmpeg 只开了 file 和 fd 两个协议，不联网，没有这一步。以后要播网络流，打开 tcp、http 协议时，解析发生在 native 层：libavformat/tcp.c 直接调 getaddrinfo，走的是上面第 ③ 层，不经过 OkHttp，自定义的 Dns 对它不起作用。

13IPv4 和 IPv6 都拿到之后

这个域名有 4 条 A 记录和 4 条 AAAA 记录。手机如果同时有 IPv4 和 IPv6 地址，getAllByName 会把 8 个地址都返回，系统按规则排好序，一般 IPv6 在前。手机没有 IPv6 地址时，系统不返回 IPv6 的结果（getaddrinfo 的 AI_ADDRCONFIG 选项）。

麻烦出在"有 IPv6 地址，但 IPv6 的路不通"：路由器发了地址，上游却没接通。按顺序一个个试的程序先连 IPv6，等到连接超时才换下一个。OkHttp 的连接超时默认是 10 秒，最坏的情况是每个 IPv6 地址各等一次。

Happy Eyeballs（RFC 8305）是解决这件事的标准做法：不等前一个失败，隔一小会儿就并行开始下一个。

① 同时问
  1. A 和 AAAA 一起发
  2. A 先回来，就再等 AAAA 最多 50 ms
② 交错排序
  1. IPv6、IPv4、IPv6、IPv4…
  2. 第一个是 IPv6
③ 错开着连
  1. 先连第一个
  2. 250 ms 没连上，不取消它，同时开始连下一个
④ 谁先通用谁
  1. 哪个先完成握手就用哪个
  2. 其余的取消
谁拿到多个地址后怎么连
getByName 之后 Socket(addr, port)只有第一个地址，连不上就失败
Socket(host, port)Android 上按顺序把每个地址试一遍，前一个失败才试下一个
OkHttp 4.x按 lookup 返回的顺序一个个试，前一个失败或超时才试下一个
OkHttp 5.x默认开启 Happy Eyeballs（它叫 fast fallback）：IPv6 先走 250 ms，然后 IPv4 并行跟上。fastFallback(false) 关掉
FFmpeg 的 tcp 协议交错排序，每隔 200 ms 并行开始下一个，最多同时 3 个（libavformat/network.c）

还在用 OkHttp 4.x 时，可以用自定义的 Dns 把 IPv4 排到前面，让 IPv6 只当后备：

class Ipv4First(private val base: Dns = Dns.SYSTEM) : Dns {
    override fun lookup(hostname: String): List<InetAddress> =
        // false 排在 true 前面：IPv4 在前，同类之间顺序不变
        base.lookup(hostname).sortedBy { it is Inet6Address }
}
