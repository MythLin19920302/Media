configure_android.sh 参数详解

编译 FFmpeg 时，所有决定都在 configure 这一步做完：给谁编、用什么工具、编成什么形态、包含哪些格式。之后的 make 只是照着执行。这篇把 ffmpeg/configure_android.sh 里的每一个参数讲清楚，并给出一份索引：想查某个参数时该去哪里找。

输入30 个参数
→
configure 探测只编译，不运行
→
输出config.h · config.mak
→
make6 个 .so

本文的默认值来自 FFmpeg n8.1.3 的 configure --help 原文，"实际结果"来自这个工程的 ffmpeg/build/arm64-v8a/ffbuild/config.mak 和构建日志。交叉编译的背景知识见 在 Mac 上编出 Android 的 FFmpeg。

01它为什么最重要

FFmpeg 的构建分三步：configure → make → make install。后两步没有任何可调的地方，全部行为由 configure 生成的四个文件决定：

configure 生成的文件内容谁来读
config.h平台探测结果：ARCH_AARCH64、HAVE_NEON 等几百个宏，以及完整的配置命令行 FFMPEG_CONFIGURATIONC 源码，用 #if 取舍
config_components.h每个组件开没开：CONFIG_H264_DECODER 1C 源码，决定哪些格式被注册
ffbuild/config.mak编译器路径、CFLAGS、LDFLAGS、要编哪些文件make
ffbuild/config.log每一次探测用的测试程序、命令和编译器输出你，configure 失败时

所以出了问题，几乎都能追到 configure 的某个参数上：架构不对是第 ② ③ 组，加载失败是第 ⑤ 组，某个格式打不开是第 ⑦ 组。

02脚本的四段

67 行的脚本分四段。真正传给 configure 的只有第三段的 ARGS 数组，前两段是在为它准备变量和挡住错误的前提。

段行做什么
按 ABI 取值9–14由 ABI 名得到 ARCH、CPU、TRIPLE。两个 ABI 的差别只在这里。
路径和版本16–23源码、构建、安装三个目录；API、NDK、工具链目录 TC。
前提检查25–29编译器存在、源码存在、源码目录里没有残留的 config.h。
参数和执行31–67ARGS 数组分七组；进入构建目录后调用 configure。

03参数的语法规则

FFmpeg 的 configure 是一个 8000 多行的 shell 脚本，参数只有三种写法：

写法含义例子
--enable-X / --disable-X开关一个功能、一个库，或一整类组件--enable-shared、--disable-doc、--disable-decoders
--X=值设置一个取值--arch=aarch64、--cc=…
--enable-类别=名字,名字点名打开某类里的若干组件，逗号分隔，不能有空格--enable-decoder=h264,hevc

有四条规则不写在帮助里，但决定了参数怎么生效：

  • 从左到右依次处理，后面的覆盖前面的。所以 --disable-everything 必须写在所有 --enable-decoder=… 之前；反过来写，刚打开的就又被关掉了。
  • 组件名写错不会报错，只有一行警告。--enable-decoder=h246 会得到 Option --enable-decoder=h246 did not match anything，configure 继续往下跑，产物里就是没有这个解码器。参数名本身写错（比如 --enable-shard）才会直接报 Unknown option 退出。
  • 组件之间有依赖，会自动带上。打开一个组件，它声明依赖的其他组件会被一并打开，所以实际启用的可能比你写的多，见 第 ⑦ 组。
  • 帮助里方括号是默认值。[no] 是默认关，[autodetect] 是探测到就用、探测不到就悄悄关掉。对 autodetect 的库显式写 --enable-xxx，探测不到时会报错退出，而不是悄悄关掉。

04① 安装位置

参数脚本里的值默认值作用
--prefixffmpeg/out/<abi>/usr/localmake install 的根目录。库装到 PREFIX/lib，头文件装到 PREFIX/include。

不写的话会试图装进 Mac 的 /usr/local，把手机用的库混进本机系统目录。每个 ABI 用各自的目录，产物才不会互相覆盖。相关的还有 --libdir、--incdir、--shlibdir，可以把库和头文件分别指到别处，这个工程用默认的 PREFIX/lib 和 PREFIX/include。

05② 目标平台

参数脚本里的值默认值作用
--enable-cross-compile开关告诉 configure 产物不能在本机运行：探测程序只编译和链接，不执行；Mac 上要跑的构建工具改用 host 编译器。
--target-osandroid空（按本机猜）目标操作系统。决定动态库的命名和链接方式。
--archaarch64 / arm空（按本机猜）目标 CPU 架构。决定编哪个目录下的汇编优化（libavcodec/aarch64/ 或 libavcodec/arm/）。
--cpuarmv8-a / armv7-a空产物要求的最低指令集，变成编译器的 -march=。

--target-os=android 具体改了什么

configure 里有一段按目标系统分支的代码，android 这一支只有几行，但每一行都对应 Android 的一个限制：

android)
    disable symver                                  # 不做符号版本
    SLIB_INSTALL_NAME='$(SLIBNAME)'                 # 安装的文件名不带版本号
    SLIB_INSTALL_LINKS=                             # 不创建 .so.62 → .so 这类软链接
    SHFLAGS='-shared -Wl,-soname,$(SLIBNAME)'       # soname 也不带版本号
    add_allcflags -fPIE

桌面 Linux 上会得到 libavcodec.so.62.x.y 加两个软链接，soname 是 libavcodec.so.62。APK 只打包文件名以 .so 结尾的文件，也不支持软链接，所以这里全部去掉版本号。不写 --target-os=android，产物在手机上会报 library "libavcodec.so.62" not found。

--cpu 落到哪里

# ffmpeg/build/arm64-v8a/ffbuild/config.mak
CFLAGS=   -march=armv8-a -std=c17 -fPIE -fomit-frame-pointer -fPIC -pthread -g …
# ffmpeg/build/armeabi-v7a/ffbuild/config.mak
CFLAGS=   -march=armv7-a -std=c17 -fPIE -fomit-frame-pointer -fPIC -marm -pthread -g …

--cpu 是下限：写 armv8-a 表示所有 arm64 手机都能跑。写得更高（比如 armv8.2-a）编译器会用上新指令，老手机遇到就崩溃。更新的指令集优化不靠这个参数，FFmpeg 默认开着运行时 CPU 检测，在支持的手机上自动走更快的汇编路径。

--cpu=host 在交叉编译时没有意义。它的意思是"按当前这台机器的 CPU 优化"，而当前机器是 Mac。configure 会给出警告。

06③ 工具链

参数脚本里的值默认值这个工具做什么
--cc$TC/bin/<triple>24-clanggccC 编译器，同时也被当作链接器和汇编器的入口。
--ar$TC/bin/llvm-arar把多个 .o 打成静态库 .a。只编动态库时构建过程中间也会用到。
--nm$TC/bin/llvm-nmnm -g列出目标文件的符号。configure 用它探测符号名前缀，make 用它生成导出符号表。
--ranlib$TC/bin/llvm-ranlibranlib给静态库建索引。
--strip$TC/bin/llvm-stripstripmake install 时去掉调试符号，体积大幅减小。

五个默认值都是 Mac 自带的工具：gcc 在 Mac 上其实是 Apple clang，产出 Mach-O；ar、nm、strip 只认 Mach-O。漏掉任何一个，要么 configure 失败，要么在 make 或 install 的某一步报"无法识别的文件格式"。

为什么不用 --cross-prefix

很多教程写的是 --cross-prefix=aarch64-linux-android-，让 configure 自己拼出 …-gcc、…-ar、…-nm。这套写法对应的是旧版 NDK 的 GCC 工具链。现在的 NDK 里，编译器文件名中间夹着 API 级别（aarch64-linux-android24-clang），而 llvm-ar 这些工具没有前缀，拼不出来，所以逐个指定。

没写但存在的第二个编译器

构建日志里有一行 host C compiler gcc。FFmpeg 构建时要先编几个小工具并在 Mac 上当场运行，它们用 --host-cc 指定的编译器，默认就是本机的 gcc，正好是对的，所以脚本里不用写。相关参数还有 --host-cflags、--host-ldflags。

07④ sysroot

参数脚本里的值默认值作用
--sysroot$TC/sysroot空把这个目录当作目标系统的根目录，头文件和系统库都从这里找。

它会同时出现在编译和链接两边：

CPPFLAGS= --sysroot=…/darwin-x86_64/sysroot -D_ISOC11_SOURCE -D_FILE_OFFSET_BITS=64 …
LDFLAGS=  -Wl,-z,max-page-size=16384 --sysroot=…/darwin-x86_64/sysroot -march=armv8-a …

NDK 的 clang 包装脚本其实已经知道自己的 sysroot 在哪，不写这个参数通常也能编过。显式写上有两个好处：configure 自己做探测时用的路径和编译时一致；别人读脚本时能看出系统头文件来自哪里。只想换头文件目录、不换库目录时用 --sysinclude。

08⑤ 产物形态

参数默认值作用不写会怎样
--enable-shared关编动态库 .so没有 .so，App 无法 loadLibrary
--disable-static静态库默认开不编静态库 .a多编一套用不到的 .a，构建时间接近翻倍
--enable-pic按平台决定生成位置无关代码，变成 -fPIC开了 shared 时通常会自动打开；显式写上避免依赖推断
--extra-ldflags空原样追加到链接参数。这里传 -Wl,-z,max-page-size=16384.so 按 4 KB 对齐，在 16 KB 页的设备上加载失败
--disable-programs默认编不编 ffmpeg、ffprobe、ffplay 命令行程序多编几个 App 用不到的可执行文件
--disable-doc默认编不生成 man、HTML 文档浪费时间，还可能因缺少文档工具而警告
--disable-avdevice默认编不编 libavdevice（摄像头、麦克风、屏幕采集的封装）多一个 .so。Android 上采集走系统 API，用不到

--extra-* 是通用的后门

configure 没有专门参数的事，都通过这一族参数把选项直接塞给编译器或链接器：

参数追加到典型用途
--extra-cflags编译每个 .c-I 外部库头文件目录、-D 宏
--extra-ldflags所有链接页对齐、-L 外部库目录
--extra-ldsoflags只在链接 .so 时只影响动态库的链接选项
--extra-libs链接的库列表末尾-lm 之类需要额外链接的库

值里有空格或逗号时要整体加引号，脚本里写的是 --extra-ldflags="-Wl,-z,max-page-size=16384"。

六个库各是什么

库职责关掉它的参数
libavutil公共基础：内存、数学、像素和采样格式定义。其他库都依赖它不能关
libavcodec编解码器、解析器、码流过滤器--disable-avcodec
libavformat容器的解封装和封装、读写协议--disable-avformat
libavfilter画面和声音的滤镜图--disable-avfilter
libswscale画面缩放和像素格式转换--disable-swscale
libswresample音频重采样和采样格式转换--disable-swresample

09⑥ Android 能力

这一组在帮助里属于 "External library support"：让 FFmpeg 链接到它自己源码之外的库。这里的三个"外部库"都是 Android 系统自带的，不需要另外编译。

参数默认值作用依赖
--enable-jni关让 FFmpeg 能持有 JavaVM、从 C 调用 Java 方法。MediaCodec 的一部分实现要靠它。pthreads
--enable-mediacodec关接入系统的硬件编解码器，才会有 h264_mediacodec 这类组件可选。目标是 android、能链接到 libmediandk、pthreads
--enable-zlibautodetect链接系统的 libz。PNG 解码要用它做解压。sysroot 里有 libz.so
  • 打开能力不等于打开组件。--enable-mediacodec 只是让硬件编解码器"可以被选"。真正编进去哪个，还要在第 ⑦ 组点名。这个工程只点了编码器 h264_mediacodec；解码器列表里的 h264 是软件解码器，硬件解码器的名字是 h264_mediacodec，目前没有打开。
  • zlib 为什么显式写。它本来就是自动探测的，探测不到会被悄悄关掉，随后 PNG 解码器因为依赖不满足也被悄悄关掉。显式写上后探测不到会直接报 zlib requested but not found，问题暴露在 configure 这一步。
  • JNI 还需要运行时配合。编进去之后，App 启动时要把 JavaVM 交给 FFmpeg（av_jni_set_java_vm），MediaCodec 的 Java 路径才能工作。

构建日志的摘要里能看到这一组的结果，还多出一个没写的：

jni                     mediacodec              zlib

External libraries providing hardware acceleration:
v4l2_m2m                                        ← 自动探测到的，见第 11 节

每一环都要有对应的组件，缺一环整条链就断。新增一种格式时，按这条链逐环检查。

--enable-protocol=file,fd

名字作用为什么要

fd从一个已打开的文件描述符读写Android 10 起拿不到媒体文件的真实路径，只能通过 ContentResolver 拿到 fd

没有打开 http、https、rtmp 等网络协议，所以这个构建不能直接播放网络地址。

--enable-decoder=… 和 --enable-parser=…

解码器负责解压；解析器负责在解码之前把连续的码流切成一帧一帧，并读出分辨率、采样率等信息。大多数格式两者要成对打开，名字通常相同，少数不同。

--enable-bsf=…

码流过滤器不解码，只改写压缩数据的包装方式。同一种编码在不同容器里的存放格式不一样，换容器或交给硬件编解码器时要转。

点名的和实际启用的不一样

构建日志摘要里比脚本多出三个组件，都是 mp4 封装器带进来的。configure 源码里写着依赖关系：

mp4_muxer_select="mov_muxer"
mov_muxer_select="iso_media iso_writer riffenc rtpenc_chain vp9_superframe_bsf aac_adtstoasc_bsf ac3_parser"
多出来的类别原因
movmuxermp4 封装器只是 mov 封装器的一种模式
ac3parsermov 封装器写 AC-3 音轨时要解析它的头
vp9_superframebsfmov 封装器写 VP9 视频时要用

依赖声明有三种，在 configure 里搜 组件名_类别_ 就能看到：_deps 是必须满足的前提，不满足这个组件就被关掉；_select 是它会强制带上的；_suggest 是有就用、没有也行的。

11没写但生效的默认值

脚本没写的参数都按默认值走。构建日志开头的摘要把它们全列出来了，下面是值得知道的几项，以及想改时用哪个参数。

摘要里的一行含义想改用
runtime cpu detection yes运行时检测手机 CPU 支持哪些指令集，选最快的实现--disable-runtime-cpudetect，体积略小但失去这层优化
NEON enabled yes 等ARM 的汇编优化全部编进去，运行时按上一条选择--disable-neon、--disable-asm。只在排查汇编相关问题时关，解码会明显变慢
optimizations yes开编译器优化--disable-optimizations，调试 FFmpeg 本身时用

v4l2_m2m自动探测到的 Linux 视频硬件接口。Android 内核是 Linux，所以探测通过；没有点名相关组件，不起作用--disable-v4l2-m2m，或用 --disable-autodetect 关掉所有自动探测

14改参数的流程

  1. 先确认名字存在。用 ffmpeg/src/configure --list-* 或 --help 查，组件名写错只有一行警告，容易漏看。
  2. 改 ffmpeg/configure_android.sh 的 ARGS。放进对应的组，组件类参数保持在 --disable-everything 之后。
  3. 重跑 ffmpeg/build_android.sh。它会删掉旧的构建目录从头来，两个 ABI 都重编，避免新旧配置混在一起。只想快速试一个 ABI 时在后面加 ABI 名。
  4. 看摘要。打开 ffmpeg/build/<abi>/build.log，确认要的组件出现在 Enabled … 列表里，再搜一下有没有 WARNING。
  5. 验证产物并重编 App。检查架构、依赖和页对齐的三条命令见 验证产物。头文件有变化时，桥接库的 C 代码要跟着核对。
新增一种格式最常见的遗漏：只加了 decoder，没加 parser 或 demuxer。按 第 ⑦ 组的那条链逐环检查。

默认值和分组取自 FFmpeg n8.1.3 的 configure --help；组件总数取自 --list-* 的输出；实际启用的组件和编译参数取自本工程 arm64-v8a 的构建结果。
