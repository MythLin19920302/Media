用 OpenGL 把 YUV 画到屏幕

解码器给的是三块 YUV 数据，屏幕要的是 RGB 像素。中间的换算、缩放和旋转都交给 GPU：把三个平面当成三张纹理传上去，画一个铺满的矩形，让着色器对每个像素做一次矩阵乘法。这份笔记对着工程里的 YuvGlRenderer 走一遍。

解码线程YuvFrame
→
上传3 张纹理
→
画2 个三角形
→
片元着色器，每像素mat3 × (yuv − offset)
→
屏幕RGB

代码引自 app/src/main/java/com/example/music/player/YuvGlRenderer.kt，用的是 OpenGL ES 2.0。YUV 的排列和换算公式见 YUV 与像素格式。

01要解决的问题

把一帧 1280×720 的 yuv420p 显示出来，要做三件事：把色度放大回全尺寸，逐像素换算成 RGB，再缩放到 View 的大小。按 30 帧算：

921,600 像素 × 30 帧/秒 ≈ 每秒 2765 万次"取 3 个数、乘一个 3×3 矩阵"

在 CPU 上做，一颗核的相当一部分时间就花在这上面，还要另外分配一块 RGB 内存。GPU 天生就是干这个的：它对每个像素并行运行同一小段程序，放大和缩放由纹理采样顺带完成，结果直接写进屏幕的缓冲区。CPU 只需要把三块 YUV 原样交出去。

02整体流程

涉及两个线程。解码线程只管产出帧，所有 OpenGL 调用都在 GLSurfaceView 自己的渲染线程上。

解码线程
  1. 从帧池取一个空帧
  2. 解码，填满 Y、U、V
  3. 等到该显示的时刻
  4. renderer.submit(frame)
交接
  1. 帧放进 pending
  2. 旧的没画就还回帧池
  3. requestRender()
渲染线程
  1. onDrawFrame 被调用
  2. 取走 pending
  3. 三个平面上传成纹理
  4. 帧还回帧池
GPU
  1. 画一个铺满的矩形
  2. 每个像素跑一次着色器
  3. 交换缓冲区，上屏

03OpenGL 的几个词

词是什么这里的用法
上下文（context）OpenGL 的全部状态，绑定在一个线程上GLSurfaceView 创建并管理，只能在渲染线程上用
纹理（texture）存在显存里的一张图Y、U、V 各一张
顶点着色器对每个顶点运行，决定它在屏幕上的位置原样输出四个角
片元着色器对每个像素运行，决定它的颜色取 Y、U、V，换算成 RGB
程序（program）一对编译链接好的着色器只有一个
attribute每个顶点各不相同的输入位置、纹理坐标
uniform整次绘制都相同的输入三张纹理、换算矩阵、零点
varying顶点着色器传给片元着色器的值，在三角形内部自动插值纹理坐标

OpenGL 是一台状态机：先"绑定"一个对象，后面的调用都作用在它身上。所以代码里总是成对出现 glBindTexture 然后 glTexImage2D。

04GLSurfaceView 的三个回调

GLSurfaceView 替你建好上下文和渲染线程，你只实现 Renderer 的三个方法，它们都在渲染线程上被调用：

回调什么时候工程里做什么
onSurfaceCreated上下文刚建好，或丢失后重建编译着色器、创建三张纹理、设置纹理参数。之前的 GL 对象全部作废，必须重建
onSurfaceChangedView 尺寸变了glViewport(0, 0, width, height)：画满整个 View
onDrawFrame需要画一帧时有新帧就上传，然后画

View 的创建在 SoftwarePlayerScreen.kt 里，有三处设置值得注意：

GLSurfaceView(viewContext).apply {
  setEGLContextClientVersion(2)                          // 用 OpenGL ES 2.0
  preserveEGLContextOnPause = true                       // 切后台时尽量保留上下文
  setRenderer(renderer)
  renderMode = GLSurfaceView.RENDERMODE_WHEN_DIRTY       // 有新帧时才画
}
  • RENDERMODE_WHEN_DIRTY：默认模式是按屏幕刷新率不停地画。视频只有 30 帧，没有新帧时重画是浪费电。改成这个模式后，只有调用 requestRender() 才会触发 onDrawFrame。
  • 画面比例不在 GL 里处理。GL 总是把画面拉伸铺满 View，由 Compose 布局把 View 的宽高比设成视频的宽高比。
  • 生命周期：页面 onPause / onResume 时要调用 GLSurfaceView 的同名方法，否则渲染线程不会停。

05三张单通道纹理

OpenGL ES 2.0 没有"YUV 纹理"这种东西。做法是把每个平面当成一张只有一个通道的灰度图：

纹理内容尺寸（1280×720 时）纹理单元
uTexYY 平面1280 × 720GL_TEXTURE0
uTexUU 平面640 × 360GL_TEXTURE1
uTexVV 平面640 × 360GL_TEXTURE2
 
GLES20.glActiveTexture(GLES20.GL_TEXTURE0 + i)
GLES20.glBindTexture(GLES20.GL_TEXTURE_2D, textures[i])
if (reallocate) {
  GLES20.glTexImage2D(GLES20.GL_TEXTURE_2D, 0, GLES20.GL_LUMINANCE, width, height, 0,
      GLES20.GL_LUMINANCE, GLES20.GL_UNSIGNED_BYTE, planes[i])       // 分配显存并上传
} else {
  GLES20.glTexSubImage2D(GLES20.GL_TEXTURE_2D, 0, 0, 0, width, height,
      GLES20.GL_LUMINANCE, GLES20.GL_UNSIGNED_BYTE, planes[i])       // 只更新内容
}

四个细节，每一个漏掉都会出一种特定的问题：

设置作用不设会怎样
GL_LUMINANCE每个像素 1 字节。着色器里读 .r 得到 0–1 的值—
glPixelStorei(GL_UNPACK_ALIGNMENT, 1)告诉 GL 每行数据不做 4 字节对齐默认按 4 对齐。宽度不是 4 的倍数时每行错位，画面斜纹
GL_CLAMP_TO_EDGE纹理坐标超出边缘时取边缘的值ES 2.0 里宽高不是 2 的幂的纹理必须用它，否则采样结果是黑的
GL_LINEAR采样时在相邻像素间线性插值用 GL_NEAREST 的话放大后有锯齿，色度边缘尤其明显

GL_LINEAR 顺带解决了色度放大：U、V 纹理只有画面的四分之一大，着色器用和 Y 相同的纹理坐标去采样，GPU 自动插值出每个像素该用的色度值，不需要自己把 U、V 放大。

只在尺寸变化时用 glTexImage2D 重新分配，平时用 glTexSubImage2D 只换内容，省掉每帧重新分配显存的开销。

06一个全屏四边形

GPU 只会画三角形。要让着色器对屏幕上每个像素都跑一遍，就画两个三角形拼成的矩形，正好铺满整个视口。

屏幕坐标（范围固定是 −1 到 +1，原点在中心，y 向上）

(-1, 1) ③────────④ (1, 1)
        │ ╲      │              顶点顺序 ① ② ③ ④
        │   ╲    │              GL_TRIANGLE_STRIP 把它画成
        │     ╲  │              ①②③ 和 ②③④ 两个三角形
(-1,-1) ①────────② (1,-1)
private val positions = floatBufferOf(-1f, -1f,  1f, -1f,  -1f, 1f,  1f, 1f)   // 左下、右下、左上、右上
…
GLES20.glDrawArrays(GLES20.GL_TRIANGLE_STRIP, 0, 4)

每个顶点除了位置，还带一个纹理坐标：这个角对应图像的哪个位置。纹理坐标的范围是 0 到 1，(0, 0) 是上传数据的第一行最左边，也就是画面的左上角。不旋转时四个角的对应关系是：

顶点屏幕位置纹理坐标取的是画面的
①左下 (−1, −1)(0, 1)左下角
②右下 (1, −1)(1, 1)右下角
③左上 (−1, 1)(0, 0)左上角
④右上 (1, 1)(1, 0)右上角

屏幕坐标的 y 向上，而图像数据的第一行在上面，所以纹理坐标的纵向是反着配的。配反了画面就上下颠倒。

07着色器

顶点着色器没有任何计算，位置原样输出，纹理坐标传给下一级：

attribute vec4 aPosition;
attribute vec2 aTexCoord;
varying vec2 vTexCoord;
void main() {
  gl_Position = aPosition;
  vTexCoord = aTexCoord;
}

GPU 在三角形内部对 vTexCoord 做插值，所以片元着色器在每个像素上拿到的，正好是这个像素对应的图像位置。片元着色器是整件事的核心：

varying vec2 vTexCoord;
uniform sampler2D uTexY;
uniform sampler2D uTexU;
uniform sampler2D uTexV;
uniform mat3 uYuvToRgb;
uniform vec3 uOffset;
void main() {
  vec3 yuv = vec3(
      texture2D(uTexY, vTexCoord).r,          // 三张纹理用同一个坐标采样
      texture2D(uTexU, vTexCoord).r,
      texture2D(uTexV, vTexCoord).r);
  gl_FragColor = vec4(clamp(uYuvToRgb * (yuv - uOffset), 0.0, 1.0), 1.0);
}

最后一行就是 YUV 换算公式 rgb = matrix × (yuv − offset)。纹理采样得到的值已经是 0–1，所以零点也按 0–1 给：有限范围时是 (16/255, 128/255, 128/255)。clamp 把超出范围的结果截断。

矩阵和零点不写死在着色器里，而是每次绘制前作为 uniform 传入：

GLES20.glUniformMatrix3fv(uYuvToRgb, 1, false, matrix.matrix, 0)
GLES20.glUniform3fv(uOffset, 1, matrix.offset, 0)

这样换一个视频、换一套标准或范围，只要换这两个数组，着色器不用重新编译。

矩阵是列主序的。GLSL 的 mat3 按列存放：数组的前三个数是第一列，不是第一行。YuvColorMatrix 里的数组就是按列排的，第一列是 Y 对 R、G、B 的贡献。按行填的话颜色完全错乱。

精度

着色器开头按设备能力选择浮点精度：支持就用 highp，否则退到 mediump。ES 2.0 不保证片元着色器支持 highp，直接写 highp 在个别老设备上会编译失败。

08旋转靠纹理坐标

手机竖着拍的视频，文件里存的仍然是横向的画面，另外带一个"显示时请旋转"的标记。工程里的 portrait_rotate90.mp4 就是这样：存储尺寸是 1280×720，标记要求顺时针转 90° 后显示成 720×1280。

旋转不需要搬动任何像素。只要改四个顶点的纹理坐标，让屏幕的每个角去取画面的另一个角：

顺时针旋转① 左下② 右下③ 左上④ 右上
0°(0, 1)(1, 1)(0, 0)(1, 0)
90°(1, 1)(1, 0)(0, 1)(0, 0)
180°(1, 0)(0, 0)(1, 1)(0, 1)
270°(0, 0)(0, 1)(1, 0)(1, 1)

以 90° 为例：屏幕左上角 ③ 取的是 (0, 1)，也就是原始画面的左下角。原来的左下角跑到了左上，正是顺时针转了 90°。

旋转角度来自视频流的显示矩阵。FFmpeg 给出的是逆时针角度，portrait_rotate90.mp4 里读到的是 −90，C 层取反并归一化成 0、90、180、270 之一再交给 Kotlin。转 90° 或 270° 后宽高互换，View 的宽高比也要跟着换。

09帧怎么交接

解码线程和渲染线程之间只有一个位置 pending，用一把锁保护。规则很简单：只保留最新的一帧。

fun submit(frame: YuvFrame) {
  val target = synchronized(lock) {
    pending?.let {
      it.release()            // 上一帧还没画：还回帧池
      framesReplaced++        // 记一次"被替换"
    }
    pending = frame
    view
  }
  target?.requestRender()     // 请渲染线程画一次
}
  • 不排队。渲染跟不上时，旧帧直接作废。视频宁可丢一帧，也不能越积越多、画面越来越落后。
  • 上传完立刻归还。数据进了纹理，这块内存就没用了，马上还回帧池给解码线程复用。纹理本身留在显存里，所以没有新帧时重画（比如 View 尺寸变化）仍然能画出上一帧。
  • 帧池限制了内存。帧池里固定只有 3 个 YuvFrame（一帧在解、一帧等着画、一帧备用），解码线程拿不到空帧就等着，不会无限分配。
  • 配置也走同一把锁。换视频时 configure 更新矩阵和旋转角度，渲染线程在 onDrawFrame 开头一次性读走，保证一帧里用的是同一套设置。

什么时候调用 submit 由播放调度决定：按帧的时间戳等到该显示的时刻再交；晚得太多的帧直接不交，接着解下一帧追进度。这部分在 SoftwareVideoPlayback.kt。

11常见坑

现象原因处理
全黑在渲染线程之外调用了 GL；或纹理不是 2 的幂却没设 CLAMP_TO_EDGE；或着色器编译失败没检查GL 调用只放在三个回调里；检查编译和链接状态并打印日志
全绿U、V 纹理没上传，采样得到 0确认三个平面都上传了，三个 sampler 各绑到自己的纹理单元
画面斜纹没设 GL_UNPACK_ALIGNMENT 为 1，或传进来的数据带行填充设对齐为 1；数据先按 linesize 拷成紧密排列
上下颠倒纹理坐标的纵向配反了屏幕下边对应纹理的 t = 1
颜色完全错乱矩阵按行填进了 mat3按列填，或在数学上先转置
切后台回来后黑屏或花屏上下文丢失，旧的纹理和程序 ID 已经作废在 onSurfaceCreated 里无条件重建所有 GL 对象，并把记录的纹理尺寸清零
竖屏视频被压扁旋转 90° 后没有交换宽高比布局用旋转后的显示尺寸
上传时崩溃ByteBuffer 不是 direct 的，或 position 不在 0用 allocateDirect；上传前 position(0)
