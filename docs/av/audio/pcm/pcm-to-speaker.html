从 PCM 到喇叭

PCM 是一串按时间排列的数字，每个数是某一瞬间喇叭振膜该在的位置。这份笔记沿着数据走一遍：它在文件和内存里长什么样，三个参数怎么决定它的含义，AudioTrack 怎么把它播出来，以及在哪里、按什么规则加工它。

02PCM 是什么

声音是空气压力的连续起伏，喇叭振膜跟着前后运动。电脑存不了连续的量，只能每隔一小段时间量一次振膜的位置，记成一个数。48000 Hz 就是每秒量 48000 次。按顺序排好的这串数就是 PCM，在代码里就是一个 FloatArray 或 ShortArray。

  • 下标就是时间。第 n 格对应第 n ÷ 采样率 秒。数组里没有存时间，时间是算出来的。
  • 单独一格听不到声音。它只是某一刻的位置，就像单张照片看不出动作。声音来自格子之间的变化。
  • 混音就是逐格相加。人声、钢琴、鼓同时响，每一刻它们的位置相加成一个数，所以一个数组装得下整首歌。
  • 立体声是两串数交错存放。L R L R…，同一时刻的左右两个数合起来叫一帧。

示例音轨解码后的前几格：

pcm[0]  0.000 ms  -0.00092
pcm[1]  0.023 ms  +0.01451
pcm[2]  0.045 ms  +0.03422
pcm[3]  0.068 ms  +0.04976     相邻两格相隔 1/44100 秒 ≈ 0.0227 ms

class PcmChunk(
    val data: FloatArray,   // 交错排列：L R L R …
    val sampleRate: Int,    // 每秒多少帧
    val channels: Int,      // 每帧几个数
    val startFrame: Long,   // 第一帧在整条音轨里的帧号，来自 pts
) {
    val frames: Int get() = data.size / channels
    val durationUs: Long get() = frames.toLong() * 1_000_000L / sampleRate   // 先乘再除，用 Long 防溢出
    operator fun get(frame: Int, channel: Int) = data[frame * channels + channel]
}
整数除法会把短片段算成 0。2048 / 2 / 48000 在 Kotlin 里等于 0。先换成微秒并用 Long，或者直接用 Double。平面格式的数据，单个数组的长度就是帧数，不要再除以声道数。

04采样率：时间的尺子

采样率和视频的 fps 是一回事：时间方向上的分辨率。它不代表音高。同一个 1000 Hz 的声音，用 44100 Hz 采样每个来回记 44.1 个点，用 48000 Hz 记 48 个点，描述的是同一个波形，播出来音高一样。

它决定能记录的最高音

振膜来回一次至少要两条指令，一条往前、一条往后，所以：

能表示的最高频率 = 采样率 ÷ 2
44100 Hz → 22050 Hz（人耳上限约 20000 Hz，够用）
 8000 Hz → 4000 Hz（老式电话，听得懂但发闷）

超过上限的振动不会消失，而是被记成一个假的低频，叫混叠：用 44100 Hz 采 30000 Hz，点连起来是一条 44100 − 30000 = 14100 Hz 的波。电影里车轮倒转、30 fps 拍每秒闪 25 次的灯看起来像闪 5 次，是同一个原理。所以录音设备采样前会先滤掉一半采样率以上的成分。

和视频不同的是，采样率低不会"卡"，而是会"闷"。DAC 后面的低通滤波器会把台阶抹平成连续波形，耳朵听不到"一格一格"，损失的只是高音。

声明错了会变速变调

数组里没有时间，时间全靠声明的采样率换算。48000 Hz 的数据按 24000 Hz 播放，就是半速播放，振膜来回也慢一半，低一个八度，时长翻倍。就像把 60 fps 的视频当 30 fps 播成了慢动作。

更高的采样率换来的是余量

对 20 kHz 以内的声音，44.1 kHz 和 96 kHz 抹平后画出的是同一条曲线，听不出区别。多出来的是 20 kHz 到采样率一半之间的空间：

  • 放慢录音：放慢一半，40 kHz 的成分降到 20 kHz。96 kHz 录的能补满高频，44.1 kHz 录的高频是空的。
  • 失真、压缩这类处理：会产生新的高频谐波。10 kHz 的三次谐波 30 kHz，在 44.1 kHz 下会折回到 14.1 kHz 变成刺耳的杂音；在 96 kHz 下安全地待在听不见的区域。插件内部的"过采样"就是为此。
  • 滤波：44.1 kHz 下，从"全部保留"到"必须滤掉"只有 20→22.05 kHz 这 2 kHz 的过渡带，滤波器必须很陡；96 kHz 下有 28 kHz。

"变速不变调"用的是切段重排一类的算法，效果主要看算法，和采样率关系不大。只做裁剪、淡入淡出、EQ、混音的话，44.1 kHz 或 48 kHz 完全够用。

和采样率绑在一起的两件事。滤波器系数要按采样率计算：按 48000 算的 4000 Hz 系数用在 44100 的数据上，实际起点会偏到 4000 × 44100 / 48000 = 3675 Hz。采样率不同的两段 PCM 不能逐格相加，第 n 格代表的时刻不一样，必须先重采样到同一个采样率。

05位深：数值的尺子

满幅是固定的：±1.0 就是振膜能推到的最远位置，位深再高也不会更响。多出来的位是在同一个范围里画更密的刻度，就像同一把 1 米长的尺子，8 位有 256 个刻度，16 位有 65536 个。刻度粗时，很轻的声音只落在少数几格上，被四舍五入成颗粒噪声。每多 1 位，动态范围增加约 6 dB，16 位约 96 dB。视频里对应的是色深：8 位天空渐变会出色带，10 位就平滑了。

值和位深不是一回事

PCM 里存的是值：每一刻振膜该在的位置。位深不是值，而是装这个值的格子有多少位、能写多细。把 PCM 画成坐标图就很清楚：值是每个点的纵坐标读数，位深决定纵轴从 −1 到 +1 画了多少条横线，采样率决定横轴每秒画多少条竖线。两个轴的范围都是固定的，采样率和位深只决定格子切得多细。

真实的值可以是 ±1 之间的任意数：麦克风输出的电压本来就是连续的，解码、混音、EQ、淡入淡出算出来的也都是任意小数。存的时候只能取最近的刻度，这一步叫量化，误差最多半格。刻度越细越准，但有上限：好的 DAC 连同模拟电路，有效精度大约 20 位，手机通常更低，再细的刻度播放端发挥不出来。

示例音轨的 pcm[1] 换不同位深去存：

四行描述的是同一个时刻、同一个振膜位置，位深只改变每个值占几个字节、写得多准。另外两点：

  • 位深按每个值算，不按每帧算。立体声 s16 的一帧是 2 个值 × 2 字节 = 4 字节。
  • 位深整段固定，值每帧都在变。位深只在格式里声明一次（WAV 头的 0x22、AudioTrack 的 ENCODING_PCM_16BIT），值是每秒 44100 个、个个不同。

同样 32 位，int 和 float 不是一回事

32 位整数32 位 float
位的分配32 位全部存一个整数1 位符号 + 8 位指数 + 23 位尾数
可表示的值均匀的整数，相邻差 1越靠近 0 越密，相对精度约 24 位
满幅2147483647（s16 是 32767）1.0，而且可以超出

加工时用 float 有三个实际原因：

  • 超出范围不翻转。s16 里 26214（0.8）+ 19661（0.6）存回 Short 会变成 −19661，从 +1.4 跳到 −0.6，听起来是很响的"啪"。float 就是 1.4，最后统一限幅即可。
  • 小声音不丢。s16 里 3 × 0.1 = 0.3 只能存成 0，再 × 10 还是 0；float 原样还原。
  • 算式直接写。滤波系数、音量都是小数，整数要改成"乘 65536 再右移 16 位"的定点写法。

s16 够不够

作为最终交付格式，播放、存储、传输都够用。CD 是 16 位，Android 播放链路默认也是 16 位，取整误差约 −96 dB，低于 DAC、功放和环境的底噪。只有两处值得更高精度：中间加工用 float，防止误差累积和溢出；录音用 24 位，给后期放大留余量。这和修图一样：在 RAW 或 16 位里编辑，最后导出 8 位 JPEG。

两种格式之间的换算

// 两个方向都用 32768，转一圈完全无损
fun toFloat(s: Short): Float = s / 32768f
fun toShort(x: Float): Short = (x * 32768f).roundToInt().coerceIn(-32768, 32767).toShort()

去程乘 32767、回程除以 32768 这种不对称写法，会让 32767 转一圈变成 32766。每转回 short 一次就取整一次、多一份误差，所以中间全程用 float，只在最后写入或导出前取整一次。淡出尾巴只剩几格时，取整会让波形变成台阶、带点颗粒感；专业做法是取整前加一点极小的随机噪声（dither），把误差变成均匀的底噪，手机播放和 AAC 导出用不到。

  • ENCODING_PCM_8BIT 是无符号的，0 到 255，静音是 128。
  • ENCODING_PCM_24BIT_PACKED、ENCODING_PCM_32BIT 需要 API 31；float 需要 API 21；s16 所有版本都支持。

把 95 cd 6d 3c 解码成 float

1. 文件里是小端序，倒过来写：         3c 6d cd 95
2. 逐位换成二进制：                   0011 1100 0110 1101 1100 1101 1001 0101
3. 按 1 | 8 | 23 切开：               0 | 0111 1000 | 110 1101 1100 1101 1001 0101
4. 符号 0 → 正数
   指数 0111 1000 = 120，减 127 = −7 → × 2⁻⁷ = 0.0078125
   尾数前补 1：1 + 0x6dcd95 / 2²³ = 1 + 7,196,053 / 8,388,608 = 1.857836
5. 乘起来：+1.857836 × 0.0078125 = +0.0145143

float 就是二进制的科学计数法：0.0145 = 1.857836 × 2⁻⁷。同样 4 个字节按 32 位整数读是 1,013,829,013，按 float 读才是 0.0145143。字节本身没有类型，怎么读由格式规定。转成 s16 后是 476 = 0x01DC，在内存里是 dc 01。

Float.fromBits(0x3c6dcd95)                                           // 0.014514347
ByteBuffer.wrap(bytes).order(ByteOrder.LITTLE_ENDIAN).float          // 从原始字节读

FloatArray 在内存里就是一个接一个的 4 字节，和 .f32 文件的内容完全相同。所以文件、Java 数组和 C 的 float* 之间传递只是原样拷贝，前提是字节序一致。Android 手机和 Mac 都是小端序。

08音高、振幅、响度

AudioTrack 和硬件只需要两样东西：时间尺子（采样率）和每一刻的数值。音高和响度没有任何字段存着，是从数值的变化规律里统计出来的。

一个来回怎么界定

从一次"从下往上穿过 0"到下一次"从下往上穿过 0"是一个完整来回（周期）。从 0 到下一个 0 只是半个来回，按它算频率会高一倍。更准确的定义是"整个形状多久重复一次"：带泛音的声音一个周期里有好几个小峰，峰的个数不等于来回次数。

频率 = 采样率 ÷ 每个来回的帧数        44100 ÷ 44.1 = 1000 Hz
振幅 = 数值离 0 最远能到多少          示例音轨约 0.125
响度 = 一个时间窗内的均方根（RMS）    0.125 ÷ √2 ≈ 0.088 → 20·log₁₀(0.088) ≈ −21 dBFS

同一串数里叠着几种时间尺度：1 帧约 0.023 ms 是最小刻度；一个来回 0.05 到 50 ms，是音高所在的尺度；响度要用 50 到 400 ms 的窗口统计；一个音符几百毫秒，旋律和淡入淡出在这个尺度变化。

// 只适用于单一频率的纯音；真实音乐要用 FFT
fun estimateFrequency(pcm: FloatArray, sampleRate: Int): Double {
    val ups = (1 until pcm.size).filter { pcm[it - 1] < 0f && pcm[it] >= 0f }
    if (ups.size < 2) return 0.0
    val framesPerCycle = (ups.last() - ups.first()).toDouble() / (ups.size - 1)
    return sampleRate / framesPerCycle
}

fun rmsDbfs(pcm: FloatArray, from: Int, frames: Int): Double {
    var sum = 0.0
    for (i in from until from + frames) sum += pcm[i] * pcm[i]
    return 20 * log10(sqrt(sum / frames))
}

横向看音高，纵向看响度

单独一个数什么也说明不了，声音的信息全在数值随时间的变化里。对比有两个方向，互不影响：

  • 横向（时间方向）：同一个形状隔多少帧重复一次 → 频率 → 音高，也就是尖不尖。
  • 纵向（数值方向）：离 0 最远能到多少 → 振幅 → 响度，也就是大不大。峰顶高是"响"，不是"尖"。

钢琴上，往右的键是高音（弦振得快），按得重是大声（弦振得幅度大），轻按最右边的键就是"小声的高音"。还有两种情况不影响音高：一是快速上下跳但间隔没有规律，那是噪声，听起来"沙沙"的，没有音高；二是波形很陡，比如 100 Hz 的方波每次跳变瞬间完成，音高仍是 100 Hz，陡只带来更多高次泛音，让声音更亮、更"嗡"。

频率怎么控制

生成声音时，频率就是公式里的 f。每帧前进的角度是 360° × f ÷ 采样率，1000 Hz 在 44100 Hz 下每帧前进 8.16°，第 11 帧到峰，第 44 帧完成一个来回。f 翻倍，每帧步幅翻倍，音高高一个八度。

for (n in pcm.indices) {
    val t = n.toDouble() / sampleRate                       // 第 n 帧的时刻
    pcm[n] = (0.125 * sin(2 * PI * f * t)).toFloat()        // 每秒振 f 次的振膜，此刻在哪
}

录下来的声音，频率来自真实的发声体：弦越短越紧振得越快，声带越紧音越高。

同一段 PCM 里频率一直在变

  • 旋律：采样率从头到尾不变，变的是数值起伏的快慢。
  • 泛音：一个音除了基频（如 440 Hz），还有 880、1320 Hz 等。基频决定音高，泛音比例决定音色。
  • 和弦：几个音逐帧相加，波形变复杂，但每帧仍然只有一个数。
  • 噪声：峰谷到处都是但毫无规律，各个频率都有。
  • 直流偏移：整体被抬高、一次都不穿过 0，先减去平均值再数。
  • 真峰值：高频时采样点可能落在峰顶两侧，DAC 抹平后的曲线比最大的那个数还高，所以导出时限幅常留到 −1 dBFS。

要知道"这一刻是多少 Hz"，得取一小段（比如 2048 帧）做 FFT。段取得长，频率分得清但时间模糊；段取得短，时间准但频率糊。时频图就是逐段 FFT 后按时间排起来。

为什么振得快听起来就尖

空气里没有"尖"，只有振得快和振得慢。快慢一路原样传下去：喇叭每秒来回 4000 次，空气疏密就每秒交替 4000 次，鼓膜也每秒来回 4000 次。把"快"翻译成"尖"的是内耳的耳蜗：里面有一条约 3.5 cm 长的基底膜，入口端窄、硬、轻，最里端宽、软、重。和琴弦一样，细而紧的地方容易被快的振动带动，粗而松的地方容易被慢的带动，所以膜上每个位置都有自己的频率。

耳蜗相当于一台机械的频率分析器，和时频图做的是同一件事：把混在一起的振动按快慢摊开到不同位置。图上的刻度还说明一件事：频率每翻一倍，在膜上大致挪动一样长的距离。所以 220 → 440 Hz 和 440 → 880 Hz 听起来升高得一样多，都是一个八度（钢琴上隔 12 个键），EQ 的频率轴也因此按对数画。

至于为什么偏偏叫"尖"：生活里小、轻、细、绷紧的东西振得快（哨子、鸟叫、细弦），大、重、松的振得慢（大鼓、打雷、粗弦），大脑就把"快"和"细、尖"联系在了一起。

尖不等于刺耳

频率越高越尖，这是单调的；刺耳却在 2000 到 5000 Hz 最严重，再往上反而变成"细、亮"。同样的振幅，只改频率：

频率听感
100 Hz闷，听着偏轻
1000 Hz普通的"嘟"，示例音轨就是它
3000～4000 Hz听着最响、最扎耳
10000 Hz细、亮，没那么刺
16000 Hz很细，不少成年人已经几乎听不见
20000 Hz 以上听不见

耳道是一根约 2.5 cm 的管子，会在 3000 Hz 上下共振，把这一段放大；耳蜗对这里也最灵敏，说话的辅音、婴儿哭声都在这一段。所以 PCM 里数值一样大，3500 Hz 听起来比 100 Hz 或 12000 Hz 响得多。让声音刺耳的常见原因：

  • 2000 到 5000 Hz 能量太多：尖叫、刹车声、EQ 提过头的人声。
  • 陡峭的跳变或削波：数值被截平或突然跳一下，会多出一串高次泛音，破音和"咔哒"声就是这么来的，见超出 ±1。
  • 太响：任何频率开大了都难受。
  • 两个很接近的频率同时响：1000 Hz 和 1030 Hz 一起响，音量每秒忽大忽小 30 次，听起来粗糙、发毛。

09AudioTrack 怎么播

你往缓冲区里写，硬件按固定速度从里面读。某个采样点什么时候响，由硬件时钟和它在整段数据里的位置决定，不由你的代码决定。

  • 写得快：缓冲区满了，write(…, WRITE_BLOCKING) 阻塞，直到硬件读走一部分。播放循环不需要自己 sleep。
  • 写得慢：缓冲区读空（underrun），硬件只能输出 0，听起来是卡顿或"啪"的一声。
  • 延迟：写进去的数据要等缓冲区里排在前面的播完才轮到，缓冲区越大越不容易卡，但改了参数也越晚听到。

用示例音轨、2048 帧缓冲区、每块 1024 帧模拟的时间线：

时间发生了什么
0 msplay()，开始解码块 0；硬件开始每秒取 44100 帧
2 ms块 0 写入 1024 帧，喇叭开始播
4 ms块 1 写入，缓冲区 1960 帧（这 2 ms 硬件读走了 88 帧）
6 ms块 2 只放得进 176 帧，write() 阻塞
25.2 mswrite(块 2) 返回，阻塞了 19.2 ms；喇叭开始播块 1，它是 21.2 ms 前写进来的
之后每 23.2 ms 放行一块，每块在缓冲区里等约 44 ms

如果每块解码要 30 ms，比它能播的 23.2 ms 还久：块 0 在 53.3 ms 播完，块 1 到 60.0 ms 才写进来，中间输出了 6.8 ms 的 0。缓冲区再大也只能推迟卡顿，消除不了。

开始、结束和进度

  • 流式模式不知道总长度。对它来说"播完了"和"应用来不及写"一样，都是缓冲区空了。结束要由你告诉它：写完最后一块调用 stop()，已写入的会播完再停。
  • 立即停止：pause() 再 flush()，丢掉没播的数据。seek 时就这么做，同时把滤波器状态清零。
  • 知道何时真正播完：记下写了多少帧，用 notificationMarkerPosition 加 onMarkerReached，或者轮询 playbackHeadPosition。
  • MODE_STATIC：一次性放进整段数据，适合按键音这类短声音。
  • 进度：playbackHeadPosition 是数据被系统取走的帧数，后面还有混音器和驱动的缓冲。做音画同步要用 getTimestamp()，它给出"第几帧在哪个时刻真正到达输出端"。
write 第三个参数的单位随重载变化。FloatArray 是 float 个数，ShortArray 是 short 个数，ByteArray 是字节数，而且必须是每帧字节数的整数倍。传错单位不会报错，只会播错。

环节做什么pcm[1] 在这里

11加工 PCM

加工放在解码之后、写入之前。加工过的数据要在缓冲区里排一会儿队才被听到，由此有五条规则：

  1. 必须比实时快。处理 21 ms 的音频要远少于 21 ms，否则 underrun。
  2. 状态跨块保留。滤波器的中间状态是成员变量，块与块之间不能清零，否则交界处会"咔"；seek 时才清零。
  3. 参数改了不会立刻听到。缓冲区里已经存着加工好的数据，蓝牙耳机还要再加 150 到 300 ms。
  4. 按"第几帧"决定效果，不按"现在几点"。你处理的数据比实际听到的提前一个缓冲区。
  5. 顺序：统一格式（交错 float）→ EQ 等效果 → 音量和淡入淡出 → 限幅到 ±1.0 → 写入。中间可以超过 1，最后才限幅，做法见超出 ±1。

淡入淡出

直接截断时，截断点的值很可能不是 0，振膜会在 1/44100 秒内被猛拉回原位，发出"啪"。不想要明显的渐变，首尾也至少各加 5 到 10 ms。以 48000 Hz、截 30 秒、淡入 0.3 秒、淡出 1.5 秒为例：总帧数 1,440,000，前 14,400 帧系数从 0 升到 1，最后 72,000 帧从 1 降到 0。立体声同一帧的左右两个数乘同一个系数。

class FadeEnvelope(
    sampleRate: Int,
    private val channels: Int,
    private val totalFrames: Long,
    fadeInSec: Double = 0.3,
    fadeOutSec: Double = 1.5,
) {
    private val fadeInFrames = (fadeInSec * sampleRate).toLong()
    private val fadeOutFrames = (fadeOutSec * sampleRate).toLong()
    private var frameIndex = 0L                    // 跨块累计

    private fun gainAt(frame: Long): Float {
        val fadeIn = if (frame < fadeInFrames) frame.toFloat() / fadeInFrames else 1f
        val left = totalFrames - 1 - frame
        val fadeOut = if (left < fadeOutFrames) left.toFloat() / fadeOutFrames else 1f
        val x = minOf(fadeIn, fadeOut).coerceIn(0f, 1f)
        return x * x                               // 平方曲线；人耳按对数感知，线性会显得前快后慢
    }

    fun process(pcm: FloatArray, size: Int) {
        val frames = size / channels
        for (f in 0 until frames) {
            val g = gainAt(frameIndex + f)
            for (c in 0 until channels) pcm[f * channels + c] *= g
        }
        frameIndex += frames
    }
}
  • 开头要截准：AAC 只能按包跳转，从某个包开始解码时第一个包输出不完整。从起点前约 0.1 秒开始解码，丢掉起点之前的帧，起点那帧记为 0。
  • 结尾：数满总帧数就停，最后一块只用前面一部分。
  • 配合歌词：歌词在 12.34 秒、淡入 0.3 秒，就从 12.04 秒开始截，淡入正好在第一个字处结束；歌词时间轴同步偏移 0.3 秒。

突出高音：高架滤波

/** f0 以上放大 gainDb，以下基本不变。系数来自 RBJ Audio EQ Cookbook。 */
class HighShelf(sampleRate: Int, f0: Double, gainDb: Double, private val channels: Int) {
    private val b0: Float; private val b1: Float; private val b2: Float
    private val a1: Float; private val a2: Float
    private val z1 = FloatArray(channels)          // 每个声道各自的状态，跨块保留
    private val z2 = FloatArray(channels)

    init {
        val a = 10.0.pow(gainDb / 40)
        val w0 = 2 * PI * f0 / sampleRate          // 系数和采样率绑定
        val cosW = cos(w0)
        val k = 2 * sqrt(a) * (sin(w0) / 2 * sqrt(2.0))
        val a0 = (a + 1) - (a - 1) * cosW + k
        b0 = (a * ((a + 1) + (a - 1) * cosW + k) / a0).toFloat()
        b1 = (-2 * a * ((a - 1) + (a + 1) * cosW) / a0).toFloat()
        b2 = (a * ((a + 1) + (a - 1) * cosW - k) / a0).toFloat()
        a1 = (2 * ((a - 1) - (a + 1) * cosW) / a0).toFloat()
        a2 = (((a + 1) - (a - 1) * cosW - k) / a0).toFloat()
    }

    fun process(pcm: FloatArray, size: Int) {
        for (i in 0 until size) {
            val ch = i % channels
            val x = pcm[i]
            val y = b0 * x + z1[ch]
            z1[ch] = b1 * x - a1 * y + z2[ch]
            z2[ch] = b2 * x - a2 * y
            pcm[i] = y
        }
    }
}

"突出高音"按想要的效果有不同做法：想让人声更清楚，用峰值滤波在 2 到 5 kHz 提 2 到 3 dB，多了马上刺耳；想更亮但不刺，把高架设在 8 kHz 左右，加的是"空气感"。也可以反过来削弱低频，同样显得高音突出，而且不会超限。提升会让接近 1 的值超出范围，处理方法见下一节。

超出 ±1：削波和余量

超过 1 的值会不会"按 1 算"，要看在哪一步：

位置超过 1 会怎样做法
float 处理过程中没关系。EQ 提完是 1.2，后面乘 0.8 就是 0.96，什么都没丢。这是用 float 加工的主要好处中间不用管
直接把 float 写给 AudioTrackAndroid 允许超出约 +3 dB（约 1.41），但后面的增益和处理随时可能把它削掉，DAC 最终也有硬上限写入前回到 ±1 以内
float 转 short不限幅会溢出：1.2 × 32768 = 39321，存进 Short 变成 −26215，振膜从最前面猛拽到后面，很响的"啪"先 coerceIn 再转
 
// 正确：先限幅再转，1.2 → 32767（相当于 +1）
(x * 32768f).roundToInt().coerceIn(-32768, 32767).toShort()

// 错误：直接转，1.2 → 39321 → 溢出成 −26215
(x * 32768f).toInt().toShort()

"按 1 算"叫削波。它不只是顶到最大音量，而是把波形顶部削平：

比到了 1 才一刀切更好的做法有三种。同样输入振幅 1.2 的正弦，出口对比：

硬削波 coerceIn顶部削平、拐角尖，刺耳。只适合当最后的保险。
软削波超过 0.8 后越接近 1 压得越狠，永远到不了 1，拐角是圆的，泛音少很多。
压低增益预留余量或限幅器：整体先降，形状完整，只是小声一点。
  1. 预留余量（最简单）：EQ 提了多少分贝，就先把整体降多少，数值根本不会超。
  2. 限幅器（limiter）：只在快超的时候自动把增益压下来，之后再慢慢放回去。平时不改变音量，适合动态大的歌。
  3. 软削波：用 tanh 这类曲线把超出的部分压进剩余空间。偶尔几个峰超一点时用它，影响很小。
// 1. 预留余量：高音提 6 dB，就先整体乘 10^(−6/20) ≈ 0.5
val headroom = 10f.pow(-boostDb / 20f)

// 2. 软削波：门限以下原样不动，以上用 tanh 压进剩余空间，连接处斜率连续
fun softClip(x: Float, t: Float = 0.8f): Float {
    val a = abs(x)
    if (a <= t) return x
    return sign(x) * (t + (1 - t) * tanh((a - t) / (1 - t)))
}

// 3. 限幅器：超过上限立刻压低增益，之后按 release 慢慢恢复。没有前瞻，是示意
class Limiter(
    sampleRate: Int,
    private val channels: Int,
    private val ceiling: Float = 0.95f,
    releaseMs: Double = 100.0,
) {
    private val release = exp(-1000.0 / (releaseMs * sampleRate)).toFloat()
    private var gain = 1f                                   // 跨块保留

    fun process(pcm: FloatArray, size: Int) {
        for (f in 0 until size / channels) {
            var peak = 0f
            for (c in 0 until channels) peak = maxOf(peak, abs(pcm[f * channels + c]))
            val target = if (peak > ceiling) ceiling / peak else 1f
            gain = if (target < gain) target else target + (gain - target) * release
            for (c in 0 until channels) pcm[f * channels + c] *= gain
        }
    }
}

对 music_demo 来说第一种就够：提高音的同时把整体降同样的分贝，最后转 short 时的 coerceIn 只当保险。歌曲本身已经很响、动态又大时，再在淡入淡出之后加限幅器。

处理代码只写一套

输入可能是 short 也可能是 float，只在边界转换：short 进来除以 32768 变成 float，用同一套 float 代码处理，限幅后乘 32768 变回 short。按元素操作时（data[frame * channels + ch]）两种数组写法完全一样；只有直接操作字节时，要再乘每个采样的字节数。

  • 统一采样率：歌曲多半是 44.1 kHz，视频原声多半是 48 kHz。用 swresample 转一次到同一个采样率再混合，不要往上升采样。
  • 按帧号裁剪：起点帧 = 秒 × 采样率，30 秒就是 30 × 采样率 帧；从起点前约 0.1 秒开始解码。
  • 淡入提前：从歌词时间点前 0.3 秒开始截，歌词时间轴同步偏移。
  • 全程 float：FFmpeg 的 AAC 解码器输出 fltp，AAC 编码器也直接吃 fltp，导出链路不必经过 short。
  • 滤镜白名单：想在 FFmpeg 滤镜里做截取、淡入淡出和 EQ，要在 configure_android.sh 的 filters 里加 atrim、asetpts、afade、treble（或 highshelf、equalizer）后重新编译。
  • EQ 留余量：提高音时整体降同样的分贝，出口的 coerceIn 只当保险，见超出 ±1。
  • 预览和导出一致：两边用同一套参数和曲线，最好就是同一份 PCM 处理代码。
解码 → 重采样（统一成 48000 立体声 float）→ 截取（丢掉起点之前的、数满就停）
     → EQ → 淡入淡出 → 限幅 → AudioTrack 或 AAC 编码器
