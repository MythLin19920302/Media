H.264 解码：350 字节怎么变回一帧画面

示例视频里，一帧 1280×720 的画面平均只占 350 字节，解码后是 138 万字节。这份笔记把视频包按位拆开，看里面到底存了什么，解码器又是凭什么用这么少的数据把整帧画面算回来的。

一个包，平均350 字节
→
拆成 NAL，读到一个 slice3600 个宏块
→
逐块：预测 + 残差一帧 YUV
→
内存里1,382,400 字节

示例是工程里 landscape_720p.mp4 的视频轨：H.264 High 档次、1280×720、30 fps、240 帧，画面是彩条测试图。参数集和 slice 头的字段用 FFmpeg 的 trace_headers 读出，宏块类型用 -debug mb_type 统计。解码之后的 YUV 是什么样，见 YUV 与像素格式。

01为什么能压到几千分之一

解码后   1280 × 720 × 1.5 字节 × 240 帧 = 331,776,000 字节 ≈ 332 MB
文件里   240 个包合计                    =      84,056 字节 ≈ 84 KB
                                            约 3900 : 1

示例是静止的彩条加一小块在动的东西，特别好压，所以比例很夸张。手机拍的 720p 视频一般是 2 到 5 Mbps，对应 70 到 170 比 1。不管哪种，靠的都是同一个思路：不存画面本身，只存"猜不准的那部分"。

画面里的规律怎么利用名字
相邻的像素通常差不多用左边和上边已经解出来的像素去猜这一块帧内预测
相邻的两帧通常差不多到前面的帧里找一块最像的，只记"在哪里"帧间预测、运动补偿
猜完剩下的误差，细节部分眼睛不敏感把误差变换到频域，细节记得粗一点变换和量化
最后剩下的数里 0 特别多常见的用短码，少见的用长码熵编码

真正丢信息的只有量化那一步，其余三步都是无损的。解码就是把这四步倒着做一遍。

02NAL：码流的最小单位

H.264 的码流由一个个 NAL 单元组成。每个 NAL 单元的第一个字节是头，后面是内容。头的 8 位分三段：

0禁止位
永远是 0
11重要程度
0 = 没有别的帧要参考它
00101类型
5 = 关键帧的画面数据

这是示例第一帧画面数据的头字节 65。

播放时会遇到的类型只有几种：

类型名字内容常见的头字节示例里有几个
7SPS整条流的参数：分辨率、档次、参考帧数671，在容器里
8PPS图像级的参数：熵编码方式、默认的量化强度681，在容器里
5IDR slice关键帧的画面数据651
1非 IDR slice其余帧的画面数据41、01239
6SEI附加信息，解码不依赖它061
9AUD分隔符，表示新的一帧开始090
  • slice 是一帧画面的一部分。一帧可以切成几个 slice，各自独立解码。示例每帧只有 1 个 slice，所以 240 帧正好 240 个 slice。
  • 重要程度那 2 位很有用。239 个非 IDR slice 里，120 个是 2（41），119 个是 0（01）。是 0 的那些帧没有任何别的帧参考，来不及解的时候可以整帧扔掉，不会影响后面的画面。
  • 示例第一个包有 7618 字节，其中 691 字节不是画面。那是一个 SEI，里面是明文：编码器 x264 的版本号和它用的全部参数（cabac=1 ref=5 bframes=3 keyint=250 crf=26.0 …）。想知道一个视频是怎么压出来的，可以先找这段文字。

03两种包装

NAL 单元一个接一个放在一起时，要有办法知道每个从哪开始。有两种做法：

起始码（Annex B）长度前缀（AVCC）
怎么分隔每个 NAL 前面放 00 00 00 01 或 00 00 01每个 NAL 前面放它的长度，通常 4 字节
SPS、PPS 在哪夹在码流里，一般每个关键帧前面重复一次不在码流里，在容器的 avcC 里
谁在用裸 .h264 文件、MPEG-TS、直播流、MediaCodec 的输入MP4、MKV、FLV
FFmpeg 怎么认extradata 为空或者以起始码开头extradata 的第一个字节是 1

示例是 MP4，用的是长度前缀。第 2 个包的头 8 个字节：

00 00 03 B9   41 9A 24 6C …
└ 长度 953 ┘  └ NAL 从这里开始，头字节 41

这个包一共 957 字节，4 字节长度加 953 字节的 NAL，正好。第 1 个包里有两个 NAL：00 00 02 AF（687）后面是 SEI，再往后 00 00 1B 0B（6923）后面是 IDR slice。

两种包装里的 NAL 内容完全一样，转换只是换掉前面那几个字节，再决定 SPS、PPS 放哪。FFmpeg 的码流过滤器 h264_mp4toannexb 做的就是这件事。

防止内容里出现起始码

NAL 的内容是任意的二进制数据，万一里面正好出现 00 00 01，就会被误认成下一个 NAL 的开头。所以编码器写内容时，只要遇到连续两个 00 后面跟着 00 到 03，就在中间插一个 03。示例的 SPS 里就有一处：

… 02 80 00 00 03 00 80 00 00 1E 07 …
              └ 这个 03 是插进去的，解码前要去掉

长度前缀的包装并不需要这个保护，但内容里照样带着这些 03，这样两种包装之间转换时不用改内容。自己解析 SPS 时忘了去掉它，后面的字段全都会错位。

档次和级别

档次说的是用了哪些工具，级别说的是规模有多大。解码器声明自己支持到哪个档次和级别，超出的就解不了：

档次profile_idc特点
Baseline66没有 B 帧，没有 CABAC。视频通话常用
Main77加上 B 帧和 CABAC
High100再加 8×8 变换。现在最常见
High 1011010 位。手机的硬件解码器大多不支持

级别 3.1 的上限是每帧 3600 个宏块、每秒 108,000 个宏块，正好是 1280×720、30 fps。1080p30 要 4.0，1080p60 要 4.2，4K 要 5.1 以上。

字段是怎么编码的

SPS 里的数大多不是定长的，用的是指数哥伦布码：数越小占的位越少。读法是先数前面有几个 0，设为 n，再读 n + 1 位，得到的数减 1：

1                  → 0
010                → 1
011                → 2
00100              → 3
0000001010000      → 79      （6 个 0，再读 7 位是 1010000 = 80，减 1）

最后一行就是示例 SPS 里的 pic_width_in_mbs_minus1。slice 头和宏块数据里的大部分字段也是这样编码的。

05一帧切成 3600 个宏块

编码的基本单位是宏块：16×16 个亮度像素，加上对应的两块 8×8 色度。1280×720 是 80 × 45 = 3600 个宏块，从左到右、从上到下依次编码。每个宏块自己选一种预测方式：

宏块类型怎么预测码流里存什么
帧内 16×16整块用左边和上边的像素推出来，4 种方式选了哪种方式 + 残差
帧内 4×4、8×8切成小块，每块各选一个方向，9 种每小块的方向 + 残差
帧间从参考帧里搬一块过来。可以再切成 16×8、8×8，最小到 4×4，每块各有各的运动矢量参考哪一帧、运动矢量 + 残差
跳过（skip）按周围宏块的运动推出一个位置，从参考帧原样搬过来几乎什么都不存

运动矢量精确到四分之一个像素。参考帧里并没有"半个像素"的位置，解码器要用周围的像素插值算出来，这是帧间预测里计算量最大的部分。

示例里三帧的宏块是这样分的：

帧字节帧内 16×16帧内 4×4、8×8帧间跳过
第 1 帧，I76182763837——
第 5 帧，P957181232173179（88%）
第 4 帧，B9460353559（99%）

彩条是大片的纯色，所以 I 帧里四分之三的宏块用最省的 16×16 方式就够了。后面的帧里画面几乎不动，九成左右的宏块是跳过。

那个 94 字节的 B 帧一共 752 位，要描述 3600 个宏块，平均每个宏块 0.2 位。一个标志位都不止 1 位，这只有 CABAC 做得到：它是算术编码，一个几乎肯定会出现的符号可以只占零点几位。这也是视频能压到这种程度的最后一环。

06解一个宏块的五步

① 熵解码
  1. 从比特流里读出宏块类型、预测方式或运动矢量
  2. 读出量化后的系数
② 反量化、反变换
  1. 系数乘上量化步长
  2. 反变换得到残差
③ 预测
  1. 帧内：用邻居像素
  2. 帧间：到参考帧里取，需要时插值
④ 重建
  1. 预测 + 残差
  2. 得到这个宏块的像素

⑤ 整帧的宏块都重建完之后，再做一遍去块滤波：每个宏块是各自量化的，边界上会有肉眼可见的方格，滤波器把边界两侧的像素抹平。滤波后的画面才是最终输出，也是后面的帧参考的对象。

量化参数 QP

丢多少信息由量化参数 QP 决定，范围 0 到 51。QP 每加 6，量化步长翻一倍，残差记得粗一倍。示例每个 slice 头里的差值加上 PPS 的基准 26：

帧的类型slice_qp_deltaQP
I、P−1313
被参考的 B−1016
不被参考的 B−917

越多帧依赖的帧，QP 越低、画质越好，因为它的误差会传给所有参考它的帧。没人参考的 B 帧可以压得最狠。

两种熵编码

CAVLC 是查表的变长码，简单、快；CABAC 是算术编码，同样画质下码率低 10% 左右，但只能一位一位顺序解，是软件解码里最难并行的部分。用哪种写在 PPS 里，示例是 CABAC。Baseline 档次只能用 CAVLC。

H.264 的变换是整数运算，规范规定了每一步的精确结果。所以任何两个合格的解码器，解同一段码流得到的每个像素都完全相同，这和 AAC 不一样。验证视频解码可以直接逐字节比较。

按显示顺序，示例在开头的 I 帧之后每 4 帧一组：三个 B 帧，再跟一个 P 帧。中间那个 B 帧自己也被两边的 B 帧参考，所以 179 个 B 帧里有 60 个是被参考的，119 个不是，和第 02 节 NAL 头里数出来的一致。

关键帧和 IDR

IDR 是一种特殊的 I 帧：它之后的所有帧都不许参考它之前的帧。所以从 IDR 开始解码一定能得到正确的画面，跳转和直播中途加入都要从 IDR 开始。容器里标的"关键帧"指的就是它。

示例只有第 1 帧是 IDR。x264 的默认设置是最多隔 250 帧放一个关键帧，而整个视频只有 240 帧。结果是跳到任何位置都得从头解起：想看第 7 秒，要先解出前面 210 帧再扔掉。点播的视频一般 2 到 10 秒一个关键帧，直播 1 到 2 秒一个。关键帧越密，跳转和起播越快，码率越高。

08解码顺序和显示顺序

B 帧要参考它后面的帧，所以后面那帧必须先解。文件里的包是按解码顺序放的，和显示顺序不一样。示例的前 9 个包：

这张表里有两套互相独立的记法：

  • 容器记时间。dts 是该送进解码器的时刻，一路递增；pts 是该显示的时刻。播放器用 pts 决定什么时候把画面交给屏幕。这两个数在 MP4 里怎么存的见 MP4 封装格式。
  • 码流记次序。POC 是显示次序的计数，示例里每帧加 2；frame_num 每解完一个被参考的帧加 1，用来发现丢帧。解码器靠 POC 把解出来的帧排回显示顺序，不看容器的时间戳。

解码器的延迟

解码器解完一帧不能马上交出去，因为不知道后面会不会来一个该排在它前面的帧。SPS 里的 max_num_reorder_frames = 2 告诉它：最多等 2 帧就够了。所以送进第 1 个包不会立刻得到画面，要再送 2 个，第 1 帧才出来；之后每送一个出一帧；文件读完时解码器里还压着几帧，要专门取一次。

dts 从 −1024 开始也是这个原因：视频要提前两帧的时间开始解，第 1 帧才来得及在时刻 0 显示。

解码器手里还同时拿着最多 5 帧参考帧，加上正在解的和等着输出的，720p 下常驻十几 MB 内存，和文件大小没有关系。

09FFmpeg 的 h264 解码器

工程用的 FFmpeg n8.1.3 里，软件解码器的代码在 libavcodec/ 下，名字以 h264 开头。和前面几节的对应关系：

做什么文件
入口：收到一个包，拆出 NAL，按类型分发h264dec.c
按起始码或长度前缀拆 NAL，去掉插进去的 03h2645_parse.c
解析 avcC，读 SPS、PPSh264_parse.c、h264_ps.c
读 slice 头，准备参考帧列表h264_slice.c、h264_refs.c
① 熵解码h264_cabac.c、h264_cavlc.c
②③④ 反变换、预测、重建h264_mb.c，底层是 h264idct、h264pred、h264qpel
⑤ 去块滤波h264_loopfilter.c

调用方式和音频一样是"送包、收帧"，但有几处不同：

avcodec_parameters_to_context(dec, stream->codecpar);   // 把 avcC 交给解码器
dec->thread_count = 0;                                   // 0 = 按 CPU 核数自动开线程
avcodec_open2(dec, codec, NULL);

for (;;) {
    ret = avcodec_receive_frame(dec, frame);             // 先试着收
    if (ret == 0) { use(frame); continue; }
    if (ret != AVERROR(EAGAIN)) break;                   // 出错，或者全部取完了
    if (av_read_frame(fmt, pkt) < 0)
        avcodec_send_packet(dec, NULL);                  // 文件读完：送空包，把压着的帧挤出来
    else {
        if (pkt->stream_index == video_index) avcodec_send_packet(dec, pkt);
        av_packet_unref(pkt);
    }
}
  • 送和收不是一一对应的。开头要送几个包才有第一帧，结尾不送包还能收到几帧。循环必须按"能收就收，收不到再送"来写。
  • 多线程会让延迟更大。FFmpeg 默认的方式是几个线程同时各解一帧，开 N 个线程就要先多攒 N − 1 个包。总耗时短了，但第一帧出来得更晚。
  • 收到的帧已经按显示顺序排好了。frame->pts 是容器给的显示时间，解码器原样带过来。
  • frame->linesize 可能大于宽度。每行后面有填充，拷贝像素时要一行一行来。
  • 跳转之后要调 avcodec_flush_buffers。它清空参考帧和压着没输出的帧，否则跳转后的画面会参考到跳转前的帧。

10Android 硬解

手机的芯片里有专门解 H.264 的硬件电路，通过 MediaCodec 使用。同一段码流，硬解和软解的差别主要在外围：

FFmpeg 软解 h264MediaCodec 硬解
怎么选中AV_CODEC_ID_H264MIME 类型 video/avc
参数集从哪给extradata，可以直接是 avcCcsd-0 放 SPS，csd-1 放 PPS，都带起始码
包的格式两种包装都认起始码分隔
输出内存里的 AVFrame，三个平面直接画到 Surface；或者输出到缓冲区，排列方式由厂商决定，常见 NV12
耗电、发热全靠 CPU，分辨率越高越吃力低，1080p 和 4K 基本只能靠它
能解什么所有档次和级别看芯片：10 位、4:2:2、过高的级别常常不支持
结果是否一致所有设备相同像素相同，但个别机型有自己的毛病
  • 用 MediaExtractor 读 MP4 时不用操心格式。它给出的包已经换成了起始码，csd-0、csd-1 也填好了，直接送给 MediaCodec 就行。
  • 用 FFmpeg 解封装、MediaCodec 解码时要自己转。MP4 来的包是长度前缀的，要先过 h264_mp4toannexb。FFmpeg 自带的 h264_mediacodec 解码器内部做的就是这个转换。
  • 输出到缓冲区时要读输出格式。行宽（stride）、裁剪区域（crop-right、crop-bottom）、颜色格式都在 INFO_OUTPUT_FORMAT_CHANGED 之后的 MediaFormat 里，不能按视频的宽高想当然。

11落到 music_demo

工程的 FFmpeg 裁剪列表里，和 H.264 有关的是这些：

组件名字用途
解码器h264软件解码，播放用的就是它
解析器h264在没有容器的码流里找帧的边界
码流过滤器h264_mp4toannexb、extract_extradata在两种包装之间转换，给硬件编解码器用
编码器h264_mediacodec导出视频时用硬件编码

解码这一侧没有启用 h264_mediacodec，所以播放走的是纯软解。video_decoder.c 里的流程：

文件 ─▶ mov 解封装 ─▶ 视频包 ─▶ h264 软解 ─▶ AVFrame（yuv420p）
                                               │ 去掉每行的填充，Y、U、V 各拷进一个 ByteBuffer
                                               ▼
                         Kotlin：按 pts 等到点 ─▶ YuvGlRenderer 画到屏幕
  • 线程数设的是 0，由 FFmpeg 按 CPU 核数决定。示例只有 720p，软解没有压力。
  • 不是 8 位 4:2:0 的画面会先转一次。解码器输出别的像素格式时，代码用 sws_scale 统一转成 yuv420p，渲染那一侧只需要认一种格式。
  • 旋转角度不在 H.264 里。它记在容器里，由解封装器给出，见 MP4 封装格式。
  • 后面两步见 YUV 与像素格式 和 OpenGL 渲染；整条线见 一个视频是怎么播出来的。

12常见坑

现象原因处理
跳转后花屏、灰屏，过几秒自己恢复从不是关键帧的地方开始解，参考帧不存在跳到目标之前最近的关键帧，清空解码器，解到目标时间再显示
报 NAL 长度无效，或者找不到起始码两种包装弄混了看 extradata 的第一个字节；需要转换时用 h264_mp4toannexb
报引用了不存在的 PPS解码器没拿到 SPS、PPS软解检查 extradata；硬解检查 csd-0、csd-1
画面前后抖动按解码顺序或者按 dts 显示了用 pts
视频结尾少了几帧读完文件后没有把解码器里压着的帧取出来送一个空包，继续收到返回结束为止
1080p 的画面底部有一条绿边编码的是 1088 行，没按裁剪信息去掉多出来的 8 行软解用 frame->height；硬解读输出格式里的裁剪区域
颜色偏灰或者偏艳换算矩阵或亮度范围用错了读帧上的颜色信息，没写就按分辨率猜
硬解打不开或者输出全绿档次、级别或分辨率超出了芯片的能力先查 CodecCapabilities，不支持就回退到软解
跳转特别慢关键帧间隔太大编码时把间隔设小；播放端没有办法
竖屏视频横着显示旋转信息在容器里，解码器不管读容器的旋转角度，渲染时转

NAL 的类型和长度是从 music_demo 工程的 landscape_720p.mp4 逐字节解析的；SPS、PPS 和 slice 头的字段来自 ffmpeg -bsf:v trace_headers；帧类型和大小来自 ffprobe；宏块类型来自 ffmpeg -debug mb_type。文件名对照的是工程里的 FFmpeg n8.1.3 源码。
