YUV 与像素格式

视频解码器吐出来的不是屏幕用的 RGB，而是 YUV：一份亮度加两份缩小过的颜色。这份笔记讲一帧 YUV 在内存里怎么排、每个数代表什么、怎么换算成 RGB，以及换算时最容易弄错的两件事：用哪套系数，数值范围是多少。

解码器输出的三个字节Y 219 · U 16 · V 138
→
减零点、拉伸、乘矩阵BT.709 有限范围
→
屏幕上的 RGB254 · 255 · 0
→
看到的黄色

示例数据来自工程里 landscape_720p.mp4（H.264、1280×720、yuv420p、BT.709、有限范围）的第一帧，一张彩条测试图。这是画面正中间 (640, 360) 的像素，数值用 ffmpeg 导出原始帧后读出。

01一帧画面有多大

一帧画面是一个二维数组，每个像素若干个字节。解码后的数据量非常大：

RGB       1280 × 720 × 3 字节   = 2,764,800 字节 ≈ 2.76 MB
yuv420p   1280 × 720 × 1.5 字节 = 1,382,400 字节 ≈ 1.38 MB
一秒 30 帧的 yuv420p            ≈ 41 MB

示例视频 8 秒共 240 帧，解码后是 332 MB，而文件里的视频轨只有 84 KB。视频压缩比音频狠得多，所以解码后的帧不能攒着，只能解一帧、显示一帧、马上复用这块内存。

02为什么不是 RGB

RGB 把一个像素拆成红、绿、蓝三份。YUV 换了一种拆法：一份亮度 Y，加两份色度 U、V。

分量别名含义取值
Yluma这个像素有多亮。只看 Y 就是一张黑白照片16 是黑，235 是白
UCb蓝色偏离亮度多少128 是"不偏"，大于 128 偏蓝，小于偏黄
VCr红色偏离亮度多少128 是"不偏"，大于 128 偏红，小于偏青

U = V = 128 时没有颜色，画面是灰阶。示例帧里黑色是 (16, 128, 128)，白色是 (235, 128, 128)。

这样拆有两个好处：

  • 眼睛对亮度敏感，对颜色迟钝。把亮度和颜色分开后，颜色可以存得粗一些，眼睛看不出来。这是下一节色度抽样的前提，也是视频压缩的第一步。
  • 历史原因。彩色电视要兼容黑白电视：黑白机只收 Y，彩色机多收两路颜色。这套拆法一直沿用到今天的视频编码里。

Y 是 R、G、B 按固定权重相加：Y = Kr·R + Kg·G + Kb·B。绿色的权重最大，因为眼睛对绿色最敏感。权重具体是多少有几套标准，见第 06 节。

03色度抽样

既然眼睛对颜色不敏感，就让几个相邻像素共用一份颜色。Y 每个像素一个，U、V 少存一些。三种常见的存法：

4:4:4

每个像素都有自己的 U、V。每像素 3 字节，和 RGB 一样大。

4:2:2

横向每 2 个像素共用一份。每像素 2 字节。

4:2:0

每个 2×2 方块共用一份。每像素 1.5 字节。

实心格子是存了色度的位置，虚线格子借用旁边的。

手机拍的视频、网上的视频几乎都是 4:2:0。它的 U、V 平面宽和高各是画面的一半，面积是四分之一：

Y 平面   1280 × 720 = 921,600 字节
U 平面    640 × 360 = 230,400 字节
V 平面    640 × 360 = 230,400 字节
合计                  1,382,400 字节 = 宽 × 高 × 1.5

示例帧里 (640, 360) 所在的 2×2 方块，四个像素各有一个 Y，共用一个 U 和一个 V：

Y[360][640] = 219   Y[360][641] = 219        U[180][320] = 16
Y[361][640] = 219   Y[361][641] = 219        V[180][320] = 138

宽或高是奇数时，色度平面向上取整：(宽 + 1) / 2。工程里 YuvFrame 的 chromaWidth 就是这么算的。

04平面怎么排

同样是 4:2:0，三份数据在内存里的摆放方式有好几种。名字不同，数据量相同：

yuv420p（也叫 I420）   三个平面，各自连续
  YYYYYYYY
  YYYYYYYY
  UU
  VV

NV12                    两个平面，U 和 V 交错放在一起
  YYYYYYYY
  YYYYYYYY
  UVUV

NV21                    和 NV12 一样，只是 V 在前
  YYYYYYYY
  YYYYYYYY
  VUVU
格式常见出处FFmpeg 里的名字
yuv420p软件解码器的输出AV_PIX_FMT_YUV420P
NV12硬件解码器（MediaCodec）的常见输出AV_PIX_FMT_NV12
NV21Android 旧相机接口的默认预览格式AV_PIX_FMT_NV21

名字末尾的 p 是 planar，和音频采样格式里的 fltp 是同一个意思：每个分量各占一个数组。

按坐标取一个像素

// yuv420p，每个平面紧密排列（每行正好是宽度那么多字节）
val y = Y[row * width + col]
val u = U[(row / 2) * chromaWidth + col / 2]
val v = V[(row / 2) * chromaWidth + col / 2]

同一个 2×2 方块里的四个像素，row / 2 和 col / 2 相同，所以取到的是同一个 U 和 V。

05linesize 不等于宽度

上面的下标公式有个前提：每行正好是"宽度"那么多字节。解码器给出的 AVFrame 不保证这一点。为了让 SIMD 指令能整块处理，它会把每行补齐到 16、32 或 64 的倍数，每行的实际字节数记在 linesize 里：

frame->data[0]       Y 平面的起始地址
frame->linesize[0]   Y 平面每行占多少字节，可能大于 width

正确的下标：Y = data[0][row * linesize[0] + col]

把带填充的数据当成紧密排列来用，每一行都会错开几个字节，画面变成一条条斜纹，或者右边多出一条绿边。

工程里的做法是在 C 层就把填充去掉：逐行拷贝，每行只拷"宽度"那么多字节，Kotlin 拿到的三个缓冲区都是紧密排列的。

// app/src/main/cpp/video_decoder.c
// 源数据每行 linesize 字节（可能大于宽度），目标每行正好是宽度，所以必须逐行拷
av_image_copy_plane(dst[0], d->width, f->data[0], f->linesize[0], d->width, d->height);
av_image_copy_plane(dst[1], chroma_w, f->data[1], f->linesize[1], chroma_w, chroma_h);
av_image_copy_plane(dst[2], chroma_w, f->data[2], f->linesize[2], chroma_w, chroma_h);
不能用一次 memcpy 拷整个平面。除非确认 linesize 正好等于宽度。App 的播放页会显示解码器输出的像素格式和三个平面的"每行字节数"，可以直接看到实际的 linesize 是多少。

06换算成 RGB

屏幕只认 RGB，显示前必须换算。分三步：减去零点，把有限范围拉伸到满幅，乘一个 3×3 矩阵。写成归一化到 0–1 的形式就是一行：

rgb = matrix × (yuv − offset)

矩阵里的数由两个权重 Kr、Kb 决定（Kg = 1 − Kr − Kb），它们就是第 02 节里红、蓝在亮度中所占的比例。不同标准的权重不同：

标准KrKb用在哪FFmpeg color_space
BT.6010.2990.114标清bt470bg（5）、smpte170m（6）
BT.7090.21260.0722高清，今天最常见bt709（1）
BT.20200.26270.05934K、HDRbt2020nc（9）、bt2020c（10）

把 BT.709、有限范围的数代进去，就是常见的这组公式（Y、U、V 是 0–255 的原始字节）：

R = 1.164 × (Y − 16)                      + 1.793 × (V − 128)
G = 1.164 × (Y − 16) − 0.213 × (U − 128) − 0.533 × (V − 128)
B = 1.164 × (Y − 16) + 2.112 × (U − 128)

其中  1.164 = 255 ÷ 219          把 Y 的 16–235 拉伸到 0–255
      1.793 = 2 × (1 − Kr) × 255 ÷ 224
      2.112 = 2 × (1 − Kb) × 255 ÷ 224

系数用错会怎样

示例帧的彩条，同一组 YUV 分别按两套标准换算：

位置Y, U, V按 BT.709（正确）按 BT.601（用错）
(270, 360)188, 154, 160, 254, 25522, 255, 253
(450, 360)78, 214, 230255, 0, 254235, 0, 246
(640, 360)219, 16, 138254, 255, 0252, 255, 10
(810, 360)173, 42, 260, 255, 120, 255, 9
(990, 360)63, 102, 240255, 1, 0233, 0, 2

用错标准不会花屏，只是颜色偏一点：红色从 255 掉到 233，绿色里混进了红。黑、白、灰不受影响，因为它们的 U、V 都是 128，矩阵里和颜色有关的项全是零。这种偏差单看不明显，和别的播放器并排对比才看得出来，所以很容易漏掉。

07有限范围与全范围

8 位能表示 0–255，但视频通常只用中间一段：

范围YU、V别名常见出处
有限范围16–23516–240limited、tv、video range绝大多数视频文件
全范围0–2550–255full、pc、jpeg rangeJPEG 图片、部分手机录像

两头留出的空间来自模拟电视时代，用来容纳信号的过冲。换算时要把 16–235 拉伸回 0–255，这就是公式里 Y − 16 和 × 1.164 的来历。全范围则不减 16、不拉伸。

数据实际是却按…换算结果
有限范围全范围画面发灰：黑色是 (16,16,16) 的深灰，白色是 (235,235,235) 的浅灰
全范围有限范围对比度过强：暗部一片死黑，亮部一片死白，细节丢失

FFmpeg 里有一个旧的像素格式 yuvj420p，就是全范围的 yuv420p，数据排列完全相同，只是名字里带了范围信息。

08颜色信息从哪来

YUV 数组本身不带"我是哪套标准、什么范围"，和 PCM 不带采样率是一回事。这些信息写在视频流的参数里：

$ ffprobe -show_streams landscape_720p.mp4
pix_fmt=yuv420p
color_range=tv          ← 有限范围
color_space=bt709       ← 换算矩阵用 BT.709
color_transfer=unknown
color_primaries=unknown
字段决定什么AVCodecParameters
color_spaceYUV 和 RGB 之间用哪个矩阵color_space
color_range有限范围还是全范围color_range（1 = 有限，2 = 全范围）
color_primaries红、绿、蓝三原色的具体色度color_primaries
color_transfer数值和实际亮度的曲线（伽马、HDR）color_trc

前两个决定换算公式，本文只处理这两个。后两个涉及色域映射和 HDR，SDR 视频在普通屏幕上可以先不管。

很多文件根本没有标注，字段是 unknown。这时只能猜，通行的规则是按分辨率：高清用 BT.709，标清用 BT.601；范围按有限范围处理。工程里是这样写的：

// app/src/main/java/com/example/music/player/YuvColorMatrix.kt
fun fromFFmpeg(colorSpace: Int, height: Int): YuvStandard = when (colorSpace) {
  1 -> BT709
  5, 6 -> BT601
  9, 10 -> BT2020
  else -> if (height >= 720) BT709 else BT601     // 没标注：按高度猜
}

09位深

上面说的都是 8 位：每个分量一个字节。HDR 和一部分高质量视频是 10 位，每个分量 0–1023，渐变更平滑。内存里每个分量占 2 个字节（低 10 位有效），所以同样分辨率的一帧大一倍：

格式每个分量1280×720 一帧
yuv420p8 位，1 字节1.38 MB
yuv420p10le10 位，2 字节，小端2.76 MB

工程的渲染只接受 8 位 yuv420p。解码器输出别的格式时，C 层先用 libswscale 转成 8 位 yuv420p 再交给 Kotlin，代价是每帧多一次 CPU 转换，10 位视频的额外精度也丢掉了。

10落到 music_demo

文件和本文对应的部分
app/src/main/cpp/video_decoder.c解码出 AVFrame；不是 8 位 yuv420p 就用 swscale 转；按 linesize 逐行拷成紧密排列；把 color_space、color_range 回调给 Kotlin
player/YuvFrame.kt一帧的三个平面，各一块 direct ByteBuffer；色度宽高向上取整；帧池复用
player/YuvColorMatrix.kt三套标准的 Kr、Kb；由标准和范围算出矩阵与零点；没标注时按高度猜
player/YuvColorMatrixTest.kt单元测试：BT.709 有限范围的结果与 ffmpeg 一致，全范围保持黑白不变，没标注时的猜测规则
player/YuvGlRenderer.kt把矩阵和零点交给着色器，在 GPU 上逐像素换算

换算公式只写了一份：GPU 着色器用的矩阵和单元测试里 CPU 算的是同一个 YuvColorMatrix，所以测试验证过的颜色就是屏幕上的颜色。画到屏幕上的过程见 用 OpenGL 把 YUV 画到屏幕。

11常见坑

现象原因处理
整个画面偏绿U、V 全是 0（缓冲区没填，或者只拷了 Y）。U = V = 0 换算出来是绿色检查三个平面是否都拷了、大小是否正确
整个画面偏紫或偏粉U、V 全是 255，或越界读到了别的数据同上
红蓝互换：人脸发蓝U 和 V 弄反了，常见于 NV12 当 NV21，或平面顺序传错核对格式名和平面顺序
斜纹，或画面向一侧倾斜把带填充的数据当紧密排列用按 linesize 逐行拷贝
画面发灰，黑不够黑有限范围的数据按全范围换算读 color_range，没标注时按有限范围
颜色略偏，红色不够红BT.709 的数据用了 BT.601 的矩阵读 color_space，没标注时按分辨率猜
画面下方三分之一是花的把 yuv420p 当 NV12 读，色度平面错位核对像素格式
奇数宽高时最右一列或最下一行颜色不对色度尺寸用了 宽 / 2 而不是 (宽 + 1) / 2向上取整
