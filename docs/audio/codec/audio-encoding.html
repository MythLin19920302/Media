音频编码：PCM 之前的那一步

文件里存的几乎从来不是 PCM，而是压缩过的数据。播放时先解码成 PCM，才轮到 AudioTrack。这份笔记讲压缩是怎么回事：为什么能压到二十分之一还听不出来，压缩后的数据长什么样，以及解码器怎么把它还原成 PCM。

文件里的 AAC64 KB
→
346 个包，每个约186 字节
→
解码器每包 → 1024 个采样
→
内存里的 PCM1.41 MB

示例数据来自工程里 landscape_720p.mp4 的音轨（AAC-LC、44100 Hz、单声道、64 kbps、8 秒），数值用 ffprobe 读出。PCM 本身见 从 PCM 到喇叭。

01为什么要压缩

PCM 把每一瞬间的振膜位置都老老实实记下来，所以很大。示例音轨只有 8 秒、单声道：

PCM   44100 帧/秒 × 4 字节（float）× 8 秒 ≈ 1,411,200 字节 ≈ 1.41 MB
AAC   346 个包合计                          =    64,492 字节 ≈ 64 KB
                                              约 22 : 1

一首 4 分钟的立体声歌，16 位 PCM 约 42 MB，压成 AAC 约 4 MB。存储、下载和流量都按这个比例省下来，所以音乐文件、视频里的音轨、通话，用的都是压缩格式。

压缩后的数据不能直接送给喇叭。喇叭这一侧只认 PCM，所以播放链路上一定有一步解码。

02编码、容器、码率

三个最容易混的词：

词是什么示例文件里
编码格式（codec）压缩声音的算法和数据格式AAC
容器（container）把音轨、视频轨、时间戳、参数装在一起的文件格式MP4
码率（bitrate）每秒声音占多少比特约 64 kbps

扩展名说的是容器，不是编码。.mp4 里的音轨可能是 AAC，也可能是 MP3 或 Opus；.m4a 其实就是只有音轨的 MP4。只有少数格式两者同名，比如 .mp3、.flac。

码率     = 压缩数据的字节数 × 8 ÷ 时长
         = 64,492 × 8 ÷ 8.01 秒 ≈ 64 kbps
文件大小 ≈ 码率 × 时长 ÷ 8          例：128 kbps × 240 秒 ÷ 8 = 3.84 MB

码率是压缩时人为选定的预算。同一种编码，码率越高，丢掉的越少，音质越好，文件越大。它和采样率是两回事：采样率描述 PCM 有多密，码率描述压缩后有多大。

03有损与无损

压缩分两类。无损压缩解码后和原来的 PCM 逐位相同，像 zip；有损压缩解码后的 PCM 和原来不同，但设计目标是听不出来。

编码类型每帧采样数常见容器特点
AAC有损1024MP4、M4A、ADTS视频和流媒体里最常见
MP3有损1152MP3最老、兼容最广，同码率下音质不如 AAC
Opus有损通常 960OGG、WebM低延迟，低码率下表现好；内部固定按 48000 Hz 工作
Vorbis有损不固定OGGOpus 的前辈，游戏和老资源里常见
FLAC无损通常 4096FLAC大约压到原来的一半到七成
PCM（WAV）不压缩—WAV没有编码这一步，文件里直接就是 PCM

有损压缩能到十分之一以下，无损只能到一半左右，这个差距就是"扔掉听不见的东西"换来的。

04有损编码扔掉了什么

有损编码依赖一个事实：耳朵不是测量仪器，PCM 里有很多信息人根本听不到。

  • 太轻的声音听不到。每个频率都有一个最低可听音量，低于它的成分可以直接不存。耳朵对 2–5 kHz 最敏感，对很低和很高的频率迟钝得多。
  • 响的声音会盖住旁边轻的。一个很响的 1000 Hz 存在时，旁边 1100 Hz 的轻微声音就听不到了，这叫频域掩蔽。
  • 响的声音前后一小段时间里，轻的也听不到。一记鼓声之后几十毫秒内，耳朵还没恢复，这叫时域掩蔽。

要利用这些规律，得先知道每个频率上有多少能量，所以编码器不直接处理 PCM 波形，而是分四步：

① 切帧
  1. 取一段 PCM
  2. AAC 是 1024 个采样
② 变到频域
  1. 算出这一段里各个频率的强度
  2. 用的变换叫 MDCT
③ 按听感量化
  1. 听得清的频率记得细
  2. 被掩蔽的记得粗，或者不记
④ 无损打包
  1. 把量化后的数再压一遍
  2. 写成一个包

真正丢信息的只有第 ③ 步。码率就是这一步的预算：预算少，只好把更多频率记得更粗，于是高频发闷，或者出现"水声"一样的杂音。

解码出来的 PCM 和原始 PCM 逐个数对比是不一样的，波形图上也看得出差别。有损编码保证的是听起来一样，不是数值一样。所以不要用"比较 PCM 数值"来判断解码是否正确。

05一帧一帧地压

编码器不是把整首歌一次压完，而是每 1024 个采样压成一个包。播放器因此可以边读边解，也可以跳到中间某个包开始播。

一帧的时长 = 每帧采样数 ÷ 采样率 = 1024 ÷ 44100 ≈ 23.2 ms
包的个数   ≈ 时长 ÷ 一帧的时长  = 8 秒 ÷ 23.2 ms ≈ 345

每个包解出来都是 1024 个采样，但压缩后的大小并不相同。示例音轨开头几个包：

pts −1024271 B
pts 0243 B
pts 1024139 B
pts 2048163 B
pts 3072197 B
pts 4096212 B
pts 5120179 B
pts 6144195 B

全部 346 个包最小 139 字节、最大 271 字节、平均 186 字节。每个包对应的 PCM 都是 1024 × 4 = 4096 字节。第一个包的时间戳是负的，见第 07 节。

时间戳 pts 以采样数为单位，每个包加 1024，和 PCM 里"下标就是时间"是同一把尺子：秒 = pts ÷ 采样率。

包和帧，两个词

FFmpeg 的类型装的是示例里的大小
AVPacket压缩数据，解封装器给出约 186 字节
AVFrame解码后的 PCM，解码器给出4096 字节（1024 个 float）

06解码：从包到 PCM

解码是编码反过来：解开无损打包，把量化后的数还原成各频率的强度，再做一次反变换回到波形。数据在 FFmpeg 里经过四个组件：

文件 ──▶ demuxer ──▶ AVPacket ──▶ decoder ──▶ AVFrame ──▶ swresample ──▶ AudioTrack
         拆容器       压缩数据      解码        平面 float     转成交错排列      write()
         mov                        aac         fltp, 1024 帧  flt 或 s16

解码器用"送一个包、收若干帧"的方式工作：

while (av_read_frame(fmt, pkt) >= 0) {            // 解封装：读出一个包
    if (pkt->stream_index == audio_index) {
        avcodec_send_packet(dec, pkt);              // 送进解码器
        while (avcodec_receive_frame(dec, frame) == 0) {
            // frame->nb_samples   这一帧有多少个采样（AAC 是 1024）
            // frame->format       采样格式（AAC 是 AV_SAMPLE_FMT_FLTP）
            // frame->data[ch]     每个声道一个数组
            use_pcm(frame);
        }
    }
    av_packet_unref(pkt);
}
avcodec_send_packet(dec, NULL);                     // 读完后送空包，把解码器里剩下的帧取干净

"送"和"收"不是一一对应的：解码器内部可能攒着数据，送进一个包不一定马上出一帧，所以收的那一层是循环，结束时还要冲刷一次。

解码器内部每一步具体怎么算，拿一个包按位拆开看，见 AAC 解码。

解出来的 PCM 是什么格式

解码器输出什么格式由解码器自己决定，不由你决定。FFmpeg 自带的几个解码器：

解码器输出采样格式说明
aacfltp平面 float
mp3s16p平面 16 位整数。另有一个 mp3float 解码器输出 fltp
vorbisfltp
opusfltp采样率固定输出 48000 Hz，不管原始素材是多少
flacs16 或 s32取决于文件的位深

末尾带 p 的是平面排列，每个声道一个数组；AudioTrack 只收交错排列。所以解码之后通常要过一次 libswresample（swr_convert），把格式、排列方式和采样率统一成播放端要的那一种。三要素的含义见 PCM 的三要素。

07开头多出来的一个包

示例音轨有 346 个包，解码后只得到 345 帧。第一个包的时间戳是 −1024，并且带着"丢弃"标记：

pts     时长   字节  标记
-1024   1024   271   K D     ← D = 解码后丢弃
    0   1024   243   K
 1024   1024   139   K

原因在第 04 节的变换上。MDCT 的相邻两帧是互相重叠一半的，一帧的波形要和前一帧的后半段叠加才完整。文件里的第一帧没有"前一帧"，单独解出来是残缺的。所以编码器在最前面多放一帧垫底，它本身的输出不要，只为让后面那帧能解对。这段多出来的采样叫 priming，也叫编码器延迟。

这件事由解码器和解封装器配合处理，平时不用管。会碰到它的场合：

  • 无缝循环和拼接：如果没有丢掉 priming，每段开头会多出二十几毫秒，循环播放时听得到停顿。
  • 自己数采样算时长：包数 × 1024 会比真实时长多一帧。应该以时间戳为准。
  • 裸 ADTS 的 .aac 文件：没有容器来记录要丢多少，开头的 priming 通常会被原样播出来。

08参数存在哪里

解码器开工前要知道采样率、声道数、编码档次（profile）。这些参数不在每个包里重复，存放位置取决于容器：

形式参数在哪FFmpeg 里
MP4 / M4A 里的 AAC文件头里一小段全局配置（AudioSpecificConfig）。示例文件里只有 5 个字节AVCodecParameters.extradata
裸 .aac（ADTS）每个包前面都有一个 7 字节的 ADTS 头，重复写着采样率和声道数由 aac 解析器读出

那 5 个字节和 ADTS 头的每一位是什么，见 AAC 解码。

这是同一种编码的两种包装。把 ADTS 的 AAC 写进 MP4 时，要去掉每个包的头、改成一份全局配置，做这件事的就是码流过滤器 aac_adtstoasc。

打开解码器时要把容器里读到的参数交给它，否则它不知道怎么解：

avcodec_parameters_to_context(dec, stream->codecpar);   // 包括 extradata
avcodec_open2(dec, codec, NULL);

09落到 music_demo

App 里的 FFmpeg 是裁剪过的，只包含 ffmpeg/configure_android.sh 点名的组件。音频相关的是这些：

环节已启用能处理的文件
解封装mov、mp3、flac、wav、ogg、aac、matroskaMP4/M4A、MP3、FLAC、WAV、OGG/OPUS、裸 AAC、MKV/WebM
解析aac、mpegaudio、flac、vorbis、opus
解码aac、mp3、flac、vorbis、opus全部是软件解码
编码aac导出视频时压音轨
格式转换libswresample，滤镜 aresample、aformat解码后统一采样格式和采样率

WAV 没有对应的解码器条目：这个构建没有点名 pcm_s16le 这类 PCM 解码器，所以 WAV 目前能拆开容器但解不出数据，要播放 WAV 需要在裁剪列表里补上。每个参数的含义和怎么补，见 configure_android.sh 参数详解。

目前工程里的 JNI 代码只接了视频解码，音频解码还没有接进 App。

10常见坑

现象原因处理
播出来全是噪音把平面格式（fltp）的数据当交错格式写给了 AudioTrack，或者 float 当成了 16 位先过 swr_convert 转成播放端声明的格式
声音变快或变慢、变调播放端声明的采样率和解码输出的不一致，常见于 Opus 固定输出 48000 Hz以 frame->sample_rate 为准，不要用文件名或经验值
结尾少了一小段读完文件后没有送空包冲刷解码器avcodec_send_packet(dec, NULL) 后继续收帧
循环播放有缝开头的 priming 没丢掉用容器给的时间戳和丢弃标记；裸 AAC 换成 M4A
跳转后开头一声爆音跳到的那一帧缺少前一帧的重叠数据往前多解一两帧，丢掉它们的输出
转码一次比一次差有损编码每压一次都再丢一遍信息，提高码率也补不回来保留一份无损或原始素材，只从它导出
打开文件成功但没有声音轨可解裁剪时漏了这个格式的解码器或解析器查 config_components.h，在 configure 脚本里补上

包数、包大小、时间戳、码率和 extradata 长度是用 ffprobe 从 music_demo 工程的 landscape_720p.mp4 读出的；各解码器的输出格式取自 ffmpeg -h decoder=…。
